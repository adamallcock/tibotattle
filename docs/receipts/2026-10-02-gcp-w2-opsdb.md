## The production migration job

Order of work, each step refusing with a closed code:

1. The job context, environment and target are validated before any identity,
   manifest or SQL access. The target is the environment's configured
   instance (`ENVIRONMENT_PRIMARY_INSTANCE_CONNECTION_NAME`), or a scratch
   instance in the same project and region whose id matches
   `/-rehearsal-[a-z0-9]{8}b?$/`. Test instances, schemas, databases and
   identities are refused by identity and by the `test` token. Any `LEDGER_*`
   variable is refused (`POSTGRES_PRODUCTION_MIGRATIONS_LEDGER_FORBIDDEN`), as
   is a key-file identity (`GOOGLE_APPLICATION_CREDENTIALS`).
2. The attached identity must equal the configured migrator. It is read
   through google-auth-library's Application Default Credentials, which on
   Cloud Run calls the metadata server and checks its `Metadata-Flavor`
   header.
3. The image's primary migrations are read; the ledger directory is never
   read. Each contract migration must be in `CONTRACT_MIGRATIONS` with its
   sha256 and operations. The classifier flags drop, rename, SET NOT NULL, a
   NOT NULL column without a default, a column type change, a CHECK, UNIQUE,
   PRIMARY KEY, FOREIGN KEY or EXCLUDE constraint added without NOT VALID
   (or to a domain), a unique index, and any `EXECUTE` of dynamic SQL; a
   constraint or unique index on a table a plain `CREATE TABLE` makes in the
   same migration is exempt. It does not detect a constraint declared inline
   on an added column or behaviour changes inside trigger and function bodies;
   those are left to migration review, as its docstring states. The promoted
   tail 0001-0062 classifies as 23 contract migrations, all pinned with a
   reviewed reason. For a non-scratch target, a manifest without a migration
   named `*_append_only_residue.sql` after 0053 is refused
   `PRODUCTION_SIMP_RESIDUE_MISSING`.
4. The history is read read-only. Ahead of the image is
   `MIGRATION_STATE_NEWER_THAN_IMAGE`; not a prefix is
   `MIGRATION_HISTORY_DIVERGED`; neither writes anything.
5. Then `ensureSchema`, the canonical forward runner, the shared
   grant-and-verify to the distinct runtime role, `readBackReceipts`, and a
   production-only posture read-back of the runtime role (no cluster
   attribute, not a member of the migrator, no database CREATE, not the schema
   owner, no TRUNCATE, REFERENCES, TRIGGER or MAINTAIN).
6. One content-free receipt, `tibotattle-gcp-migration-v1`: target names,
   counts, the latest migration, manifest and history sha256, role names, the
   policy digest, `ledger: "not-migrated"`, and its own digest. It carries no
   execution name or timestamp, so a rerun's receipt is identical.

`PRODUCTION_MIGRATION_JOB` single-sources the job shape for OPS-3: manual,
migrator service account, one task, no retries, 1800 s, one primary
connection, entry `dist/production-migrations.mjs`.

## The rollout CLI

Without `--execute` a verb validates its inputs and prints argv; it runs no
`gcloud` and no `node`, makes no request, and runs only local read-only `git`
where an input check needs it. With `--execute`, a mutating verb needs
`--authorize=<verb>:<environment>:<commit or digest>` and runs under
`scripts/production-deployment-lock.mjs`'s lock, released on success and on
failure. Commands are argv through an injected runner, never a shell, and no
argv contains `delete`.

The environment's resources come from the OPS-2 infrastructure manifest's
`rolloutTarget(environment)`: `environment`, `project`, `region`, `service`,
`migrationJob`, `jobNames`, `primaryInstance`, `imageRepository`,
`builderServiceAccount`, `verifierServiceAccount` and `originAudience`.
`scripts/gcp-ops-infra-manifest.mjs` does not export it on this base, so every
verb refuses `ROLLOUT_INFRA_MANIFEST_UNAVAILABLE` until it does (checked).

- `preflight`: a clean tree at `--commit`; `node scripts/gcp-infra.mjs
  readback --require-clean --environment=<env>` exiting 0 with a JSON object;
  an OPS-1 audit receipt (`--backup-audit`) that verifies, names the target
  project and primary instance, is not `breach` and is at most six hours old;
  and the scheduled-jobs readback. That readback lists every Cloud Scheduler
  trigger in the target's location whose HTTP target is a Cloud Run job run
  URI (v1 or v2; any other `run.googleapis.com` URI counts as `unparsed`),
  with its state, and every execution of each manifest Job without a
  completion time. Preflight reports it and whether it is quiescent; it does
  not refuse a live trigger.
- `build`: renders `cloudbuild.production.yaml` (every placeholder but
  `${_IMAGE}`), runs `node scripts/cloud-run-build-archive.mjs` (the audited
  archive the test builds use), recomputes the archive's sha256 itself and
  refuses `ROLLOUT_BUILD_ARCHIVE_MISMATCH` if the tool's receipt differs, and
  submits that file. `assessProductionBuild` then checks the build's UUID id,
  `projectId` and regional `name`; no trigger, secret, approval or dependency
  field; `SUCCESS` under the builder account; options exactly
  `CLOUD_LOGGING_ONLY`, `sourceProvenanceHash: [SHA256]` and `VERIFIED`; the
  one pinned docker step with its exact arguments and the step image's
  resolved digest; a storage source whose resolved bucket, object and
  generation equal it; `sourceProvenance.fileHashes` with exactly that
  object, whose SHA256 equals the archive's (base64 or base64url); and one
  image at `<repository>:source-<commit>` with its digest. It is checked like
  the test build's `assessCloudBuildProvenance`, which is bound to the test
  target and so is not reused.
- `migrate`: the checkout's manifest must pass the contract review and carry
  the SIMP residue before any lock or backup. The live service's
  `DEPLOYMENT_SOURCE_COMMIT` must be readable (else
  `ROLLOUT_LIVE_COMMIT_UNKNOWN`, before the lock); it is the lock record's
  predecessor. Under the lock: preflight, and the jobs must be quiescent
  (`ROLLOUT_JOBS_NOT_PAUSED`, `ROLLOUT_JOBS_RUNNING`); two labelled
  `pre-migration` on-demand backups through OPS-1's `createOnDemandBackup`
  (30-day expiry, read back, distinct ids); the jobs are read again and must
  still be quiescent; then the migration Job moves to the digest and commit,
  runs with `--wait`, and its receipt is read from the execution's log and
  matched to the environment, commit, Job, environment target and local
  manifest. It writes a 0600, never-overwritten migrate receipt.
- `roll`: requires the matching migrate receipt (environment, project,
  commit, digest, image, Job, self-digest, at most 24 hours old) and an edge
  capture `{schema, capturedAt, snapshot, deployment}` (`--edge-live`) at
  most 15 minutes old, checked again under the lock right before the service
  moves. The capture's Worker must be the environment's tracked Worker
  (`wrangler.jsonc` `env.<environment>.name`; production must be EP-9's
  `app-usagemonitor` with its three custom domains), it must serve the
  tracked `PUBLIC_ORIGIN`, and it must verify for its own mode: worker,
  fenced and gcp through EP-9's `verifyEdgeModeLiveSnapshot` with the
  environment's own domains (`[]` for the workers.dev-only staging Worker),
  and a pre-edge Worker through the same identity facts (one active version
  at 100%, the snapshot's source commit, the domains). In gcp mode,
  `apps/worker/src/edge-origin-contract.ts` must have the same git blob at
  `--commit` and at the live edge's commit (else `EDGE_CONTRACT_DRIFT`), and
  the edge's `EDGE_UPSTREAM_ORIGIN` must be one of this service's run.app
  origins with `EDGE_ORIGIN_AUDIENCE` equal to the target's
  (`ROLLOUT_EDGE_ORIGIN_MISMATCH`, before the lock). Under the lock:
  preflight, quiescent jobs, then the service and every Job move to one image
  digest and `DEPLOYMENT_SOURCE_COMMIT` and are read back, and the
  infrastructure readback runs. Last, the served commit: in gcp mode the
  public `<PUBLIC_ORIGIN>/api/health` must answer 200, `status: "ok"` and
  `deployment.sourceCommit` equal to `--commit`; in every other mode the EP-6
  verifier path (`verifyEdgeOriginBeforeGcp` on the service's own run.app
  origin, with an identity token from `gcloud auth print-identity-token
  --impersonate-service-account=<verifier> --audiences=<originAudience>`, held
  in memory only) must report `--commit`. The roll receipt records the live
  predecessor commit, the edge mode, commit, contract blob and capture time,
  the served-commit path, the paused triggers OPS-3 `resume-all` must resume
  (the rollout never resumes one), and `secondsSinceMigrate`.

  `EDGE_E2E_GOLDEN` set for its S9 stage. Without them the spec is an
  `ENVIRONMENT_GAP` naming what is missing, and the run is `incomplete`

- The journal-transfer spec's TCP describe runs only when the caller supplies
  `PG_TEST_TCP_HOST`, so the socket-only shared cluster and the Worker gate

## Deviations from the brief, following the code

- `scripts/gcp-test-database.mjs` had no exports, and neither
  `gcp-backup-horizon.mjs` nor `gcp-test-build-context.mjs` imports it: the
  first pins its `INSTANCE_PATTERN` literal in a check, the second copies the
  file into the test image. Both are preserved.
- The attached-identity check uses Application Default Credentials rather
  than a direct metadata request: a new `cloud-run` module that reads the
  `Metadata-Flavor` response header fails
  `apps/worker/test/edge-request-header-allowlist.spec.ts`, which this package
  does not own and must not weaken.
- The OPS-1 audit enters preflight as a verified receipt file, because the
  audit CLI on this base still requires a separate ledger instance.
- The brief asks for two pre-migration backups. With one primary instance
  (D4) both are of that instance; they are independent restore points.
- OPS-3 `pause-all` and `resume-all` do not exist on this base, so migrate
  and roll require the operator to have paused the triggers and refuse
  otherwise; resuming stays an OPS-3 step after the roll.
- The production build uses `cloud-run-build-archive.mjs`, which includes
  `apps/web/public` as the image's assets, as the test and fast-path test
  builds do; the `e46ceb56` build used the context without them.

  W2-INFRA CLI on `claude/gcp-fp-w2-infra` (`b523ac64`) reads
  `readback --desired-state=<path>` rather than `readback --require-clean

  `EDGE_E2E` gap and exits `incomplete`.
- `apps/worker` `check` does not run the two new keys; the Cloud Run gate and
  the hosted suite do.
- `cloud-sql.mjs` connects with `ipType: "PUBLIC"`; a private-IP-only
  production instance needs that settled with OPS-2.
- The operator's gcloud identity must be able to impersonate the verifier
  account for a non-gcp-mode roll; nothing here grants that.
