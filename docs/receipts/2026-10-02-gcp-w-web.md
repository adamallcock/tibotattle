work only: nothing was pushed, deployed, or read from or written to any GCP or

## What changed

**(a) Unknown tuples are skipped and counted.** A breakdown tuple whose model id
is not in the page's reviewed catalog, or in a valid metadata block, is dropped
and counted (`unrecognizedModelTuples`, and `unrecognizedModelCount` for
distinct ids). One unknown model no longer nulls every breakdown. Everything
else is as closed as before: the tuple's shape and numbers are validated
whether or not its id is known (a non-string id, a fourth element, a zero or
non-finite number still refuse the whole block), a duplicated known id still
refuses it, and the per-day tuple cap is now a fixed 256 instead of the catalog
size. An unknown id is never retained, stored, or rendered, and the model view
says plainly that estimates for newer models are left out
(`community.allowance.unrecognizedModels`, in all three shipped languages).
Spark and other providers' models are unknown on this contract and are skipped.
The plan and aggregate views never depended on those tuples and do not show the
notice. The old canary cases ("unknown id nulls the block") are reworded as
"tuple dropped" in `community-model-tolerance.test.mjs`.

**(b) Optional, closed model metadata.** `allowanceBreakdowns` may carry
`modelConfig`, an array of `{ id, label, family, order }`:

- at most 128 entries; no extra keys; no duplicate ids;
- `id` is at most 128 characters from `A-Za-z0-9._:/+-`, a join key only;
- `label` is at most 80 characters of letters, digits, spaces and `.+_()×·/:-`,
  and is the only text the page prints;
- `family` is a lowercase token of at most 24 characters. A family in the
  closed set (`astra`, `sol`, `terra`, `luna`, `classic`) reuses that identity's
  icon and colour; any other family draws with the generic series colours;
- `order` is an integer from 0 to 9999. Models with a published order lead, by
  that order; every other model follows in the page's own order.

Metadata replaces a catalog model's label, adds models the catalog has never
seen, and never removes a model. It cannot promote a Spark or other-provider
model. The block is all-or-nothing: a malformed block is ignored whole and
reported as `modelMetadata: "rejected"`, and the page then draws exactly what
it would have without one. Without the block the page behaves as before. The
cache projection stores an applied block (and only that), so a cached render
re-reads as the same series; `COMMUNITY_DAILY_CACHE_SCHEMA_IDENTITY` is
unchanged because an older cache re-reads identically, and an older reader that
meets a newer cache simply refuses the breakdowns while the activity renders.
The wire contract is in `docs/reference/api-surface.md`. No server emits the
block yet.

**(c) A catalog-known model off the roster.** On `afd865a0` the roster is
already derived from the catalog, so every primary Codex model the catalog names
is drawn when it has an estimate (tested with GPT-5.4, GPT-4.1 and o3). On the
main tip the cause is a hand roster, and the roster is **not an accident**:
commit `2d6cfbc8` (2026-09-28, "show six requested public allowance models")
made it an owner request, and the tests assert that GPT-5.5 is not shown. So the
main-tip branch does not simply draw everything the catalog names. It keeps the
roster, pinned (a roster model keeps its card while it has no estimate), turns
the older generations it leaves off into an **explicit frozen hide list**
(35 ids at `reviewed-model-catalog-2026-09-29.1`), and charts everything else.
A model appended to the catalog later is therefore charted as soon as the server
publishes an estimate for it, with no page edit, and only once it has one. A
metadata block also charts a hidden model it names. Hidden models' tuples stay
valid and stored exactly as before. **Owner decision needed:** confirm the hide
list keeps the intent of `2d6cfbc8`. The simplest alternative, a roster only
with the omission made visible, would leave a newly appended model undrawn until
someone edits the page.

**The 192 KiB gate.** It was `test/admin-model-history.test.js`, not source. It
compared the model history alone with `192 * 1024`, "leaving a separately tested
64 KiB allowance for the outer blended preview". The real ceiling is the Worker
guard `PREVIEW_CACHE_JSON_LIMIT_BYTES` (256 KiB), which equals the storage CHECK
(262,144) on `analytics_community_graph_previews` (D1) and
`community_graph_previews` (PostgreSQL). Over it, the cache is reported
unavailable and the public per-model graph stops updating.

- No test measured the 64 KiB. At the main tip's four plans the outer preview
  alone is 71,767 B at the widest serialization (70.1 KiB), and the model history
  alone is 190,513 B (186.0 KiB, the research note's number). Together they are
  262,280 B, **136 B over the ceiling before any new model.** The old gate passed
  only because it never added them. It passed at 186.0 KiB and tripped at the
  second new model (about 190 KiB, then 195 KiB).
- Raising the guard is not a test change: the ceiling is a CHECK in D1 and
  PostgreSQL, so it needs a migration for each store. Not done here.
- The gate now accounts for the whole preview against the real ceiling. The
  ceiling is read from the Worker source and must equal the narrowest CHECK it
  can read; the preview's key list is read from the Worker validator, so a new
  field fails the gate until it is measured; the plan count is read from source
  (never fewer than four). Dollars stay at the widest finite double. Counts are
  bounded at eight digits, about three thousand times the 32,768-owner cohort that the
  2 MiB capture budget allows. Everything else is the widest the validators
  accept.
- Result: 231,234 B of 262,144 B on `afd865a0` (room for 7 more primary models
  at 4,327 B each) and 234,767 B on the main tip (room for 6). The guard itself,
  a hard `total < ceiling`, is kept. There is no early-warning floor, only a
  diagnostic of the spare models.
- The one assumption that is not anchored in source is the eight-digit count
  bound. A real count above 99,999,999 would be a defect elsewhere; the Worker's
  own write-time byte check remains the backstop.
- The structural fix is out of scope: drop the redundant `modelConfig` from the
  cached preview (about 4.6 KB), or store dollars as integer cents, both under a
  successor preview schema. The vendored kernels are byte-identical to
  `d43c8f92` and were not touched.

## Rendered result

A disposable loopback server served `apps/web/public` with a synthetic
`/api/v1/community/daily` payload, and the community page was inspected in the
Browser pane. Browser rendering does not qualify the packaged app or the public
deployment. The pane's page was hidden, so the refresh controller was released
by overriding `document.visibilityState` for the check.

- **Metadata present** (a metadata-only model in a known family, one in an
  unknown family, one hidden catalog model, one unknown id): the models view led
  with the published-order models, then the page's own order. The known-family
  model took the Sol icon and colour, the unknown-family one the generic colour
  with no icon. The unknown id appeared nowhere in the DOM, and the notice read
  "Estimates for newer models this page does not recognize yet are not shown.
  Plan and aggregate figures are not affected." The main-tip build kept the
  roster's empty cards ("—") and left the hidden models off.
- **Same payload without metadata:** the metadata-only models were skipped, the
  page drew the rest, and the notice appeared.
- **Only unknown tuples:** the "no identified model estimates" state plus the
  notice, with no leak.
- **Observation, not changed:** the legend is a translucent overlay on the top
  of the plot (`styles.css`, `.allowance-series-legend`). With six model series
  it wraps. At 375 px the legend is 84 px over a 95 px plot, hiding most of it;
  at 1,280 px it covers the highest series. It exists today whenever four or
  five models have data. More drawn models make it more likely. The main tip
  already switches the maximized dialog to an in-flow legend; the inline view
  needs the same, or a plot margin that follows the legend rows.
