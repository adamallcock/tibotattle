# GCP K-V0X guard on the v0.x admission price columns

This is a 2026-10-02 receipt for stream K-V0X on branch
`claude/gcp-fp-k-v0x`, built on `1bea3b5f` (`claude/gcp-fastpath-final`). It is
carried by two commits: `cd1d110d` (the guard) and a review-fix commit on top of
it (the wildcard analysis and the origin reach proof, see "Review fixes"). It
records **local, synthetic** evidence only: one macOS arm64 workstation, Node 26.2.0 (the
repository toolchain) and Node 22.16.0 (the image runtime), and esbuild 0.28.2
from `apps/worker/cloud-run`. The guard reads source and runs esbuild in
memory; it needs no database, so the PostgreSQL 17 fan-out cluster was not
used and no `k_v0x` object was created. No `gcloud`, `wrangler` or push ran,
nothing was built in Cloud Build, deployed or migrated, and no production or
Cloudflare resource was read.

The work is cross-check build-order step 1 in
`design/wave5-critic-2026-10-02.json` and the K-V0X package in
`design/engine-v2-design-2026-10-02.md` section 6.6. Round 7 of
`design/owner-decisions-2026-10-02-answers.md` drops the KM-6 intake rewrite
and the v0.x admission repricing and keeps this guard, so uploads stay stored
exactly as sent and the stored v0.x price is never consumed. No owner decision
was taken here, and the guard does not depend on OD-8 (whether v0.1 and v0.2
intake retire): it constrains readers, not the admission writer.

## The rule

A v0.x contribution is priced once, at upload, and the result is stored beside
the record. Twenty distinct columns hold it: fifteen on `telemetry_records` and
eleven on `telemetry_contributions`, six of them on both. They are declared in
D1 `migrations/0006_server_pricing.sql` and
`0022_historical_price_provenance.sql` and in PostgreSQL primary
`0011_retained_telemetry.sql`. They are **admission receipts**: they hold the
registry and method that happened to be live at upload, so a consumer that read
them would price an old registry into new analysis, and that price would never
move when the registry does. Everything else prices from the stored
quantities (the token columns and `record_json`) through the current registry,
as the v1 readers already do through `priceTelemetryUsageEvent`. A future
consumer of v0.x rows (E-NONEFF, an admin view, a v0.2 graph port) follows the
same rule; a tool that must copy receipts verbatim, such as the v0.x importer,
needs its own reviewed role in the allowlist.

## What the guard enforces

All six parts run with no database.

1. **Source scan.** Every JavaScript or TypeScript module under the Worker's
   `src`, `cloud-run`, `scripts`, `vendor` and `ops` directories (tests
   excluded by file name, as in `postgres-retired-analytics-readers.check.mjs`)
   that names one of the 20 columns must be listed in `ALLOWED` with a role,
   the mention kinds that role may hold, and a ceiling. An unlisted file, a kind
   the role does not allow, or a count above the ceiling fails. The list only
   shrinks: fewer mentions pass and are reported as slack. Mentions are
   classified as `write` (an INSERT column list or an UPDATE assignment),
   `inventory` (a whole line of quoted identifiers), or `read` (everything
   else, including a comment, a row-type field and a property access). A comment
   is deliberately not exempt, because no comment-stripping rule can be made
   free of loopholes.
2. **Wildcard reads, in code and in SQL.** A statement whose select list holds
   a bare `*`, an `alias.*` or a whole row (`to_jsonb(r)`, `row_to_json(r)`, a
   bare alias, `(r).*`) over a `FROM` clause that names `telemetry_records` or
   `telemetry_contributions`, alone or joined to other tables, returns every
   receipt column without naming one, and so does a `RETURNING` list of that
   shape on an `INSERT`, `UPDATE` or `DELETE` of them. The analysis reads each
   `SELECT` and `RETURNING` as a statement: it normalizes the source so every
   reference to a retained table (any schema qualifier or interpolated table
   helper) is one token, finds the select list and the tables joined at the
   statement's own depth, and tests the list. A CTE, subquery or
   `INSERT ... SELECT` body is a statement of its own. A wildcard is a
   `wildcard` mention held to the same allowlist, and it is detected in the
   PostgreSQL SQL under `postgres/` too, so a view over `SELECT *` is refused.
3. **PostgreSQL SQL.** No migration, staged migration or proposal under
   `postgres/` names a column except the column definitions of
   `0011_retained_telemetry.sql` (`ddl`), so no view, trigger, function or index
   can read a receipt either.
4. **DDL cross-check.** `PRICE_COLUMNS` equals what the D1 migrations and
   PostgreSQL 0011 each declare, and no SQL file anywhere under `apps/worker`
   names another `server_` identifier, so a new receipt column cannot appear
   unclassified.
5. **Bundle proof.** The entry points of `cloud-run/build.mjs` (parsed from its
   source, refused if any line of the entry block is not recognised) are bundled
   in memory with its own options, and the modules whose **shipped** text names
   a column are listed per entry. `analytics-refresh.mjs` and every entry except
   `server.mjs` ship none. This is what covers the vendored reader, which cannot
   be edited and which a source scan can only list.
6. **Reach proof.** The origin ships the Worker's D1 code, so a new route
   bundled into it could import a D1 reader and call it without naming a
   column, and neither the source scan nor the shipped text would see it. For
   every entry that ships a reader (only `server.mjs`), the import graph is read
   from the esbuild metafile (static and dynamic imports, externals excluded)
   and the modules that can reach a D1 reader (`src/telemetry-repository.ts`,
   `src/quota-analysis.ts`, derived from the `d1-legacy` allowlist entries) are
   compared with `D1_REACH`: for each such module, the imports that lead to a
   reader too. At `1bea3b5f` that is 27 modules and 69 imports. A new importer, a
   new import into an existing member (the host, a GCP port or the Worker's
   index), or an entry that ships a reader and has no reviewed reach, fails.
   This proves the import graph, not which export is called: it is a static
   reach, so the GCP ports that import only helper functions from a D1 module
   (the admission module takes `telemetryContributionAdmissionWindow` and
   `telemetryEnvelopeDigest` from the D1 repository) are members of the reach and
   are recorded there. A reviewed importer that starts calling another export of
   a reader it already imports is not seen; the source scan and the shipped
   text cover that only when a column is named.

### Why the D1 readers were not changed

Nothing in the GCP line needed to comply. The three D1 modules are recorded
rather than rewritten, for these reasons.

- **They are Cloudflare production code at the parity basis.** Pricing
  `accountScopedQuotaAnalysis` from quantities would change what d43c8f92
  computes for v0.2 participants, and the cutover claim is byte parity with
  that commit. The vendored copy is generator-owned and verified against
  d43c8f92 by `vendor:kernels:check`, so it cannot be edited at all.
- **They cannot run on GCP.** The origin binds `USAGE_MONITOR_DB` and
  `DELETION_LEDGER` to `throwingD1(...)`, a Proxy whose every property access
  throws (`cloud-run/server.mjs:326-331` and `:450-451` at `1bea3b5f`), so a D1
  reader fails before it runs a statement. They reach the origin bundle only
  because it composes the Worker's `index.ts`, and the bundle proof lists exactly
  that: `server.mjs` ships the admission module and the two Worker D1 modules,
  and nothing else ships any. The reach proof now pins which modules of the
  origin can import them, so a new route that does is refused. That the D1
  handles throw is still read from the source: the guard does not pin
  `throwingD1` itself, because D-CRB is rewriting the host composition.
- **The analytics path never reaches them.** `analytics-refresh.mjs` ships no
  module that names a column, so the vendored copy's reader is tree-shaken out.
  GCP analytics computes only owners routed `effective`; every other owner,
  including a legacy-only v0.2 owner, gets the `non_effective_source_unported`
  refusal and is never evaluated (`src/analytics-v2/compute.ts` header and
  `:590-603`). A v0.x record reaches GCP analytics only as typed quantities
  (`typed_telemetry_*`, primary 0030), which carry no `server_` column, and the
  vendored v1 reader prices those through `priceTelemetryUsageEvent`.
- **They retire with the Worker.** Each entry says so, and the check's slack
  output names the entry to delete when the D1 module goes.

What the allowlist forbids is more mentions than today (107, 10 and 10), any
use of the admission module other than writing, and any new import path into
the D1 readers from the origin.

## Not covered

- A wildcard the analysis cannot read: a table reached through a view, a
  table named at run time (`FROM ${name}`), a retained table inside a
  parenthesised join group, and a column name assembled at run time. The named
  scan, the bundle proof and the reach proof are the guarantee for those. A
  `SELECT` that has no `FROM` before the next statement is skipped, and the
  analysis reads at most 1,500 characters of a select list.
- Which export is called. The reach proof is a static import graph: a reviewed
  importer of a reader (the admission module, `src/index.ts`) that starts
  calling another export of it is not seen unless it names a column, and an
  `import()` whose specifier is built at run time is not resolved by esbuild at
  all. The graph is also a superset of what runs: it lists the GCP ports that
  reach a D1 module through helper imports only.
- The reviewed reach is pinned to the 69 imports read at `1bea3b5f`. A merge
  that adds or removes an import among those 27 modules changes it and needs the
  edit in `D1_REACH`; the check prints the exact edge, and prints a removed edge
  as slack.
- The guard is source and bundle evidence. It does not run a database or the
  origin, and it does not prove the D1 handles throw (see above).
- Test files are excluded by name, so a production module named `*.spec.*` would
  not be scanned; the bundle proof would still list it if it shipped.
- No full `npm run product:worker:check`, Worker Vitest, PostgreSQL spec or root
  `npm test` ran. The change adds no Worker route and no root product code.
- No R7 regeneration. The change touches no workload source.

## Observations for integration

- **K-VENDOR** will move the vendor path. The vendored entry in `ALLOWED` and the
  assertion that no bundle ships it name
  `vendor/analytics-d43c8f92/apps/worker/src/quota-analysis.ts`; update that one
  path, and re-count the entry if the re-vendor changes the file. Run
  `npm run v0x:admission:check` after any vendor change.
- **D-PT5A (the v0.x importer)** and any other tool that must copy receipts
  verbatim: if it names a column it will fail the check. Give it a reviewed role
  with copy-only semantics instead of widening an existing one.
- **D-CRB and the later route ports** must not import the D1 repository or quota
  modules into a new GCP route, and must not read a receipt column. The check
  fails if they do: a new importer of either module, or of any module that can
  reach them, and a new import into an existing member (including
  `cloud-run/server.mjs`), are refused until `D1_REACH` is edited, and that edit
  is the review. If D-CRB rewrites the host composition and changes
  `server.mjs`'s imports, expect to update the four `cloud-run/server.mjs` edges
  in `D1_REACH`.
- **K-REPRICE, E-NONEFF and OD-8.** A v0.x consumer prices from the stored token
  columns through the K-REPRICE function. If OD-8 retires v0.x, design section
  6.6 item 3 (record the snapshots as inert) is still open and is not done here.
- **Merge sites.** `apps/worker/package.json` gains one script and one `&&`
  step in `check`; the plan edit touches two table cells. Both are single-line
  changes.
- **The check needs esbuild from `apps/worker/cloud-run`.** The Worker gate in
  `hosted-backend.yml` already installs that lockfile (a contract test pins it).
  Without it the check fails with a named code and never passes silently.
- **An unwired sibling.** `scripts/postgres-retired-analytics-readers.check.mjs`
  is named in no `package.json` script and no workflow, so it is not enforced;
  this change did not touch it. C-CI or the integrator may want to wire it the
  same way.
- **The ceiling for the guard's own list** (`scripts/v0x-admission-price-readers.mjs`)
  is 20 `inventory` mentions; adding a column means editing `PRICE_COLUMNS`,
  the DDL cross-check and the ceilings together.
