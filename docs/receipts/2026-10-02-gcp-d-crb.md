# GCP D-CRB production origin composition (CR-6/CR-7 phase B)

This is a 2026-10-02 receipt for branch `claude/gcp-fp-d-crb`, built on
`fce3572e` (`claude/gcp-fastpath-final` when the worktree was made) with
W3-CRA phase A (`3024a521`) merged in first (`aaeb86f5`). It records
**local, synthetic** evidence only: one macOS arm64 workstation, Node 26.2.0
for the checks and scripts, Node 22.16.0 for the image runtime (E12 and the
built entries), and the local PostgreSQL 17 fan-out cluster. No Cloudflare or
Google Cloud resource was read or written, no Wrangler deploy or gcloud
command ran, and no production data was used. Every token, key, account,
host, commit and row is a fixture constant. Nothing was pushed or merged.

`claude/gcp-fastpath-final` has since moved to `f8a8620d` (D-PT4X, primary
0066 and 0067). This branch is not rebased onto it; see
[Integration](#integration).

## Scope

Phase B of CR-6 and CR-7: the request-serving origin composed for
`HOST_MODE=production` and `HOST_MODE=staging` from CR-3's configuration
alone, behind EP-6, over the one CR-6 registry; the fastpath-test and
edge-test modes re-composed on the same pipeline; and every D-CRB item of
the cutover checklist (section D) and the owner answers through round 12.
No migration was added (`stagedMigrations` is empty).

## What landed

### The production host (CR-7)

- `cloud-run/postgres-production-host.mjs` (new) is the composition root.
  `createPostgresProductionRuntime({processEnv, hostMode, adminHostPolicy,
  dependencies})` reads CR-3 (`readProductionConfiguration`) and opens three
  pools on the one primary (data 3, admission 4, readiness 1; application
  names `tibotattle-origin-<name>`), the origin-tier limiters from
  `cfg.rateLimits.originTier` with `cfg.admissionTimeouts` (staging gets
  300/6), the PostgreSQL ingress budget, the edge-tier admission bindings,
  `createProductionWorkerEnv`, the GCS store with CR-3's
  `resources.bucketHistoryProof` (OD-2), the storage gate (TTL 0), RD-2 and
  RD-3, the families (`composeOriginFamilies`, the one family composition all
  modes share), the registry, the CR-6 handler and EP-6. A refusal after the
  first pool closes every pool and the connector.
- Owner answers pinned as constants: `PRODUCTION_ADMIN_HOST_POLICY = "refuse"`
  (OD-CR-3; ADMIN-R12 flips it, see [Open issues](#open-issues)),
  `PRODUCTION_UNPORTED_RETRY_AFTER_SECONDS = null` (OD-CR-6 iv),
  `PRODUCTION_STORAGE_GATE_TTL_MILLISECONDS = 0` (OD-ROLL / OD-CR-10).
- Bind address (`productionListenHost`): `0.0.0.0` only when `HOST=0.0.0.0`,
  `K_SERVICE` equals CR-3's validated service name and the host origin is a
  run.app origin; unset or `127.0.0.1` binds loopback; anything else is
  `HOST_INVALID`.
- `isProductionConfiguration` (CR-3, new export) admits only an issued
  configuration (WeakSet provenance); a lookalike object is refused by the
  families' origin admission and by the host, with negative tests.
- `cloud-run/server.mjs`: `HOST_MODE` is read first. An unknown value is
  `HOST_MODE_INVALID`; a non-empty `POSTGRES_TEST_HTTP_MODE` beside it is
  `HOST_MODE_CONFLICT`; `--scheduled` is
  `POSTGRES_SCHEDULED_HOST_MODE_FORBIDDEN`; the owner fixture commands are
  `HOST_MODE_COMMAND_UNSUPPORTED`. The Worker-env tail, the throwing D1 and
  the source-digest plumbing are deleted: without a test mode or
  `HOST_MODE` the dispatch answers `503 POSTGRES_REQUEST_PATH_UNSUPPORTED`
  and never reaches a Worker handler. `serve()` sets the production server
  timeouts (300 s request, 60 s headers) and accepts the run.app host or a
  Cloud Run revision tag of it.
- `cloud-run/Dockerfile`: `USER node` before `CMD`; the copied code stays
  root-owned (no `--chown`), pinned by a check.

### The registry and handler (CR-6)

- One registry: `createProductionRouteRegistry` folds the origin route
  modules (`ORIGIN_OVERRIDABLE_BUILT_INS`, issued registries only) over the
  built-ins. A new `admin` class holds the six admin console ids (OD-CR-2
  now 13). `src/backend-composition.ts` exports the ported list (30: scope
  plus all nine OD-CR-1) and the six admin ids;
  `isPostgresWorkerRequestPathSupported(pathname)` reads it.
- Admin host: `refuse` answers `503 POSTGRES_ROUTE_NOT_PORTED` before
  anything; `chokepoint` (built and tested, not selected) runs
  `createPostgresAdminAccessChokepoint` on every admin-host request first,
  then dispatches a ported admin id with `{requestId, routeId,
  adminIdentityKey}` and without the registry's method envelope; unported
  admin ids keep the envelope, then 503. The six ids stay 404 on the apex.
  The families' origin admission admits the CR-3 admin origin (critic
  hostGap 6).
- OD-CR-6 (i) fixed: every family error envelope carries the edge's request
  id (`requestIdFrom`, one accessor helper shared by the families, the v1.1
  routes, the upload-authorization module and the community-daily module).
- A storage-gate failure before a route module (community daily) is now
  `503 BACKEND_STORAGE_UNAVAILABLE`, not `500 INTERNAL_ERROR`: the real gate
  throws a plain error with status 503, which the handler mapped to 500. The
  PostgreSQL spec found this; the handler check now pins both throw shapes.

### Readiness and health (RD-2, RD-3)

- `cloud-run/postgres-readiness-dispatch.mjs` (new): the Worker preflight
  (admission, upload-authorization and ingress bindings, the ingress
  configuration and budget probe, sign-in-start admission) before any read;
  `readPostgresReadinessState` (`src/postgres-readiness.ts`) reads, in one
  read-only snapshot, the receipt through the one reader, the retention and
  reconciliation rows C-MAINT's pass writes, and the typed v1 and v1.1 pins
  for `TELEMETRY_STORAGE_NAMESPACE`; a single flight reuses an evaluation for
  1 s, as the Worker does (OD-CR-4 "worker-exact").
- `cloud-run/postgres-health-dispatch.mjs` (new): the Worker order
  (enrollment mode, preflight, controls, store shape, retention plus
  `SELECT 1`, the head probe, the source commit). OD-CR-5: the two capability
  flags derive from the registry, and the host refuses a drift between the
  flags it built and the registry's (`HEALTH_CAPABILITY_FLAGS_DRIFT`).
- First-roll ready path: `/api/ready` is `503` on a database no lifecycle
  pass has run against. `scripts/gcp-production-rollout.mjs` gains
  `maintenanceJob` (null, or one of `jobNames` other than the migration job),
  runs one execution of it after the roll and before verification
  (`ROLLOUT_MAINTENANCE_PASS_FAILED`), and refuses, before any write, a roll
  that verifies through the origin verifier without one
  (`ROLLOUT_MAINTENANCE_JOB_REQUIRED`). `gcp-ops-infra-manifest` derives
  `maintenanceJob` (null until D-OPS4 adds the job). The rollout also checks
  that the edge's `upstreamOrigin` equals the rolled service's `HOST_ORIGIN`
  (`ROLLOUT_SERVICE_HOST_ORIGIN_INVALID` for a service whose `HOST_ORIGIN`
  is not one of its own canonical run.app origins).

### Upload ingress

The contributions preamble follows the Worker order: authority check
(`ADMISSION_CONFIGURATION_INVALID` without one), configuration, binding,
`bodyReadPolicy` (60 s total, 15 s idle from CR-3), the preflight, the
ingress limiter, then `acquireLease` plus a heartbeat; the heartbeat is
asserted after the body, after the claim and after the handler; `finally`
stops it and releases the lease (a failed release logs one content-free
warn line). The fastpath and loopback modes inject the same authority with
the Worker defaults.

### One receipt reader (OWN-19) and one OD-2 grammar

- `src/postgres-schema-receipt.ts` (new) is the one migration-history
  reader: `readSchemaReceipt(client, {schema, expected})` with four closed
  statuses. The lifecycle pass, the storage gate
  (`createPostgresStorageGate`, `postgres-test-dispatch.mjs`) and RD-2 all
  use it. `scripts/ledger-absence.check.mjs` now has no reader exception
  (`RECEIPT_READER_EXCEPTIONS` deleted); a third copy fails the guard.
- The storage gate with TTL 0 reads the receipt independently on every
  request (no coalescing): coalesced reads released concurrent requests in
  lock step and exposed a pre-existing bearer race (see
  [Open issues](#open-issues)).
- `parseQuarantineBucketHistoryProof` (CR-3) is the one OD-2 grammar;
  `parseGcsQuarantineBucketHistoryProof` in `src/gcs-quarantine-object-store.ts`
  is deleted and the test host reads the proof through CR-3.
- `CLOUD_RUN_IAM_TEST_TARGET` moved to the import-free
  `cloud-run/cloud-run-iam-test-target.mjs` (fixes the Node 22.16 load of the
  analytics-refresh entry and a CR-3/dispatch import cycle); its 15
  importers follow.

### Test modes, E12 and edge-test (re-specified, not relaxed)

- fastpath-test and edge-test now answer through the same CR-6 handler,
  registry and RD-2/RD-3 the production host uses. edge-test lost its own
  served list, unported body and admin guard; the Node adapter
  (`originRequestFromNode`, `ORIGIN_REQUEST_REFUSAL_REASONS`) moved to
  `cloud-run/origin-node-request.mjs`.
- E12 (`postgres-test/edge-origin-e2e.spec.mjs`, harness, matrix): the
  served set is the composition's list; unported answers are the closed
  envelope with the edge's request id and no `retry-after`; `/api/ready`
  through the edge is served; the origin reads its ingress budget from
  wrangler `env.production`. Row S4 E was re-specified: the origin's own
  budget now refuses past 1,200 starts, so the row requires
  `claimed + budgetRefused == 3000` with at least 1,000 claimed and compares
  the first 1,000, instead of 3,000 claims.

### The edge-test deploy and test fixtures

The fastpath-test composition now reads the six upload-ingress settings,

## Open issues

1. **Staging service template not provided.** OPS-2 keeps
   `STAGING_SERVICE_TEMPLATE_UNAVAILABLE`. Rendering a staging service needs
   values and contract changes this branch cannot decide: CR-3 still
   requires `ACCESS_AUD` for staging, while round 11 says staging rolls
   without it (admin then answers `ADMIN_NOT_CONFIGURED`); CR-3 requires
   staging `GOOGLE_OIDC_CLIENT_ID` and `APPLE_*` values that do not exist,
   while round 12 retires the native social chain (ROUTES-R12); and
   `claude/gcp-fp-stg-prep` is changing the staging desired state. The
   composition itself (`HOST_MODE=staging`) is done and tested.
2. **Admin host flip (ADMIN-R12).** Round 12 answered OWN-17 (open with what
   is ported). The flip is one constant plus the overview's unavailable
   sections and the ledger DTO bump, which the checklist schedules after
   D-CRB.
3. **ROUTES-R12** (retirements and the definite 4xx for the accountless
   performance authorization) is not in this branch; those routes still
   answer the unported 503.
4. **Pre-existing bearer race (found here, not fixed).** Device bearer
   authentication reads `nowEpoch` before taking the row lock and compares
   `epoch <= nowEpoch`, so two concurrent replays released together can see
   `DEVICE_AUTH_INVALID`. TTL-0 gate reads are now independent per request,
   which avoids the lock-step release; the race itself needs its own fix.
5. **Maintenance job (D-OPS4).** `maintenanceJob` is null in the derived
   targets, so a roll that verifies through the origin verifier is refused
   until D-OPS4 adds the job and its every-minute trigger.
6. `apps/worker/AGENTS.md` health guidance (above).
