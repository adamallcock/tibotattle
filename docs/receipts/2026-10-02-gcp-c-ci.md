# GCP C-CI hosted backend workflow wiring

This is a 2026-10-02 receipt for stream C-CI on branch `claude/gcp-fp-c-ci`,
built on `claude/gcp-fastpath-final` at `afd865a0` in two commits: `cf5a22db`
(the workflow, its contract test and the workflow policy) and the commit that
adds this receipt. It records **local, synthetic** evidence only: one macOS
arm64 workstation, Node 26.2.0 for repository tooling, Node 22.16.0 (the image
runtime) for the edge end-to-end spec, and the local PostgreSQL 17.10 fan-out
cluster on a private Unix socket (port 55433, which also listens on loopback
TCP). **No GitHub Actions run happened.** Nothing was pushed, built in Cloud
Build, deployed or read in any GCP or Cloudflare project, and no `gcloud`,
`wrangler` or push ran.

The owner decision (`owner-decisions-2026-10-02-answers.md`, Infrastructure and
CI) was to fix and wire everything: the Cloud Run dependencies in the Worker
job, the production-tooling checks in the Cloud Run job, and Node 22.16.0 plus
the edge end-to-end golden for the PostgreSQL job.

### Worker gate

`npm --prefix apps/worker ci` does not install `apps/worker/cloud-run`, whose
lockfile owns `@google-cloud/cloud-sql-connector`. The Worker `check` runs
`gcp:fastpath:scripts-check`, and its `node --test` files reach
`cloud-run/analytics-refresh.mjs` through
`scripts/gcp-fastpath-test-deploy.mjs`. The install step now also runs
`npm --prefix apps/worker/cloud-run ci`, the same line the other two jobs
already had. The contract test checks the justification statically: the
closure of that script's test files reaches a Cloud Run module that imports the
connector, and the Worker package does not declare it.

### Cloud Run check

`gcp:production-tooling:local-check` is four components. Their placement:

| Component | Where it runs in hosted CI |
|---|---|
| `gcp:production-rollout:check` | `cloud-run-check`, its own step (19 tests; also inside the Cloud Run `check` script, so this repeats a few seconds of work for a one-to-one mapping) |
| `gcp:ops:infra:check` | `cloud-run-check`, its own step (179 tests) |
| `postgres:cutover-seal:check` | `cloud-run-check`, its own step (32 tests, about a minute, serial) |
| `postgres:production-migrations:check` | split: its offline half is already inside the Cloud Run `check` script, and its PostgreSQL-backed `postgres-production-migrations.spec.mjs` runs in `postgres-17-suite` through the suite's registration of that script |

The contract test requires the three explicit steps and forbids running
`gcp:production-tooling:local-check` or the split component whole in the Cloud
Run job. It reports a fifth component added to the local check as unclassified,
checks that the Cloud Run `check` script still names the offline half's files,
that the suite still registers the PostgreSQL-backed spec, and that no test file
of the three offline scripts reads `PG_TEST_*`.

### PostgreSQL 17 suite

The suite already has an explicit `EDGE_E2E` profile. It needs `EDGE_E2E_NODE`
(an absolute path that reports `v22.16.0`), workerd in the Worker's
`node_modules`, and `EDGE_E2E_GOLDEN` (an absolute path); otherwise it reports
`ENVIRONMENT_GAP` and exits `incomplete`. The job now:

1. installs Node 22.16.0 with the same pinned `actions/setup-node` revision;
2. checks `node --version`, checks that the committed golden's files exist and
   writes `EDGE_E2E_NODE` (`command -v node`), `EDGE_E2E_GOLDEN`
   (`$GITHUB_WORKSPACE/apps/worker/analytics-v2-test/golden`) and
   `POSTGRES_V12_TRANSFER_Q1_DUMP` (that golden's `dump/usage-monitor-db.json`)
   to `$GITHUB_ENV`;
3. installs Node 26.2.0 last, so `node` on PATH, the suite and every other spec
   stay on 26.2.0, and writes `EDGE_E2E_REHEARSAL_NODE` after checking that
   26.2.0 is active. S9's seeding rehearsal needs the newer `node:sqlite`; the
   final-merge receipt records the run that failed 14 of 15 when 22.16.0 was
   first on PATH.

`POSTGRES_V12_TRANSFER_Q1_DUMP` goes beyond the three items in the brief. The
full suite reported `SILENTLY_SKIPPED` for the transfer spec's Q-1 dump case
without it, which fails the job (see the first run below). The spec names
`dump/usage-monitor-db.json` of the Q-1 golden, which is committed.

### Workflow policy

Adding a second Node version made the toolchain a reviewed input, so the
policy refuses a range, alias, expression, partial version, v-prefixed spelling
or any version outside the allowlist, and refuses 22.16.0 in any workflow but
`hosted-backend.yml`. All 21 checked-in workflow and action files pass. Nothing
about actions, permissions, runners, checkout persistence or
`pull_request_target` changed.

## Not proven, and open

- **No GitHub run.** Hosted runner images, `actions/setup-node` resolving
  22.16.0 on ubuntu-24.04, the pinned PostgreSQL container, the Linux workerd
  binary and the 45 and 30 minute timeouts are untested. The
  local suite took 14 min 7 s, and its edge pass alone about 7 min on a shared
  machine; the job limit of 45 minutes was left unchanged, with no measurement
  on a runner.
- **The hosted `postgres-17-suite` job would still fail at `afd865a0`.** The
  full run's two failures are not workflow wiring and are outside this stream's
  files:
  - `postgres-test/typed-v12-normalized.spec.mjs`, HOST pass, "migrates forward
    from primary version 24": `TELEMETRY_REQUIRED` from
    `assertWriteAllowed`. It fails alone too. The v1.2 reader batch-cost
    receipt records the same failure at its base (the fixture participant has
    no `consent_version`, and then the erasure step trips the 0035 guard), and
    the cutover checklist lists it under red tests to clear before the merge
    to main.
  - `postgres-v12-transfer.spec.mjs`, the Q-1 dump case, reported
    `SILENTLY_SKIPPED` in that run. The workflow now sets
    `POSTGRES_V12_TRANSFER_Q1_DUMP`, and the spec alone passes with it, but no
    second full suite run followed the change (one broad run per commit).
- The Worker gate's full `npm --prefix apps/worker run check` was not run. Only
  `gcp:fastpath:scripts-check`, the new dependency's reason, was run both ways.
  The Cloud Run `check` script was not rerun: this change did not touch it.
- `npm --prefix apps/worker/cloud-run ci` was not run for real: nothing was
  installed or downloaded.
- The policy rule's negative cases live in `test/hosted-backend-workflow.test.js`
  because `test/release-workflow-policy.test.js`, the file the release-trust
  workflow runs, is outside this stream's ownership. Both workflows run the
  checker itself, so the rule is enforced in both; an integrator may move the
  two policy tests next to the others.
- Pushing, repository settings, secrets and environment approvals were not
  touched. A green hosted run would prove these source gates on one commit
  only. It would not be deployment, migration, release, signing or
  public-deployment evidence.
