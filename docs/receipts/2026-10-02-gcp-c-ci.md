# GCP C-CI hosted backend workflow wiring

This is a 2026-10-02 receipt for stream C-CI on branch `claude/gcp-fp-c-ci`,
built on `claude/gcp-fastpath-final` at `afd865a0` in three commits: `cf5a22db`
(the workflow, its contract test and the workflow policy), `4ef50dd5` (the first
version of this receipt) and the review-fix commit that is the branch head
(closes the `actions/setup-node` inputs to a reviewed list, and corrects this
receipt's account of the full-suite failures and of what the checklist item
covers; see [Review fixes](#review-fixes)). It records **local, synthetic**
evidence only: one macOS
arm64 workstation, Node 26.2.0 for repository tooling, Node 22.16.0 (the image
runtime) for the edge end-to-end spec, and the local PostgreSQL 17.10 fan-out
cluster on a private Unix socket (port 55433, which also listens on loopback
TCP). **No GitHub Actions run happened.** Nothing was pushed, built in Cloud
Build, deployed or read in any GCP or Cloudflare project, and no `gcloud`,
`wrangler` or push ran.

The owner decision (`owner-decisions-2026-10-02-answers.md`, Infrastructure and
CI) was to fix and wire everything: the Cloud Run dependencies in the Worker
job, the production-tooling checks in the Cloud Run job, and Node 22.16.0 plus
the edge end-to-end golden for the PostgreSQL job.

### Worker gate

`npm --prefix apps/worker ci` does not install `apps/worker/cloud-run`, whose
lockfile owns `@google-cloud/cloud-sql-connector`. The Worker `check` runs
`gcp:fastpath:scripts-check`, and its `node --test` files reach
`cloud-run/analytics-refresh.mjs` through
`scripts/gcp-fastpath-test-deploy.mjs`. The install step now also runs
`npm --prefix apps/worker/cloud-run ci`, the same line the other two jobs
already had. The contract test checks the justification statically: the
closure of that script's test files reaches a Cloud Run module that imports the
connector, and the Worker package does not declare it.

### Cloud Run check

`gcp:production-tooling:local-check` is four components. Their placement:

| Component | Where it runs in hosted CI |
|---|---|
| `gcp:production-rollout:check` | `cloud-run-check`, its own step (19 tests; also inside the Cloud Run `check` script, so this repeats a few seconds of work for a one-to-one mapping) |
| `gcp:ops:infra:check` | `cloud-run-check`, its own step (179 tests) |
| `postgres:cutover-seal:check` | `cloud-run-check`, its own step (32 tests, about a minute, serial) |
| `postgres:production-migrations:check` | split: its offline half is already inside the Cloud Run `check` script, and its PostgreSQL-backed `postgres-production-migrations.spec.mjs` runs in `postgres-17-suite` through the suite's registration of that script |

The contract test requires the three explicit steps and forbids running
`gcp:production-tooling:local-check` or the split component whole in the Cloud
Run job. It reports a fifth component added to the local check as unclassified,
checks that the Cloud Run `check` script still names the offline half's files,
that the suite still registers the PostgreSQL-backed spec, and that no test file
of the three offline scripts reads `PG_TEST_*`.

### PostgreSQL 17 suite

The suite already has an explicit `EDGE_E2E` profile. It needs `EDGE_E2E_NODE`
(an absolute path that reports `v22.16.0`), workerd in the Worker's
`node_modules`, and `EDGE_E2E_GOLDEN` (an absolute path); otherwise it reports
`ENVIRONMENT_GAP` and exits `incomplete`. The job now:

1. installs Node 22.16.0 with the same pinned `actions/setup-node` revision;
2. checks `node --version`, checks that the committed golden's files exist and
   writes `EDGE_E2E_NODE` (`command -v node`), `EDGE_E2E_GOLDEN`
   (`$GITHUB_WORKSPACE/apps/worker/analytics-v2-test/golden`) and
   `POSTGRES_V12_TRANSFER_Q1_DUMP` (that golden's `dump/usage-monitor-db.json`)
   to `$GITHUB_ENV`;
3. installs Node 26.2.0 last, so `node` on PATH, the suite and every other spec
   stay on 26.2.0, and writes `EDGE_E2E_REHEARSAL_NODE` after checking that
   26.2.0 is active. S9's seeding rehearsal needs the newer `node:sqlite`; the
   final-merge receipt records the run that failed 14 of 15 when 22.16.0 was
   first on PATH.

`POSTGRES_V12_TRANSFER_Q1_DUMP` goes beyond the three items in the brief. The
full suite reported `SILENTLY_SKIPPED` for the transfer spec's Q-1 dump case
without it, which fails the job (see the first run below). The spec names
`dump/usage-monitor-db.json` of the Q-1 golden, which is committed.

### Workflow policy

Adding a second Node version made the toolchain a reviewed input, so the
policy refuses a range, alias, expression, partial version, v-prefixed spelling
or any version outside the allowlist, and refuses 22.16.0 in any workflow but
`hosted-backend.yml`. The review-fix commit closes the step's other inputs the
same way: only `node-version`, `check-latest`, `package-manager-cache` and
`architecture` (`x64` or `arm64`, the two values the 23 checked-in uses take)
pass, so a download-source, registry, token or cache input such as `mirror`,
`mirror-token`, `token`, `registry-url`, `always-auth`, `scope`, `cache` or
`cache-dependency-path` is refused in every workflow, not only the hosted one.
The `package-manager-cache` input is allowed by key only; its value is not
pinned (every checked-in use is `false`). All 21 checked-in workflow and action
files pass. Nothing about actions, permissions, runners, checkout persistence or
`pull_request_target` changed.

## Review fixes

A review of `4ef50dd5` found its wiring correct (every brief item met, the diff
inside the stream's ownership, no owner decision contradicted, no permission,
pin, trigger or release-trust rule weakened) and raised three corrections. Each
was checked against the code before it was accepted:

1. **Full-suite failures, miscounted and misattributed.** This receipt's first
   version called both of the full run's failures "not workflow wiring". That
   was wrong for one of them. The Q-1 dump case reported `SILENTLY_SKIPPED`
   because `POSTGRES_V12_TRANSFER_Q1_DUMP` was unset in that run, which is
   workflow wiring, and `cf5a22db` sets it (the "Name the image runtime and the
   committed golden inputs" step). The spec alone passes 6 of 6, 0 skipped, with
   it set. The correct account is **one known red outside the workflow**,
   `postgres-test/typed-v12-normalized.spec.mjs` in the HOST pass
   (`TELEMETRY_REQUIRED`), and **one case this branch addresses**, proven by the
   spec alone, with no second full-suite run yet. The first report's summary and
   the integrator's checklist note carry the same two-failure wording; they
   should say one red outside the workflow.
2. **The checklist item is wider than this branch.** The cutover checklist's
   C-CI item reads: "Also register W3-CRA's 4 node checks (58 tests), plus
   `postgres:cutover-seal:check` and `gcp:ops:infra:check`, in hosted CI."
   This branch wires the last two (the `cloud-run-check` steps), the Cloud Run
   dependency install, the edge runtime and the policy. It does not register
   W3-CRA's four checks, which are not on `afd865a0`:
   `cloud-run/origin-node-request.check.mjs`,
   `cloud-run/postgres-host-dispatch.check.mjs`,
   `cloud-run/postgres-production-registry.check.mjs` and
   `scripts/gcp-origin-verifier-smoke.check.mjs`, added by
   `claude/gcp-fp-w3-cra` without a `package.json` registration (its receipt
   assigns registration to its phase B step 9). The first receipt never
   mentioned this clause. See the first two items under
   [Not proven, and open](#not-proven-and-open).
3. **A setup-node hardening gap.** The new rule pinned `node-version`,
   `node-version-file` and `check-latest` but let any other download-source
   input through: `mirror: https://mirror.example` in a setup-node step passed
   the checker in every workflow except `hosted-backend.yml`, where the contract
   test's exact comparison of the step's `with:` caught it. Nothing in the
   checked-in workflows uses such an input, so nothing was exposed. Reproduced
   with `mirror`, `token`, `registry-url`, `always-auth`, `cache` and
   `architecture: x86` (all passed with no failure), then fixed with the input
   allowlist described under [Workflow policy](#workflow-policy). The allowlist
   was derived from what the 21 files use: `node-version`, `check-latest`,
   `package-manager-cache` (32 uses, all `false`) and `architecture` (14 `x64`,
   9 `arm64`). All 21 files still pass.

The review's first finding (the wiring itself, with its gate reproductions)
needed no change.

  local suite took 14 min 7 s, and its edge pass alone about 7 min on a shared
