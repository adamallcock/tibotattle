# GCP interim frozen public read (C-IPR)

This is a 2026-10-02 receipt for branch `claude/gcp-fp-c-ipr`, built on
`claude/gcp-fastpath-final` at `afd865a0`. It implements owner decision OD-10
(the frozen export): between the edge switch and GCP's first own publication,
`GET /api/v1/community/daily` serves a frozen copy of Cloudflare's production
response. It records **local, synthetic** evidence only: one macOS arm64
workstation, Node 26.2.0 for repository tooling and the specs, Node 22.16.0
(the image runtime) where noted, vitest 4.1.11, and the local PostgreSQL 17
fan-out cluster on a private Unix socket (port 55433). Nothing was built in
Cloud Build, deployed, migrated, applied or read in any GCP or Cloudflare
project. No `gcloud`, `wrangler` or push ran, and no production request was
made. **No real export has been taken**: every fixture is the Q-1 oracle golden
(production code's own output over a synthetic corpus), widened to a full-year
window, and variants derived from it.

## What it does

Three states, decided inside the same `REPEATABLE READ READ ONLY` snapshot that
reads the requested days:

| State | Answer |
|---|---|
| Any row in `analytics_v2_published_daily` (any day, in or out of the requested range) | The ordinary route, exactly as before. The frozen export is never read again |
| No published day, and a frozen export is loaded | The frozen export, validated again on every read, projected onto the requested range and labelled in headers |
| Neither (table empty, or the schema predates the table) | The ordinary route's answer, byte for byte, with no interim header |

A published day is never deleted (the forward-only trigger of 0059 refuses it, and
the spec proves it), so once a publication exists the interim read cannot come
back. A frozen row that fails its digest or the contract, or cannot be read, is
`503 BACKEND_STORAGE_UNAVAILABLE`, never an empty answer. The publication
control, the public-read limiter, parameter validation and the method check run
before any of this, unchanged.

### How the evidence date is conveyed

The JSON body is the closed `community-daily-read-v1.0` body and gains no
field. Every day keeps the revision, `releasedAt` and `aggregateId` Cloudflare
published, so the body itself dates each day. The label is in response
headers, which the thin edge passes through (its drop list names none of them):

| Header | Value |
|---|---|
| `x-tibotattle-interim-read` | `frozen`; present only on the interim answer |
| `x-tibotattle-evidence-date` | `YYYY-MM-DD`, the UTC day the frozen window ends on |
| `x-tibotattle-interim-sha256` | the sha256 of the pinned export |
| `last-modified` | the capture instant as an HTTP date |

`cache-control` follows the captured allowance read state, as production's did:
`public, max-age=300`, or `no-store` when the export was captured with the
allowance unavailable. A cached frozen answer can therefore outlive the first
publication by up to five minutes at an edge or browser; the server never
serves it again.

### Projection

The full window is served byte for byte as the pinned export (the spec asserts
equality with the export text). For any other range the route serves the frozen
days inside it, echoes the requested `from` and `to`, and projects the
allowance breakdowns the way production's projection does: only breakdown days
that are served days, and `allowanceState` is `ready` exactly when one remains.
The cache-retention series and the captured `allowanceReadState` are the frozen
values. Days before the frozen window's start are not available and are
absent, not recomputed.

## The export (the OWN-4 format)

The owner, read-only, saves the exact response body of the production
Worker's `GET /api/v1/community/daily?from=<seal day minus 365 days>&to=<seal
day>` byte for byte (the full 366-day year window the public client asks for),
and records four facts beside it:

| Fact | Meaning |
|---|---|
| sha256 | `shasum -a 256` of the saved file. It is the pin: the loader refuses any other bytes |
| captured at | the UTC instant it was fetched |
| source commit | the production source commit that served it, from `GET /api/health` |
| evidence date | the UTC day the window ends on (the seal day). The capture must be on that day or the next |

**Take it immediately before the Cloudflare fence.** A fenced edge answers
every API read, this one included, with `503 MUTATION_BARRIER_ACTIVE`
(`docs/runbooks/production-edge-modes.md`, fenced mode), so the checklist's
"taken at the seal" is, in practice, "taken just before the fence". The
capture instant records the gap, and contributions the fence admits after the
export are not in the frozen copy, which is what frozen means here. The owner
can run the loader's offline `check` on a trial export at any time before the
seal to learn whether production's contract has moved past what the validator
accepts.

## Contract validation

The validator (`apps/worker/src/analytics-v2/interim-public-read.ts`, no
imports, only erasable syntax so plain Node can load it) is closed at every
level: an unknown or missing key is refused, and the error carries a closed
code and a structural path such as `days[3].payload.*`, never a key or a value.
Every string in the contract is a calendar day, an instant, a digest or a
token of a closed alphabet, so no field can carry content.

- Envelope, day wrapper and day payload: exactly the fields production's
  typed-storage handler emits. The private `capacityByPlanType` and the per-day
  `allowance` block (never current under typed storage; production's typed
  reader returns `allowancePublicationState: null`, read at `f0067d0f`) are not
  in the contract, so an export carrying either is refused.
- Totals, cells and spend: safe non-negative integers, token-shaped ids, and the
  spend rules of the site reader (counts sum to the day's events, coverage
  follows from them, the block agrees with the day's totals). The pricing
  method and registry are shape-checked only, never against this line's
  d43c8f92 registry, because the release changed both.
- Allowance breakdowns: `community-allowance-breakdowns-v1.0`, `v1.1` and
  `v1.2` (the release's `promax` plan), each with its own plan set; an unknown
  version is refused. Basis and normalization names are shape-checked, not
  pinned, because the release renamed them. Days must be ascending, published,
  closed and within the production skew rules.
- Cache retention: the full four-window by ten-band shape, with exact band
  edges and the site reader's arithmetic.
- Window and capture facts: the window ends on the evidence date and is the
  full 366 days, no day is released after the capture, and the allowance is
  `ready` exactly when breakdowns exist.

The validator accepted all four oracle goldens on its first run (the d43c8f92
production code's own output, two of them with allowance breakdowns), and the
d43c8f92 site reader accepts the route's served body, in full and for a
sub-range.

## Storage

`apps/worker/postgres/staged-migrations/primary/0065_interim_public_read.sql`
creates `community_daily_frozen_export`: one row (`id = 1`) holding the export
text, its sha256, the capture instant, the source commit, the evidence date and
the load time. The database enforces what it can: the digest is recomputed over
the stored text on insert (`sha256(convert_to(payload_text, 'UTF8'))`), the
commit is 40 hex, the evidence date is the capture day or the day before, and
the text is a JSON object with the contract's `schemaVersion`. An update or a
delete raises (`P1005`), as for the other forward-only tables.

The number 0065 is a placeholder (the staged harness needs four digits); the
integrator assigns the next free primary number after the append-only residue.
The migration is purely additive: the spec asserts OPS-10's classifier reports
no contract operation for it, so it needs no `CONTRACT_MIGRATIONS` entry.

## The loader

`apps/worker/scripts/gcp-interim-public-read-load.mjs`:

- `check` is offline. It reads the file (a regular, non-symlink file within 8
  MiB), enforces the pin on the exact bytes before parsing anything, and
  validates the contract. It writes nothing and opens no connection.
- `load` runs the check, then one transaction: both tables exist, no day is
  published, the row is inserted once (`ON CONFLICT DO NOTHING`), and it is read
  back through the route's own verification and must equal what was prepared.
  Loading the identical export again changes nothing (`already-loaded`); a
  different export or different facts are refused and name only the stored
  digest. Any failure rolls back.
- The CLI reaches only a local PostgreSQL (a private socket directory or a
  loopback host). The production load is the PT-8-lite orchestrator calling
  `loadInterimPublicReadInTransaction` inside its target handle's primary
  transaction, or `loadInterimPublicRead` on a primary pool.
- Output is one content-free JSON receipt line (digest, facts, counts and days),
  or one closed-code error line on stderr; exit 0, 2 for a usage refusal, 1
  otherwise.

The PostgreSQL 17 spec covers, per state:

- **Neither:** a schema with an empty frozen table and a schema without the
  table answer byte for byte the same, with the same cache series and the same
  `Cache-Control`, for the full window, a sub-range and a one-day range, and
  neither carries an interim header.
- **A frozen export, nothing published:** the full window is the pinned export
  byte for byte, with the four headers and no body label; sub-ranges, a window
  that extends past the frozen one and a one-day range serve the overlap and
  echo the request; an export captured with the allowance unavailable is
  `no-store`; the publication control, the limiter (called once, before the
  parameters), the parameter errors and the method check behave as before; the
  d43c8f92 site reader accepts the answer; the runtime role, granted as OPS-10
  grants it, serves the export and cannot rewrite it.
- **A publication exists:** one published day, outside the requested range,
  ends the interim read for the full window and for ranges holding no
  published day, and a published day cannot be deleted. A load after a
  publication is refused, and nothing is written.
- **Tampering:** nine corruptions made as the schema owner with the table's
  CHECKs and trigger bypassed (a changed byte, a different digest, a
  self-consistent row that breaks the contract, a wrong window, a row that is
  not an export, text that is not JSON, a wrong evidence date, a capture before
  the days, a bad commit) are each `503 BACKEND_STORAGE_UNAVAILABLE` for the
  full window and a sub-range, with the production envelope, `no-store`, no
  interim header and no frozen content, and each is served again once restored.
  An unreadable frozen row is 503; a schema that predates the table is the
  ordinary empty answer.
- **Loader:** it writes once, repeats as `already-loaded`, refuses another
  export, another capture instant or another commit and names only the stored
  digest, converges two concurrent identical loads on one row, refuses a
  missing table, rolls back a failed read-back, and loads inside a caller's
  transaction (a caller rollback leaves nothing).
- **Migration:** every constraint refuses what it should, the row is immutable
  and its function pins `search_path`.

Two mutations of the source confirmed that the specs have teeth: ignoring the
publication check failed the "never served again" case, and skipping the digest
check in the row verification failed the tamper case. The cluster holds no
schema or role with this stream's prefix, `c_ipr_`, after the runs.

## Not covered

- **No real export exists.** The validator is closed against shapes read from
  source (`d43c8f92` for the goldens, `f0067d0f` for the release's breakdowns
  and pricing). Production's real response at the seal could carry a contract
  this validator refuses, which would stop the load before the switch, not
  after. The mitigation is the offline `check` on a trial export in advance.
- The allowance semantics assume production serves typed storage at the seal,
  as the source read shows; a JSON-mode export would carry per-day allowance
  blocks and be refused.
- No PT-8-lite exists yet, so the production composition (the handle's
  transaction, the go/no-go gate on the receipt) is described, not built or
  exercised. `loadInterimPublicReadInTransaction` is tested inside a
  caller-owned transaction on PostgreSQL 17 only.
- Not run in Cloud Run, on Cloud SQL, or through the thin edge: the headers'
  passage through the edge is read from its drop list (`DROPPED_RESPONSE_HEADERS`
  in `edge-origin-contract.ts`) and not tested end to end; the edge e2e spec
  needs workerd and Node 22.16.0 and was not run.
- Per-request cost was measured only locally: about 3 ms for verify, projection
  and serialization of a synthetic 366-day, 732 KB export on Node 26.2.0 and
  Node 22.16.0, and not under load or on Cloud Run. The route re-reads and
  re-verifies the whole row on every request on purpose (fail closed), and the
  edge's five-minute cache is what bounds the rate.
- Not run: the other PostgreSQL specs of `postgres:domain:check`, the Worker's
  workerd suite, `npm run product:worker:check`, the R7 receipts (nothing here
  touches an R7 workload source) and the rest of `npm run check`.
- Requests for days before the frozen window's start (the seal day minus 365
  days) get no days for them. The public client never asks, because its window
  ends today and starts a year before.

## Integration notes

**What PT-8-lite must do at the seal (export, then load).**

1. **Export, read-only, immediately before the fence.** The owner saves the
   exact body of `GET /api/v1/community/daily?from=<seal day minus 365 days>&to=<seal day>`
   on the production Worker, byte for byte. The fenced edge refuses this read
   (503), so it cannot be taken after the fence. The owner records the file's
   sha256 (`shasum -a 256`), the UTC capture instant, the production source
   commit from `GET /api/health`, and the evidence date (the seal day, UTC; the
   capture must be on that day or the next).
2. **Check offline, as soon as it is saved:**
   `node apps/worker/scripts/gcp-interim-public-read-load.mjs check --export <file> --sha256 <hex> --captured-at <iso> --source-commit <40-hex> --evidence-date <day>`.
   A refusal here, with its closed code and structural path, is the early
   warning that the real contract moved. The owner can also run it on a trial
   export well before the seal.
3. **Record the four facts and the sha256 in the seal receipt** (OWN-4). The
   sha256 is the pin: the loader takes it from the record, never recomputes it
   to match.
4. **Load after the import verifies and before the edge switch.** PT-1's
   `beginRun` requires every primary table empty, so the load is strictly after
   the import stages. Call `checkInterimPublicRead({ exportBytes, sha256,
   capturedAt, sourceCommit, evidenceDate })` and pass its `prepared` to
   `loadInterimPublicReadInTransaction({ client, schema, prepared })` inside
   `withTransferTransaction(handle, "primary", ...)`, or to
   `loadInterimPublicRead({ pool, schema, prepared })` on a primary pool. Make
   the receipt's `state` (`loaded` or `already-loaded`) a go/no-go gate before
   the verifier smoke and the switch, and carry its `payloadSha256` into the
   PT-8-lite receipt. A load after any publication, a missing table and a
   different stored export are refusals, never silent.
5. **The verifier smoke** (checklist step 5) should read
   `/api/v1/community/daily` and expect `x-tibotattle-interim-read: frozen`,
   `x-tibotattle-evidence-date` equal to the recorded evidence date and
   `x-tibotattle-interim-sha256` equal to the pin. After the first GCP
   publication (step 8) the header must be absent: that is the acceptance check
   that the interim read has ended.
