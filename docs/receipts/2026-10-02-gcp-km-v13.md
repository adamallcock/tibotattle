## What landed

### Wrapper (`apps/worker/src/analytics-v2/public-allowance-breakdowns-v13.ts`)

The module has no imports and uses only erasable TypeScript.

- **`wrapPublicAllowanceBreakdownsV13`** accepts only the vendored projection's
  exact v1.1 envelope, with its keys in order. Anything else is refused, so a
  changed projection can never be relabelled. It makes exactly two changes:
  - it relabels `schemaVersion` in place;
  - it appends `modelConfig` as the last member.

  It never recomputes, reorders or filters a value.
- **`reducePublicAllowanceBreakdownsV13`** is the inverse. It accepts only the
  v1.1 envelope plus a trailing structurally valid `modelConfig`.
- **`buildPublicModelMetadata`** builds the block from a manifest.
  - **Roster.** The block names the manifest's models whose provider is
    `openai_codex`, whose allowanceTrack is `primary` and that are not hidden,
    in manifest order.
  - **Id and label** are the manifest's, unchanged.
  - **Bounds.** It enforces the tolerant reader's grammars and bounds: at most
    128 entries, unique ids and unique orders. The id grammar is the
    intersection with `catalog-token-guard-v1`.
  - **Refusal.** A manifest it cannot publish is refused whole, never
    published in part.
- **Family and order.** Manifest version 1 carries no presentation fields, so
  they come from a frozen table keyed by manifest version
  (`PUBLIC_MODEL_PRESENTATION_BY_MANIFEST_VERSION`).
  - Version 1 reproduces the d43c8f92 page's `model-visuals.js`. Its seven
    pinned models take orders 0 to 6 with their themes. Every other model
    takes family `generic` and order 7 plus its roster index, which is the
    page's own fallback.
  - Any other manifest version fails closed with
    `PUBLIC_MODEL_METADATA_MANIFEST_UNSUPPORTED`.
- **Size.** Version 1 gives 41 entries. The sha256 of `JSON.stringify(block)`
  is `c294cbf5…`, pinned in the spec.

### Route (`community-daily-route.ts`)

### Unknown names

- Only manifest roster models get a metadata entry.
- A tuple whose id the manifest does not name gets no entry, so the tolerant
  reader skips it and states the gap. The wrapper does not remove the tuple,
  because removing it would change oracle bytes.
- At d43c8f92 no such tuple can occur, because the vendored preview validation
  admits only reviewed catalog ids. The kernel-parity spec and the new spec
  both exercise that refusal.

### Parity compare and rehearsal

- **New family.** `scripts/analytics-v2-parity-compare.mjs` (report v4) adds
  the expected family `breakdowns-v13-metadata` and a `breakdownsV13` summary.
- **What is accepted.** A served v1.3 block is accepted only when both hold:
  - it is exactly the v1.1 envelope relabelled, with a trailing
    `modelConfig`;
  - that block equals the committed declared block, including each entry's
    key order.
- **The rest is still compared.** The block's v1.1 reduction is then compared
  with the oracle like any other block. Anything else, such as a changed
  label, a missing or extra entry, swapped orders, a `tone` key, a moved
  `modelConfig` or a `catalogManifestVersion`, is an unexpected
  `allowance-breakdowns` difference.
- **The declared block is a JSON file.** It is
  `apps/worker/analytics-v2-test/fixtures/breakdowns-v13-declared-model-metadata.json`.
  - The compare reads it rather than importing the TypeScript module, because
    the rehearsal's origin child and the edge end-to-end suite run the
    compare under Node 22.16, which does not strip types. The first Q-1 run
    failed `REHEARSAL_ORIGIN_START_FAILED` for exactly that reason, before
    this change.
  - The analytics-v2 spec and the PostgreSQL route spec hold the file
    byte-equal to the builder's output over `catalog/manifest-0001.json`.
- **Per-date compare.** `per-date-compare.mjs` (report v2) compares the
  reduced block with the oracle's per-date v1.1 expectation. It fails when
  the declared shape or block is wrong.
- **Rehearsal.** `gcp-fastpath-rehearsal.mjs` adds the gate
  `breakdownsV13Declared` whenever the read serves a breakdown.

## Not done, and why

- **The website reader change.** It belongs to `claude/gcp-fp-w-web`. It is
  recorded precisely in this stream's integration notes.
- **Design fields the reader would refuse.**
  - The design proposed `catalogManifestVersion` and `tone`. The reader's
    envelope and entry checks are exact, so either one would make it reject
    the whole block. Neither is emitted.
  - Manifest version 1 is implied by the v1.3 contract at cutover.
  - Adding either field later needs a reader change first, then a new
    contract version.
- **Presentation in the manifest.** Manifest v1 has no family, order or
  display section. The frozen per-version table is the stand-in. A later
  manifest that binds metadata (KM-4) must add a table entry or carry
  presentation itself; absence fails closed.
- **Edge end-to-end (`npm run edge:e2e`)** was not rerun. Its S9 stage
  compares through the same compare and rehearsal code, which both rehearsals
  above exercise.
