# GCP D-PT4X v0.x history, pending registrations, admin history, exclusions and the E-PT4 guard

This is a 2026-10-02 receipt for stream D-PT4X on branch `claude/gcp-fp-d-pt4x`,
built on `fce3572e` (`claude/gcp-fastpath-final`). It records **local,
synthetic** evidence only: one macOS arm64 workstation, Node 26.2.0 for the
importers, the specs and the operator checks, and the local PostgreSQL 17
fan-out cluster (port 55433) over its private Unix socket. Nothing was
deployed, migrated or read in any GCP or Cloudflare project, no `gcloud`,
`wrangler` or push ran, no production data was read and no secret value was
handled. Nothing is merged.

Revised the same day after a review of `f3dcc1fd`. Both findings were verified
and fixed, in the spec only (no product code changed). First, once `0902` is
promoted, the stock migration run would give the `bare` target the hold table,
and its P13 case would fail. Second, several closed contracts had no negative
test. The integrator note, the gates and the coverage list below reflect the
revision.

Scope (round-5 import additions plus the E-PT4 guard): N-V0X, N-ADMINHIST,
N-EXCL (table and import; its use in analytics is K-CORE-A's) and the E-PT4
reconciliation guard that PT-8-lite preflight P13 checks.

All three runners follow the PT-1 production stage pattern of PT-3 (the
PT-8-lite design's runner contract): they refuse before any write unless
`identity-authority` is complete; every check that can refuse (the column map
closure in both directions, the canonical form of every sealed value, the
reviewed trigger policy and the target layout) runs before the first write;
pages are at most 256 rows and 4 MiB, each one transaction with a pending
checkpoint (count and prefix chain, never a key); a killed run resumes at its
last page and a finished stage replays without writing; a table completes only
when its target digest equals the expected digest; receipts hold names, counts
and digests only. They export `TRIGGER_POLICY` and empty
`PRODUCTION_STAGING_RELATIONS` and `PRODUCTION_RETAINED_RELATIONS` (nothing is
created in `tibotattle_transfer`).

### Value codec

The text, integer, instant and day codecs are the reviewed T-1/PT-3 ones
(additive exports of `postgres-fastpath-identity-copy.mjs`, unchanged). The
v0.x tables add three D1 shapes:

- `real` (REAL to double precision): the shortest round-trip decimal on both
  sides.
- `decimal` (TEXT to numeric): only `0|[1-9][0-9]*` with an optional fraction,
  the grammar numeric echoes byte for byte. Anything else (an exponent, a sign,
  a leading dot) refuses `CUTOVER_SOURCE_VALUE_INVALID`.
- `json` (TEXT to jsonb): compared after parsing, with keys sorted, because
  jsonb normalizes key order and whitespace.

Key instants (the admission window start and the snapshot `captured_at`) must
already be canonical millisecond ISO, because sealed order is text order.

### Trigger policy

Suppressed on `telemetry_contributions`: the 0061 weekly admission enforce and
record triggers (the sealed windows are imported verbatim, so firing would
double count) and the 0014 `telemetry_retained_source_revision`. Suppressed on
`telemetry_records`: `telemetry_retained_record_source_revision`. Both
source-revision triggers would bump `input_versions` and
`input_source_digests` and emit journal rows; the sealed journal is imported
verbatim by ingestion-journal and analytics is recomputed. Fired:
`telemetry_contributions_active_participant` (PT-3 imported every participant
`active`) and the two new guards (UPDATE and DELETE only). The policy sha256 is
pinned in the check file.

## Contracts for the other streams

- **E-PT8 (PT-8-lite).** Call `runLegacyContributionsProduction` at stage 2,
  `runPendingRegistrationsProduction` at stage 11 (it asserts
  `identity-authority`, `legacy-contributions`, `telemetry-v1-v11` and
  `telemetry-v12` complete) and `runOperationalHistoryProduction` inside R3
  post-import, before coverage finalize. The last writes its table receipts
  under `post-import` and no stage receipt: fold its `receiptSha256` into the
  post-import digest. Preflight P13 is `checkPendingObjectTransferGuard(handle,
  {ownerFlags})`. The pending stage already enforces R3's two pending
  invariants (PostgreSQL `pending_quarantine_objects` is 0, and
  `pending_objects` equals the sealed registration set with no duplicate),
  so R3 may cite its receipt. The design's section 3 dispositions change:
  `admin_metric_snapshots` and `admin_metrics_history_cache` become
  `mapped:admin-metrics-history` (were `runtime-reset`), and
  `community_aggregate_exclusions` becomes `imported:community-aggregate-exclusions`
  (was `must-be-empty`). `LEGACY_TRANSFER_DISPOSITIONS` exports all ten.
- **D-PT5A.** A telemetry stage may write a chunk-owned `pending_objects` row
  before `pending-registrations` runs, mapped exactly as above (object key, contribution id,
  kind, `registered_at`, state and lease verbatim). The pending stage then
  verifies it field by field and does not insert it again; a differing row
  refuses `CUTOVER_PENDING_OBJECT_CONFLICT`. *Amended at the D-PT5A merge:*
  a chunk-owned registration (its contribution id is a sealed chunk's id and
  its key that chunk's key) is not kind-verbatim. Both stages map it to the
  family's PostgreSQL kind (`telemetry_v1`, `telemetry_v11` or
  `telemetry_v12`, the reviewed T-0 mapping) through D-PT5A's
  `CHUNK_REGISTRATION_FAMILIES`. Under the verbatim rule above, every
  chunk-owned registration in a seal refused `CUTOVER_PENDING_OBJECT_CONFLICT`.
  A chunk-owned registration under another key refuses
  `CUTOVER_SOURCE_VALUE_INVALID`. D-PT5A must NOT write a
  `transfer_table_receipts` row for `pending_quarantine_objects` (one
  disposition per sealed table; a second one conflicts) and need not write
  holds: the pending stage holds every sealed registration, pre-mapped or not.
  `telemetry_v1_chunk_admission_windows` belongs to `legacy-contributions`
  (PT-8-lite section 3), not to D-PT5A.
- **PT-7.** After copying an object to GCS, or proving it absent from R2, call
  `releasePostgresPendingObjectTransferHolds(pool, {schema, objectKeys,
  releaseReceiptSha256})` (at most 1,000 keys, the sha256 of the
  owner-directory receipt). It is one-way and idempotent and returns counts
  only (`released`, `alreadyReleased`, `unknown`). Until then the reconciler
  leaves the registration alone, so no orphan object is ever untracked. A hold
  is never deleted; the guard trigger refuses any other change.
- **K-CORE-A (exclusion read contract).** Read
  `community_aggregate_exclusions`. An owner is excluded from community
  aggregates (public daily and band) for analysis day D when a row has
  `scope = 'community_weekly'`, `state = 'active'`, `effective_at` before the
  end of D, and `expires_at` NULL or after the start of D: D1's weekly
  predicate, applied per day. Revoked rows are history only. Add the table's
  rows to the evidence digest or the memo key, so a revocation or a new
  exclusion recomputes the affected owner-days. At d43c8f92 only the legacy
  weekly builder read the table, so applying it on GCP is a declared
  difference from the oracle whenever production holds an active row. The Q-1
  corpus holds none, so golden parity is unaffected.
- **E-ADMIN.** The mapped snapshots are keyed by the sealed canonical source id.
  A GCP producer and reader must use that id (the imported
  `storage_source_state.source_id`). The operational runner refuses
  `CUTOVER_SOURCE_IDENTITY_MISMATCH` if the target already holds a different one.
- **E-PURGE1.** `community_aggregate_exclusions` has a `participant_id` and no
  foreign key, and refuses DELETE (D1 parity: the audit row survives the
  participant). The offline purge must decide whether it deletes an erased
  owner's exclusion rows (and disable the guard to do so), or keeps them as D1 does.
- **Integrator.** `0901` and `0902` are placeholder numbers (the brief's NNNN),
  chosen outside any sibling's range so staged versions never collide. Assign
  the next free primary numbers at promotion. Both are purely additive, with no
  `CONTRACT_MIGRATIONS` entry and no grants. Promotion is not edit-free: as in
  `fce3572e`, rewrite each file's NUMBER paragraph, move every primary count
  and tail pin to the new tail, and regenerate `src/postgres-runtime-schema.ts`
  with its generator. This stream's spec and check need no edit. They find both
  files by name suffix. The spec applies both migrations to every target by the
  same path and then drops the hold table and its guard function on `bare`, so
  `bare` lacks the guard whether the migration was staged or promoted. A local
  rehearsal moved the files to primary `0066` and `0067` (the next free numbers
  on `fce3572e`) and then restored them. In that state the spec passed 10/10
  and the check 6/6. The previous spec (`f3dcc1fd`) failed in the same state,
  because P13 returned `transfer-holds-v1` on `bare`. That is why `bare` now
  drops the table itself.

## Decisions taken in the stream (for review)

- **Orphan exclusions are not imported.** A D1 exclusion row whose participant
  is not a sealed participant (D1 keeps the audit row after an erasure) can
  never apply on GCP. The importer counts it (`participantAbsent`) and
  records the full sealed digest in the table receipt, but does not copy it, so no erased participant's id
  enters PostgreSQL. The table receipt therefore has a source count above its
  target count.
- **The cache adds snapshots, never replaces them.** A cached snapshot whose
  `captured_at` is already a sealed row is skipped (the raw row wins). An
  invalid or absent cache contributes nothing and is reported as
  `invalid` or `absent`, not refused.
- **Strict values fail closed.** A non-canonical decimal or JSON value, or a
  non-canonical key instant, refuses the stage before any write. That would
  happen inside the outage, so a pre-fence rehearsal on a trial seal should
  run the three runners against a disposable target (or an owner read should
  count such values) before the window.

The spec covers the following:

- **Refusals before any write.** Every runner refuses without
  `identity-authority`.
- **N-V0X.** A kill at `telemetry_records` page 3 resumes, and the result is
  byte-identical to a clean import with other page sizes: equal receipts, and
  equal per-table text digests across 600 records, 3 contributions (one
  `deleting`) and occurrence links.
- **Verbatim values.** Decimals, reals, `2^40` integers, JSON and canonicalized
  instants survive the import.
- **No double count.** The admission windows are not double counted.
- **Suppressed triggers.** No `input_versions` bump, digest or journal row is
  written, and every trigger is re-enabled.
- **Sequence.** The `telemetry_records` sequence passes the sealed counter.
- **Replays.** Replays leave every row version (xmin) unchanged.
- **Pending registrations.** A pre-mapped row is verified, not duplicated. A
  kill and resume produces 5 holds bound to the seal, and a clean twin has an
  equal receipt.
- **Admin snapshots and exclusions.** 3 sealed snapshots plus 1 cache-only
  snapshot are mapped. 1 exclusion is imported and 1 orphan is skipped. The
  no-delete guard holds.
- **Reconciler.** Held rows are never selected and the object store is never
  asked about them, while an unheld orphan still reconciles. After a release
  the released rows reconcile normally. The hold guard refuses delete,
  re-hold and seal edits.
- **PT-7 release is closed.** No keys, 1,001 keys, a duplicate key, an
  upper-case, short or missing digest, and a non-array key list each refuse
  `invalid` and leave every hold row version unchanged, with a still-held key
  in the call. Exactly 1,000 keys are accepted.
- **Claim-time re-check.** A pool seam writes a hold after the due-row scan and
  before the claim. The claim defers, the row stays `registered` with no
  lease, and the object store is not asked. The next pass does not select the
  row. After a release it reconciles.
- **Altered guard.** A disabled, replica-only or renamed guard trigger, or one
  that runs another function, makes P13 and the stage refuse
  `CUTOVER_PENDING_OBJECT_GUARD_MISSING` with or without the owner flag. P13
  passes again once the guard is restored.
- **No hold table.** P13 and the stage refuse unless the owner flag is
  present. A row in PostgreSQL's `pending_quarantine_objects` refuses
  `CUTOVER_PENDING_QUARANTINE_TARGET_NOT_EMPTY` before any write (no
  `pending_objects` row and no stage receipt), and again in the completion
  proof when one lands after the pages commit. A differing pre-mapped row
  refuses inside the page transaction. An extra row fails the completion
  proof, and the stage resumes once that row is removed.
- **Operational history refusals.** An absent exclusions table, a renamed
  column and a retyped column each refuse `CUTOVER_TARGET_COLUMN_MISMATCH`. A
  different `storage_source_state.source_id` already in the target refuses
  `CUTOVER_SOURCE_IDENTITY_MISMATCH`. Each refusal writes nothing: no rows,
  table receipts or checkpoints. With the sealed id in place, the runner
  produces the same receipt as `main`.

## Open items

  sets `TELEMETRY_STORAGE_MODE` to `json` with no analytics D1 binding, so the
  live capture path is the ingestion `admin_metric_snapshots` this stream
  maps. If production in fact runs typed storage analytics, its recent
  snapshots live in the analytics D1's `analytics_admin_metric_snapshots`,
  which the fast path never seals, and the charts would gap from the switch to
  typed storage. Confirm with an owner read-only count and
  `max(captured_at)` of the ingestion table before the window.
- **`input_source_digests`** are not computed for the imported v0.x rows (the
  source-revision triggers are suppressed). No product reader uses the table
  on this line. A future reader would need a backfill.

  admin snapshot producer (E-ADMIN), PT-7 itself, and PT-8-lite's call sites
