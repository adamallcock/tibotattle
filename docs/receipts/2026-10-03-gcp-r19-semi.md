# GCP refresh job semi-space flag (R19 SEMI)

This is a 2026-10-03 receipt for item SEMI of owner decision round 19
("Adopt now"), on branch `claude/gcp-fp-r19-semispace`, built on the fast-path
final line at `b8864974` (kernel 4 registered). It records **local, synthetic**
evidence only: one macOS arm64 workstation shared with other agents, Node.js
22.16.0 for the job, and a private PostgreSQL 17.10 cluster on port 55445
(private socket, created for this item and removed afterwards). Nothing ran in
the cloud. Nothing was deployed, applied or pushed.

The measurement that motivates the flag is d0 in
`design/refresh-profile-slices-2026-10-03.md` in the parity home. On the
full-scale `o05` probe, paired ABBA runs showed 75% fewer scavenges, 62% less GC
time and 6.4% less wall time, with all seven output tables identical. This
receipt does not re-measure that gain.

## What changed

- **The flag.** The inline refresh job runs
  `node --max-old-space-size=<heap> --max-semi-space-size=64 dist/analytics-refresh.mjs --mode=full`.
  - It is in the production job (`cloud-run/analytics-refresh.mjs`
    `ANALYTICS_REFRESH_PRODUCTION_JOB`, which gains `semiSpaceMiB: 64`).
  - It is in OPS-2's render (`scripts/gcp-ops-infra-manifest.mjs`
    `ANALYTICS_REFRESH_TASK_PROFILE.semiSpaceMiB` and `JOB_DEFINITIONS`).
  - It is in the `standard` and `dense` test-deploy profiles
    (`scripts/gcp-fastpath-test-deploy.mjs` `REFRESH_JOB_PROFILES`).
  - It is in the inline local rehearsal
    (`GCP_FASTPATH_REHEARSAL_REFRESH_SEMI_SPACE_MIB`).
  - It is not in `dense-workers`, nor in a rehearsal run with `--workers > 1`.
    A V8 flag reaches every Worker isolate, and the compute Workers' memory
    belongs to K-PAR-MEM (see "Merge with K-PAR-MEM").
  - The committed desired states carry no job arguments, so they are
    unchanged. The Dockerfile's `CMD` is the origin server's and is unchanged.
- **The output budget (review correction, 2026-10-03).** The partition retains
  the 48 MiB young-generation allowance counted before R19 and excludes only
  growth above it. The old space was not raised.
  - `analyticsRefreshResources` reads `execArgv` and `NODE_OPTIONS` (last old-space
    declaration wins). The partition is `heap_size_limit - max(0,
    youngGenerationBytes - 48 MiB)`; the startup guard checks that partition.
  - Without a readable old-space declaration, or one above the heap limit,
    the helper returns 0 and the whole limit is partitioned, as before R19.
  - `memory.youngGenerationMiB` reports the inferred young generation;
    `heapLimitMiB` continues to report the complete V8 heap limit.
  - An injected heap limit is paired with injected flags or none, never the
    test process's flags.
- **Task memory.** `ANALYTICS_REFRESH_TASK_MEMORY_CHECK` gains
  `youngGenerationSemiSpaces: 3`. The manifest, spec and test-deploy checks
  hold the old space, the young generation and any Worker heaps within the
  task memory less the 1 GiB native reserve. That is 12,288 + 192 MiB inside
  15,360 MiB for the production profile.

## Why exclude growth, not raise

The owner asked for correction of young-generation growth. The first SEMI
commit excluded all young generation; review found that this tightened every
profile by 48 MiB, including `dense-workers`. This follow-up preserves that
historical allowance. It is a budget compatibility allowance, not a claim
that young generation provides retained-output capacity.

On Node.js 22.16.0 the 12,288 MiB old-space flag produces 12,336 MiB total
without the semi-space flag and 12,480 MiB with it (verified again locally).
Only the additional 144 MiB is subtracted:

| Flags | Heap limit | Uncorrected output budget | Corrected output budget |
|---|---:|---:|---:|
| `--max-old-space-size=12288` | 12,336 MiB | 351 MiB | 351 MiB |
| `+ --max-semi-space-size=64` | 12,480 MiB | 495 MiB | 351 MiB |

The exact starting budget is 368,508,928 bytes (351.4375 MiB).
The 64 MiB minimum is unchanged. With a declared old space and young
generation at least 48 MiB, the startup guard accepts old space plus 48 MiB;
smaller young generations contribute only their actual size.

`dense-workers` reserves no owner budget in its main heap: owners live in
compute isolates. At its real `--max-old-space-size=3072` flag on Node 22,
the main partition remains 3,120 MiB and its starting output budget remains
1,887 MiB after the runtime and read reserves. Worker heap sizing still uses
the complete main `heap_size_limit` for task footprint; this correction does
not change that footprint contract.

## Merge with K-PAR-MEM (expected conflicts)

K-PAR-MEM (`claude/gcp-fp-kpar-mem`, in flight) moves production to four
compute Workers with no heap flag. It refuses any V8 heap flag with
`--workers > 1`, and its pattern (`ANALYTICS_V2_REFRESH_WORKER_HEAP_FLAG_FORBIDDEN`)
includes `--max-semi-space-size`. It raises the task timeout to 86,400 s.

Expected textual conflicts:

- `cloud-run/analytics-refresh.mjs`:
  - `ANALYTICS_REFRESH_PRODUCTION_JOB`: `heapMiB`, `workers`, `args`, the
    timeout, and this item's `semiSpaceMiB`.
  - The `analyticsRefreshResources` signature: both add an `execArgv`
    option.
  - The `runAnalyticsRefresh` call site: both pass `execArgv`.
  - The help text.
- `scripts/gcp-ops-infra-manifest.mjs`: `ANALYTICS_REFRESH_TASK_PROFILE` and
  the `analytics-refresh` job args.
- `scripts/gcp-fastpath-test-deploy.mjs`: `REFRESH_JOB_PROFILES` and the
  `refreshJobCommand` args.
- `scripts/gcp-fastpath-rehearsal.mjs`: the `runRefresh` args.
- The checks that pin the args: `gcp-ops-infra-manifest.check.mjs`,
  `gcp-infra.check.mjs`, `gcp-ops-infra-operations.check.mjs`,
  `gcp-fastpath-test-deploy.check.mjs` and `analytics-v2-refresh.spec.mjs`.

- `apps/worker/cloud-run/infra/monitoring.md`: reconcile the inline fallback
  and Workers profile descriptions; textual merges can otherwise leave
  contradictory claims about production flags.

Semantic reconciliation for the merger:

- If production becomes the Workers profile, the flag cannot stay on the
  production job's command line: K-PAR-MEM would refuse the run.
  - Keep `semiSpaceMiB` on the inline `dense` fallback.
  - For the Workers, the per-isolate equivalent is
    `resourceLimits.maxYoungGenerationSizeMb` in `analytics-refresh-pool.mjs`
    (192 for a 64 MiB semi-space). That is a K-PAR-MEM decision, and d0
    measured only the inline job.
  - Reconcile the actual main flags in the merged K-PAR-MEM profile. If the
    main heap has no declared old space, this
    item's exclusion reads 0 there. The output budget would count the
    default young generation, as before. That is harmless with Workers,
    where the main heap holds no owner.
- K-PAR-MEM's pool sizing uses `heap_size_limit` as the main heap's footprint
  (task memory less native reserve less `heapLimitBytes`). That is correct
  for footprint and should stay `heap_size_limit`. This item changes only the
  output-budget partition, so the two do not conflict in meaning.
