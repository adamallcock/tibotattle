# GCP round 19 retired-route answers (R19-ROUTES)

This is a 2026-10-03 receipt for stream R19-ROUTES on branch
`claude/gcp-fp-r19-routes`, cut from the fast-path final line at `b8864974`.
It records **local, synthetic** evidence only: one macOS arm64 workstation
shared with other agents, Node 26.2.0, and a private PostgreSQL 17 cluster on
ports 55481 (domain) and 55482 (E12), initialized with collation `C` for
this recovery. Nothing was pushed or deployed, no gcloud command ran, and
no provider was contacted. The edge harness used credential-free local
Wrangler dry runs to build its three modes. The parity basis is
production's source `d43c8f92`, read with `git show`.

## What the owner decided (round 19, 2026-10-03)

1. The retired accountless performance authorization must reproduce
   production's exact answer sequence, not round 12's one fixed 403.
2. Retired v0.x uploads must answer `d43c8f92`'s definite `403
   TELEMETRY_TRANSPORT_BLOCKED`, not the uniform `503
   POSTGRES_ROUTE_NOT_PORTED`. The 5xx alert's never-exclude rule stays
   strict.
3. STATUS-REUSE (the 1 s reuse of `/api/ready` and `/api/health`) is an
   accepted documented difference beside OD-CR-6 (ii), (iii) and (v).
   `GOOGLE_OIDC_CLIENT_ID` stays (no change).

## What it builds

### 1. The performance authorization's sequence

Read from `d43c8f92` `apps/worker/src/index.ts:801-835`
(`handleAccountlessTelemetryPerformanceAuthorization`), the order is: the
method (405), a session cookie (401 `AUTH_INVALID`), the ownership mode, the
admission bindings, the upload-registration control (503s), the
accountless-ownership limiter (429 `ATTEMPT_LIMIT_REACHED`, or 503
`ADMISSION_RATE_LIMIT_UNAVAILABLE`, each with `retry-after: 60`), the device
bearer (401 `DEVICE_AUTH_INVALID`), the storage-mode read, the body (415,
400 `BODY_INVALID`, 413, 408), and the grant. While production's
performance runtime is `staged` (ingestion-isolation migration 0009), the
grant answers `403 TELEMETRY_TRANSPORT_BLOCKED`.

- `cloud-run/postgres-test-dispatch.mjs`
  `createPostgresRetiredPerformanceAuthorizationPreamble`: the origin's
  preamble. Each step uses the origin's existing port of the same check, the
  same ones the sibling v1.2 authorization uses. The device bearer goes
  through `authenticatePostgresAccountlessForV12Grant` (the Worker's generic
  `authenticateDevice`, then accountless only). The preamble answers the
  first refusal in the Worker envelope under the root's request id, or
  `null` when every check passes. It never grants.
- `cloud-run/postgres-production-registry.mjs`: the retired-definite route
  now takes its preamble in the handler map (required:
  `PRODUCTION_ROUTE_HANDLER_MISSING` without it). It still can never be
  ported (`PRODUCTION_ROUTE_PORT_RETIRED`). `RETIRED_ROUTE_DEFINITE_ANSWERS`
  keeps the terminal 403. `RETIRED_DEFINITE_PREAMBLE_STEPS` pins the
  sequence as data.
- `cloud-run/postgres-host-dispatch.mjs`: the request handler runs the
  preamble inside the request-context store. A refusal is logged as a
  family's and returned no-store. Otherwise the registry's terminal answer
  is thrown. A preamble answer that is not an error is a 500, never a grant.
- `cloud-run/postgres-production-host.mjs` `composeOriginFamilies` builds
  the preamble for every origin mode, and `createOriginRouteRegistry` hands
  it to the registry.

**The 429 is reachable.** The edge evaluates `accountless_ownership`
admission for this route (`src/edge-admission-policy.ts`) and forwards only
the outcome. The origin's replay bindings
(`postgres-edge-admission-limiters.mjs`) answer the Worker helper at its own
call point. Proved through the real EP-6 boundary (unit check) and over HTTP
against PostgreSQL 17 (production-host spec).

**What differs, and why** (recorded in the round 19 amendment of
`docs/decisions/2026-09-04-accountless-sharing-policy.md`):

- `requireTelemetryPerformanceStorageMode` is not reproduced. It reads a D1
  table PostgreSQL does not have, and production's deployed state passes it.
  The origin's storage gate stands in for it, before the ownership mode, as
  on every storage-gated route (OD-CR-6 (iii)).
- The deletion-ledger tombstone read is not reproduced (append-only; no
  ledger). A deleted participant has no active device credential, so the
  bearer step answers the same 401.

### 2. v0.x uploads

`cloud-run/upload-authorization-formats.mjs`: `RETIRED_FORMAT_ANSWER` is now
`{403, TELEMETRY_TRANSPORT_BLOCKED}`. Each retired v0.x format first runs the
same transport write authority as a live format for its own identifier (the
PostgreSQL port of `d43c8f92` `assertTelemetryTransportWriteAllowed`), so
that authority's refusals stand. If the authority would allow, the format
refuses with the 403. In `cloud-run/origin-intake-composition.mjs` the
retired envelopes lose their pre-claim check: as on `d43c8f92`, the upload
is claimed and then refused at the write-authority step, and the claim is
abandoned.

Per version, against `d43c8f92` (proved on a D1 twin running the Worker's
own code):

| Identifier | `d43c8f92` | Origin after R19 |
|---|---|---|
| v0.2, any participant | 401 (no joined row) or 403 (`blocked`) | the same |
| v0.1, accountless or under the floor | 401 or 403 | the same |
| v0.1, social at the rank-1 floor | authorized or admitted | 403 `TELEMETRY_TRANSPORT_BLOCKED` (the retirement) |

The contributions preamble's existing orderings still apply: the
processing control is read after the claim, and the envelope's exact-key
check runs after the write authority. Both are recorded in the amendment.

**The alert stays strict.** `ORIGIN_5XX_NEVER_EXCLUDED_PATHS` is unchanged.
Its comments in `scripts/gcp-ops-monitoring-policies.mjs` now say that v0.x
answers a 4xx, which the 5xx alert never counts, and that the two upload
paths stay unexcludable because live v1 uploads share them. The rendered
alert is byte-identical.
