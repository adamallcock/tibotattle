# GCP W3-SIMP append-only simplification (LEAD-SIMP core)

This is a 2026-10-02 receipt for package W3-SIMP on branch
`claude/gcp-fp-w3-simp`, built on `7c310cac` (the wave-2 integration tip) in
one commit. The branch is **parked**: it must not merge until the owner
decisions in [What blocks the merge](#what-blocks-the-merge) are answered.

It records **local, synthetic** evidence only: one macOS arm64 workstation,
Node 26.2.0 for repository tooling, Node 22.16.0 (the image runtime) for the
Cloud Run host check, the OPS-10 PostgreSQL spec and the edge end-to-end
spec, and the local PostgreSQL 17
fan-out cluster on a private Unix socket (port 55433, which also listens on
loopback TCP). Nothing was built in Cloud Build, deployed, migrated or read in
any GCP or Cloudflare project. No `gcloud`, `wrangler` or push ran, and no
request left the machine. Every participant, owner, role, schema, database,
bucket, contract and digest in the tests is synthetic; the commit and file
digests this receipt names are the repository's own.

## Authority

The accepted record is
[Append-only contributions](../decisions/2026-09-26-append-only-contributions.md)
(D1 no withdrawal, D2 Variant B offline erasure, D4 no separate deletion-ledger
instance, D6 simplify the GCP line). This package implements the LEAD-SIMP
core of the wave-3 design with the critic's gap list applied. Where a step
depends on an open owner decision, the current fail-closed behaviour is kept
or the decision is an injected parameter with no default, marked with its
decision id in the code.

## Primary 0064 append-only residue

The file supersedes, without editing it, 0053's parts (3) erasure fences and
receipts, (4) terminal watermarks, and the erasure-floor half of (6). In one
runner transaction it:

1. refuses (`append_only_residue_retained_rows`, P1005) when any erasure fence,
   erasure receipt, re-enrollment cooldown or readiness-sweep row exists, or
   any terminal watermark is non-zero or carries a legacy floor. Zero
   watermark rows are the old floor's lock placeholders and carry no evidence;
2. replaces `community_daily_authority_fence()` and
   `community_graph_preview_authority_fence()` with bodies that keep the
   authority pin checks (and the daily device-method check) but no floor,
   pinned `SET search_path FROM CURRENT`, and drops
   `community_publication_erasure_floor(text)`;
3. drops the fence, receipt and watermark tables, their guard functions and
   the two terminal-epoch indexes; the AA-0 participant-erasure lease index;
   `identity_reenrollment_cooldowns`; and `postgres_readiness_sweeps`;
4. pins `retention_state.restored_participants_suppressed = 0` and
   `restore_replay_complete` with named CHECKs (a row outside them aborts
   with 23514);
5. under 0056's install lock, refuses a control schema owned by another role
   (`TRANSFER_CONTROL_SCHEMA_FOREIGN`) or a contract registered under the
   dual-role shape (`transfer_target_contract_registered_with_ledger`), then
   drops the contract's three ledger columns if they are still present.

Behaviour change to note: with the floor gone, a daily or preview row pinned
below the delivery cursor's epoch is accepted. That floor existed to fence
withdrawal and erasure, which D1 and D2 remove.

`postgres-test/append-only-residue.spec.mjs` (14 tests) runs every case in its
own database (a template holds the chain below 0064 once), so it never touches
another database's control schema: the fresh-database catalog; the upgrade
from 0063 with a provenance daily row, a JSON-mode daily row, a preview, the
zero watermark and the default retention row, all byte-identical afterwards;
the authority-mismatch and revision-order refusals that remain; the
pin-below-cursor acceptance; a second application schema in the same
database; and ten refusals (fence, non-zero epoch, non-zero sequence, legacy
floor, cooldown, readiness sweep, suppressed participants, replay incomplete,
registered dual-role contract, foreign control-schema owner), each leaving
the history at 63 and every object in place.

## What blocks the merge

1. **OD-1**: the residue file's final name and number. A rename changes the
   file, its `CONTRACT_MIGRATIONS` key and the generated runtime schema.
2. **OD-4**: the maintenance report policy. Until it is set,
   `server.mjs --scheduled` refuses.
3. **OD-6**: the A2 private test tooling. Merged as is, its deploy renders
   settings the jobs now refuse.
4. **OD-2** for any Cloud Run composition that deletes objects (unchanged
   here, but the cleanup and maintenance paths depend on it).
5. **OD-7** before any migrate of `tibotattle_fastpath`, and **OA-4** for the
   frozen ledger migrations and named ledger resources (cloud writes, owner
   only).
6. The dense workstream must take the [post-dense follow-ups](#post-dense-follow-ups):
   its rehearsal and test deploy still create and migrate a ledger schema,
   which the runner now refuses.

OD-3 and OD-5 keep current behaviour and do not block; the SIMP-1 cleanup
order follows the plan-v5 brief and needs no deviation sign-off.

## Deviations from the brief

- `readSchemaReceipt` was not extracted into `src`: the host and the Node
  22 specs import `postgres-test-dispatch.mjs` directly and `src` is
  TypeScript bundled per image. The one-copy extraction the critic asked for
  is left to CR phase B, which owns the readiness and health readers.
- The test health body moved to v2 in every mode, fast-path included. CR B6
  replaces fast-path health later; its consumers here (`synthetic-v12-smoke`,
  the host check, the fast-path and edge-test specs) are updated.
- The residue guard also covers `postgres_readiness_sweeps`, and the OPS-10
  residue gate runs before the expand-compatibility check (job and rollout)
  so a missing residue reports the residue code, not a stale map.
- `verifyProductionMigrationReceipt` now binds the receipt's target kind to
  the scratch-instance pattern; the old tamper test (kind relabelled) no
  longer failed once the scratch manifest carried the residue.
- The synthetic cleanup reuses the discovery rules, so a bridged or
  non-synthetic owner is refused before any write.
- The fast-path schema bound is now the identifier limit (63 bytes); it was
  56 because `<schema>_ledger` had to fit.
- **v1.2 grant race (product fix).** Removing the tombstone round trip made
  the host check's concurrent-grant case fail about half the time: two first
  grants for one owner raced the `participant_id` unique key, which
  `ON CONFLICT (enrollment_device_id)` does not arbitrate, and one answered
  503. The grant now takes a per-owner transaction advisory lock; the host
  check sends four concurrent grants (it failed 2 of 4 runs without the lock
  and passed 6 of 6 with it).
- Closed contracts added for stale callers: the pairing claim refuses a
  non-string header argument (the retired pool argument shifted the others),
  the community capture refuses `retirement`, and maintenance refuses
  `ledgerPool`.
