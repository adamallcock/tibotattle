# Scope

This receipt covers a zero-network next-upload inspection and enforceable
foreground contribution limits. It is development evidence, not approval for
background installation or external participant collection.

# Implemented controls

- `sync-contributions-inspect-next` discovers, verifies, and locally queues
  committed prepared sets before showing one bounded projection.
- The projection contains only allowlisted schema, platform, and provider-policy
  classes; covered timestamps; record counts; client-declared accounting
  diagnostics; prepared and reserved bytes; attempt count; and next-attempt
  time.
- The projection contains no record arrays, paths, filenames, digests, job or
  contribution identifiers, account/session scopes, origin, or credential.
- Inspection performs no key fetch, device authorization, registration, or
  upload.
- One-shot and watch delivery accept a 1–100 upload-attempt cap.
- One-shot and watch delivery accept a 16 KiB–256 MiB conservative encrypted
  upload-body reservation, with a 16 MiB default.
- Each job reserves twice its verified prepared JSON size plus 8 KiB before it
  is claimed.
- A job that would exceed the remaining pass budget stays pending and its
  attempt count remains unchanged.
- Foreground watch applies the limits independently on every visible pass and
  still installs no scheduler, login item, LaunchAgent, or daemon.

# Focused evidence

The final focused queue and CLI run passed 21 checks. It proves:

# Precise bandwidth claim

The reservation is an intentionally conservative upper bound for the encrypted
contribution request body generated by the current envelope implementation. It
does not measure or cap DNS, TCP/TLS framing, the public-key response, the
device-authorization request/response, retries below the fetch boundary, or
other network stack overhead. Product copy calls it a conservative upload-body
reservation rather than total network usage.
