# GCP O-OPS ops tooling bundle

This is a 2026-10-02 receipt for stream O-OPS on branch `claude/gcp-fp-o-ops`.
The branch is built on `9700d167` (`claude/gcp-fastpath-final`). It has two
commits: the bundle (`46e515f0`) and the review fixes recorded under
[Review fixes](#review-fixes). It covers four items from the cutover
checklist:

- D-OPS3: OPS-3 `pause-all` and `resume-all`;
- D-BLOB: the origin-deploy contract-blob check;
- C-BACKUP: one pre-migration backup;
- E-OPS5: monitoring and alerting as code, with the K-DETECT unseen-token
  probe.

It records **local, synthetic** evidence only, from one macOS arm64
workstation with Node 26.2.0:

- The offline checks drive in-memory gcloud fakes, with `PATH` blanked so
  no real gcloud can start.
- The K-DETECT SQL ran on the local PostgreSQL 17 fan-out cluster (port
  55433), in a throwaway `o_ops_kdetect_<hex>` schema. The schema was
  migrated from this checkout, seeded with synthetic typed rows, and then
  dropped (0 `o_ops_%` schemas remain).
- No gcloud or wrangler command ran. Nothing read or wrote a GCP or
  Cloudflare resource, in production or test, and nothing was pushed.
- No monitoring resource, trigger or backup exists because of this stream.

This receipt is not evidence that any of this works against a live project.
The first owner-run readback against the test project is that qualification.

## What changed

| Item | Implementation |
|---|---|
| D-OPS3 pause-all | `gcp-infra.mjs pause-all --environment=<env>` is a dry run by default. It makes one `scheduler jobs list` call and returns a plan: every plane trigger with its action, any co-tenant trigger that keeps OPS-10's gate shut, and that gate after the pauses. Applying it takes `--apply --authorize=<planDigest> --receipt-out=<abs>` and the committed desired state only. The applied run re-reads and re-plans. It refuses a different digest (`PAUSE_ALL_PLAN_DIGEST_MISMATCH`), a blocker (an unrecognized trigger state) or the synthetic fixture. It then reserves the receipt file (exclusive, `0600`, no symlink) and issues only `scheduler jobs pause` in name order. Finally it reads back and writes the receipt: `paused` (by this run), `alreadyPaused`, `failed`, the plane's states and the gate. The receipt is written even when a pause fails (`status: "incomplete"`, then `PAUSE_ALL_INCOMPLETE`), so whatever was paused can be resumed |
| The plane | In a dedicated project, the plane is every trigger in the region. In a shared project it is the plane's managed triggers plus any trigger that runs one of the plane's jobs. Co-tenant triggers are never paused. A co-tenant trigger that runs a Cloud Run job and is not `PAUSED` is listed in `foreignBlocking`, and the dry run then exits 2 |
| `ROLLOUT_JOBS_NOT_PAUSED` | The rollout's trigger classifier moved, unchanged, into the leaf module `scripts/gcp-scheduler-run-target.mjs`. Both the rollout and pause-all import it, so pause-all pauses exactly the triggers the gate reads. A check proves that the gate holds after pause-all, by the rollout's rule over the same classifier, and that OPS-10's `readback --require-clean` verdict for the managed trigger is unchanged |
| D-OPS3 resume-all | `gcp-infra.mjs resume-all --environment=<env> (--pause-receipt=<abs> \| --only=<a,b>)` is a dry run by default. A managed trigger is resumed only when its committed `state` is `ENABLED`, it is live `PAUSED`, and either `--only` names it or the verified pause-all receipt records it as paused by that run. The receipt must be for this plane, self-digested, closed in its keys and its read-back triggers, and at most `PAUSE_ALL_RECEIPT_MAX_AGE_HOURS` (24) old; otherwise it is `PAUSE_ALL_RECEIPT_STALE` or `PAUSE_ALL_RECEIPT_INVALID`. The trigger's live `userUpdateTime` and `lastAttemptTime` must also still equal the ones the receipt read back after the pauses. Every other trigger gets a closed reason: `COMMITTED_STATE_PAUSED`, `NOT_PAUSED_BY_PAUSE_ALL`, `CHANGED_AFTER_PAUSE_ALL` (resumed and paused again, updated, or run since), `PAUSE_ALL_READBACK_MISSING`, `ALREADY_ENABLED`, `TRIGGER_ABSENT`, `NOT_SELECTED` or `STATE_UNRECOGNIZED`. Unmanaged triggers are never resumed. `--only` refuses unknown names (`RESUME_ALL_ONLY_INVALID`) and ineligible ones (`RESUME_ALL_ONLY_INELIGIBLE`). Applying takes `--apply --authorize=<planDigest>` from the committed state and issues only `scheduler jobs resume` |
| Guard | `guardedGcloud` gains a `pause` mode, which may issue only `scheduler jobs pause`, and a `resume` mode, which may issue only `scheduler jobs resume`. The resume shape lives outside `MUTATING_COMMANDS` (`RESUME_COMMANDS`), so `apply` and `read` still refuse it as `GCLOUD_COMMAND_FORBIDDEN`. An unknown mode is `GCLOUD_GUARD_MODE_INVALID`. The fake gcloud learns `scheduler jobs resume` (`PAUSED` only, as Cloud Scheduler does) |
| D-BLOB, OPS-10 roll | The capture check is split out and exported as `verifyEdgeLiveCapture` and `readEdgeLiveCaptureFile`; the capture rules are unchanged. `assertOriginContractBlob` now runs in **every** edge mode, not only gcp. It refuses `EDGE_CONTRACT_DRIFT` unless `apps/worker/src/edge-origin-contract.ts` has one and the same blob at `--commit` and at the live edge's `DEPLOYMENT_SOURCE_COMMIT`, and a missing file on either side also refuses. The roll receipt's `edge.contractBlob` is always set. This matches the decision record ("Cloud Run deploys must apply the same check against the live edge commit") and `production-edge-modes.md` "Cloud Run deploys", which is updated. That runbook now orders a contract change as: brake to fenced from an edge commit that already carries the new blob, then the origin, then gcp. It also names OPS-2's first create of the service from a bootstrap image as the one unchecked origin deploy, and says why that is safe |
| D-BLOB, test deploy | The `origin` step, standalone or in `all`, requires `--commit`, `--edge-live=<abs>` (the owner's EP-9 capture) and `--edge-environment=production\|staging`. Before any remote command, it verifies the capture with the rollout's own check (fresh, of that tracked Worker, verified for its mode) and the blob equality. It repeats the blob comparison right before the origin's first write. The origin receipt records `edgeContract` (environment, mode, edge commit, capture time, origin commit, blob) |
| C-BACKUP | `PRE_MIGRATION_BACKUPS` goes from 2 to 1 (owner: one backup plus point-in-time recovery). The migrate receipt must hold exactly one backup, and the tests and the rollout header are updated to match |
| E-OPS5 | `scripts/gcp-ops-monitoring-policies.mjs` renders, from the validated desired state alone: four log-based metrics, the origin-lock uptime check and eleven alert policies. Each policy carries a severity and its own anchor in the new `cloud-run/infra/monitoring.md`. `scripts/gcp-monitoring.mjs` offers `render`, `readback` (three guarded list calls), `plan` (create, update, unchanged, deferred, refused delete, `planDigest`) and `origin-lock-probe`. **There is no apply command** |
| Alerts | <ul><li>Origin 5xx ratio over 2 % for 10 min, with Cloud Run's 5xx minus the origin's own `503 POSTGRES_ROUTE_NOT_PORTED` lines (page).</li><li>Refresh `LOCK_HELD` (ticket).</li><li>No `state: complete` refresh receipt within cadence plus 60 min, because a lost lock exits 0 (page).</li><li>No Cloud Scheduler attempt for a committed-`ENABLED` trigger within max(6 h, cadence plus slack): the paused-too-long alert (ticket). It is a log-absence proxy: about 25 h for a daily trigger, a trade-off recorded for the owner (OWN-5). A trigger with no cadence or committed `PAUSED` drops only its own condition (`deferredConditions`).</li><li>Origin lock: an uptime check that accepts exactly `[403]` with Google's front-end text and no credentials (page).</li><li>Cloud SQL CPU, memory, disk, and connections over 80 % of the committed `max_connections` (ticket).</li><li>K-DETECT unseen tokens, and a 26 h probe silence (ticket). The probe metric counts only lines with a verdict (`clear` or `unseen`), so a probe that only fails is silence.</li></ul> |
| Privacy scanner | Filters and extractors may read only `ALLOWED_LOG_FIELDS`, and PromQL may match only `ALLOWED_QUERY_LABELS`. `FORBIDDEN_LOG_FIELDS` fail explicitly: request id, method, URL, path, query, IP, email, token, `httpRequest`, `textPayload`, `protoPayload`, labels and trace. The scanner runs on every render, and negative tests tamper with every surface |
| Deferrals | Each policy waits with one closed reason: `NOTIFICATION_CHANNEL_UNASSIGNED` (OWN-5c), `SCHEDULER_CADENCE_UNSET`, `SCHEDULER_CADENCE_UNSUPPORTED`, `TRIGGER_COMMITTED_PAUSED` or `PRODUCER_NOT_IN_MANIFEST:unseen-token-probe`. The notification channel is an input whose project must be the plane's. Output shows it only as `assigned` or `unassigned`; the plan compares live channels by digest |
| K-DETECT | `cloud-run/unseen-token-probe.mjs` counts one UTC day's model, speed, tier and plan tokens. It reads both typed families (`typed_telemetry_*` and `telemetry_v12_typed_*`; plans from quota rows and usage attributions) through `typed_telemetry_dictionary`, in a read-only transaction. It selects tokens and counts only, never an owner, device, session or record id. It compares them with the bundled catalog (`REVIEWED_MODEL_CATALOG` and `TELEMETRY_MODEL_IDS`, `PERFORMANCE_SPEED_MODES`, `PERFORMANCE_API_SERVICE_TIERS`, `TELEMETRY_PLAN_TYPES`). A token is `unseen` when it fits the v1.x wire grammar `[A-Za-z0-9._:-]{1,64}` (owner, round 7 "Name guard", pinned by a check to telemetry-contract's `TOKEN` and `V12_TOKEN`), and `unrecognized` otherwise (an ARN with `/`, an email address, anything over 64 characters). **No token is printed** (`UNSEEN_TOKEN_LISTING = "held"`): each dimension reports its distinct unseen and unrecognized counts and their records. Plain-text listing (at most 50 per dimension) is built and checked, but waits for the root `AGENTS.md` invariant narrowing that the round-3 amendment requires. Sentinel shares (`unknown`, `other`, `mixed`) are reported separately. The CLI connects only to a local test endpoint; the Cloud Run job is D-OPS4's |

## Not covered, and gates that remain

- **No live qualification.** These shapes are assumptions until the first
  owner-run readback against the test project:
  - `gcloud monitoring policies list` and `monitoring uptime list-configs`
    output;
  - the PromQL names of log-based metrics
    (`logging_googleapis_com:user_<name>`);
  - Cloud Scheduler's `AttemptStarted` log entry.

  The plan's update detection compares a normalized view and may report
  spurious updates the first time.
- **No monitoring apply.** Creating the metrics, uptime check and policies
  is a separate, digest-authorized stream. It needs the notification channel
  and billing account (OWN-5c). Budget alerts are not rendered.
- **Ordering consequence of D-BLOB.** A pre-edge Worker (production today,
  `d43c8f92`) has no contract file, so every OPS-10 roll refuses
  `EDGE_CONTRACT_DRIFT` until the edge port is live in worker mode. PROD-5
  (worker-mode edge deploy) must therefore precede PROD-3 (pre-staged
  origin). Test-deploy `origin` runs likewise need a capture of an edge-port
  Worker, either the staging edge (OWN-7b) or production after PROD-5. With
  `--image`, the test deploy cannot prove that the image was built from
  `--commit`; the operator pairs them.
- **K-DETECT scheduling.** The probe has no build entry and no manifest job.
  D-OPS4 adds the probes, and its two alerts stay deferred until a job named
  `unseen-token-probe` exists.
- **AGENTS.md invariant.** The owner allowed model, speed, tier and plan
  names in plain text (round-3 amendment), and required the change that
  prints them to narrow the root "raw account IDs" invariant, with its tests
  and docs. This stream does not edit root agent guidance, so the probe's
  listing is held: it prints counts only. The narrowing, and the one-line
  flip of `UNSEEN_TOKEN_LISTING` to `"plain"` with its check, belong to the
  same later change.
- The origin request log contract is mirrored from W3-CRA
  (`ORIGIN_REQUEST_LOG_FIELDS` at `3024a521`). A check compares the mirror
  with that module once it is on the line (D-CRB).
- The six-hour paused threshold and the alert thresholds (2 %, 80 %, 90 %,
  26 h) are proposals that still need the owner's confirmation (OWN-5). So
  is the scheduler-quiet proxy: it fires after about 25 h for a daily
  trigger, not after "a few hours". The exact 6-hour signal needs a periodic
  job that runs `scheduler-probe` and logs its verdict.
- resume-all's receipt binding compares `userUpdateTime` and
  `lastAttemptTime`. Whether Cloud Scheduler moves `userUpdateTime` on a
  pause or resume is still unqualified; `lastAttemptTime` and the 24-hour
  age bound cover the case where it does not, except a resume and re-pause
  with no attempt in between.

## Review fixes

A review of `46e515f0` raised seven findings. Each was checked against the
code, the owner decisions and the tools before it was fixed. None was
rejected.

| Finding | Verified | Fix |
|---|---|---|
| High: the probe's printed-token grammar contradicted the round-7 name guard | Yes. `/^[A-Za-z0-9._:/@+=-]{1,64}$/u` accepted a `/`-bearing ARN, an email address and `a+b=c`, and the check listed an ARN with `/` | The grammar is now `/^[A-Za-z0-9._:-]{1,64}$/u`, citing round 7. A check pins it to telemetry-contract's `TOKEN` and `V12_TOKEN` (they are not exported, so it cannot be imported). An ARN with `/`, an email address and `a+b=c` are now unrecognized and never listed |
| Medium: plain-text logging of names without narrowing the root invariant | Yes. Root `AGENTS.md` was unchanged, and a colon-only ARN would still pass | Took the review's second option: **the listing is held** until the narrowing lands. The probe line carries counts only, and the default report is checked to carry no token text. This stream does not edit root agent guidance |
| Medium: a probe that fails every day was invisible | Yes. The failure line carries the probe's schema, and Cloud Run parses JSON on stderr into `jsonPayload` | The log metric now also requires `jsonPayload.verdict=("clear" OR "unseen")`. A check runs the real CLI, takes its failure line, and shows that it does not match the filter while both report lines do |
| Medium: resume-all accepted a receipt of any age and ignored later deliberate pauses | Yes. A re-digested receipt from 2026-08-01 resumed a paused trigger | Receipts are bounded to 24 hours (`PAUSE_ALL_RECEIPT_STALE`) and must not be dated ahead of now. They record each plane trigger's `userUpdateTime` and `lastAttemptTime`, which must be unchanged (`CHANGED_AFTER_PAUSE_ALL`). Negative tests cover a stale receipt, a future one, tampered read-back entries, a missing read-back, a trigger resumed and re-paused, and one that ran |
| Low: scheduler-quiet is a proxy, and one deferred trigger deferred every condition | Yes, by construction (`Math.max` window; first deferral deferred the policy) | Conditions now defer per trigger (`schedulerQuietConditions`, `deferredConditions` in the render and plan). The 25-hour trade-off is recorded for the owner in `monitoring.md` and here |
| Low: the contract-change procedure no longer worked as written | Yes. The edge checks the origin blob only in gcp mode, while origin deploys now check in every mode | The runbook orders the steps: brake to fenced from an edge commit with the new blob, then the origin, then gcp. The decision record carries a dated note that links to it |
| Low: OPS-2's first service create from a bootstrap image is an unchecked origin deploy | Yes.
