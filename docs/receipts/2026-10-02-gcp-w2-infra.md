# GCP W2-INFRA single-instance infrastructure

This is a 2026-10-02 receipt for package W2-INFRA on branch
`claude/gcp-fp-w2-infra`, built on `45afdf63` (`claude/gcp-fp-edge`). It
covers two commits: `b523ac64`, and the review-fix commit that adds
[Review fixes](#review-fixes). It records **local, synthetic** evidence only: one macOS arm64 workstation,
Node 26.2.0, and the local PostgreSQL 17 fan-out cluster for one gate. No
gcloud, wrangler or Cloudflare command ran. Nothing read or wrote a GCP or
Cloudflare resource, production or test. Nothing was pushed. Every check that
touches the OPS-2 tooling blanks `PATH`, so a real gcloud cannot start, and
drives an injected, in-memory gcloud instead. Every desired state, account,
bucket, token and image digest here is synthetic and content-free.

This receipt is not evidence that the tooling works against a live project.
The first owner-run readback against a real project is that qualification
(see [Open](#open)).

## What changed

The package removes the deletion ledger from every production-facing
infrastructure surface: one Cloud SQL PostgreSQL 17 instance and no ledger
(append-only decision record 2026-09-26, D2 and D4). It also adds OPS-2 as
scripted gcloud over a checked-in desired state.

### SIMP-0 item 7: CR-3 production configuration

[`postgres-production-configuration.mjs`](../../apps/worker/cloud-run/postgres-production-configuration.mjs)
now has these properties:

- The ledger pool is gone. `PRODUCTION_POOL_SIZES` is data 3, admission 4 and
  readiness 1, and every pool, readiness included, opens only `primary`.
  `PRODUCTION_POOL_CONNECTIONS_PER_INSTANCE` is `{ primary: 8 }`.
- The ledger database resource, `LEDGER_INSTANCE_CONNECTION_NAME_NOT_INDEPENDENT`,
  `LEDGER_SCHEMA_NOT_INDEPENDENT`, `GCS_ERASURE_BUCKET_HISTORY_PROOF`, the
  history-proof parser and `resources.historyProof` are removed. A
  configuration's `resources` is exactly `primary`, `iamUser` and `bucket`.
- The closed-key rule is **refusal**. `LEDGER_INSTANCE_CONNECTION_NAME`,
  `LEDGER_DATABASE`, `LEDGER_SCHEMA` and `GCS_ERASURE_BUCKET_HISTORY_PROOF`
  join `PRODUCTION_FORBIDDEN_VARIABLES`, and each is refused with its own code
  when present, even empty, in every profile. Any other `LEDGER_` name is
  refused with `LEDGER_CONFIGURATION_FORBIDDEN`. A deployment rendered from a
  stale template therefore fails closed.
- The Cloudflare hygiene is kept. `DELETION_LEDGER` stays in the absent-key
  list, a stray `DELETION_LEDGER` binding still fails, and the production
  deletion-ledger D1 stays in the fingerprint.
- The test estate's ledger instance and schema stay test-target identities, so
  the primary settings can never name them.

The ledger assertions lived in
[`cloud-run/postgres-production-configuration.check.mjs`](../../apps/worker/cloud-run/postgres-production-configuration.check.mjs),
not in the `scripts/cloud-run-production-configuration.check.mjs` the brief
named. Both were updated:

- Each removed behaviour is now an absence or refusal assertion.
- The history-proof cross-check was replaced by a single-instance test.
- The schema-grammar mirror still compares `PRIMARY_SCHEMA` with the canonical
  `createPostgresSchemaConfig`. That function takes a fixed probe for the
  second schema until SIMP-4 removes it.
- The drift check asserts that the retired names are never pinned,
  deployment-provided or secret, and that a `wrangler.jsonc` var of that name
  is unclassified drift.

### SIMP-0 item 8: EP-7 service template

[`production-service.template.yaml`](../../apps/worker/cloud-run/production-service.template.yaml)
no longer has the `LEDGER_*` and `GCS_ERASURE_BUCKET_HISTORY_PROOF` env
entries, placeholders or comment lines. The pool comment names data,
admission and readiness.
[`production-edge-infra.check.mjs`](../../apps/worker/cloud-run/production-edge-infra.check.mjs)
changes in four ways:

- It reports `DELETION_LEDGER_SETTING_PRESENT:<name>` for a retired name
  anywhere in the template, comments included.
- It shows that a render cannot carry a retired value.
- It keeps the IAM template invoker-only.
- It cross-checks OPS-2's renderer against its reference renderer, service
  and IAM, with and without the verifier and the optional secret.

### SIMP-0 item 9: OPS-1 backup horizon

[`ops-backup-horizon.mjs`](../../apps/worker/cloud-run/ops-backup-horizon.mjs)
now has these properties:

- `BACKUP_HORIZON_ROLES` is `['primary']`, and the independent-instance rule
  is gone.
- The tombstone derivation is removed: `RESTORE_SUPPRESSION_TOMBSTONE_DAYS`,
  `HORIZON_MARGIN_DAYS`, the margin clause of the invariant and the header
  that cited the ledger writer.
- The kept constants are byte-identical to `45afdf63`: 365, 7, 30, 7, 90,
  300, 30 and 36. The check pins their eight declaring lines and fails on
  a doctored literal.
- The audit receipt schema is now `tibotattle-backup-horizon-audit-v2`,
  because its closed shape changed to one role. A v1 receipt, and any receipt
  or input that names a ledger role, is refused.

[`gcp-backup-horizon.mjs`](../../apps/worker/scripts/gcp-backup-horizon.mjs)
takes `--primary-instance` only. A `--ledger-instance` flag is an unknown
argument, and `--instance-role=ledger` is refused. No OPS-1 file imports or
names the PostgreSQL ledger writer.

### OPS-2, OPS-3-lite and the runtime bucket grant

The new files are:

- [`gcp-ops-infra-manifest.mjs`](../../apps/worker/scripts/gcp-ops-infra-manifest.mjs):
  the closed validator and the renderers. Its header records why it uses
  scripted gcloud and not Terraform.
- [`gcp-ops-infra-operations.mjs`](../../apps/worker/scripts/gcp-ops-infra-operations.mjs):
  the guarded runner, readback, plan and apply.
- [`gcp-ops-bucket-birth.mjs`](../../apps/worker/scripts/gcp-ops-bucket-birth.mjs):
  the bucket insert.
- [`gcp-infra.mjs`](../../apps/worker/scripts/gcp-infra.mjs): the operator CLI
  for `render`, `readback`, `plan`, `apply` and `bucket-birth`.
- `scripts/fixtures/gcp-ops-infra/`: the synthetic desired state and an
  in-memory gcloud used by the checks only.

The desired state is closed. It holds the region, Artifact Registry
(immutable tags) and the service accounts: runtime, migrator, scheduler,
builder, edge invoker and an optional verifier. The edge invoker and verifier
hold no project role, and no account holds a basic role. It also holds the
custom role, the Secret Manager containers, exactly one Cloud SQL instance,
the bucket, the IAM-private service, the two jobs and the trigger.

## Deviations from the brief, following the code and owner decisions

- **The CR-3 check file.** The ledger assertions were in
  `cloud-run/postgres-production-configuration.check.mjs`. That file was not on
  this package's owned list, and no other package or forbidden list names it.
  It had to change with the module, so it was edited.
- **Instance IP.** The runtime connector (`cloud-run/cloud-sql.mjs`) dials with
  `ipType: "PUBLIC"`. The instance therefore keeps a public IPv4 address,
  reachable only through a connector: connector enforcement `REQUIRED` and no
  authorized networks. A private-IP-only instance needs a runtime change first.
- **OPS-1 receipt schema.** It is bumped to v2 because its closed shape changed.
  The 365-day ceiling is no longer bounded by the invariant, because there is
  no tombstone to derive it from. The byte pin guards it instead.
- **OPS-2 v4 brief items not rendered.** The OPS-2 v4 brief names an
  `opsBackupAudit` account and probe, restore-verify and Worker-era analytics
  jobs. None is rendered; they wait for OPS-4 and OPS-7.
- **`production-migrate`.** The job's entry (`dist/production-migrations.mjs`)
  and env keys mirror W2-OPSDB's `PRODUCTION_MIGRATION_JOB` and its
  `validateProductionMigrationEnvironment` at `e46ceb56`, which is not on this
  base. Integration should import them instead of mirroring them.

## Review fixes

A review of `b523ac64` reported five defects and two notes. Each defect was
reproduced on the in-memory gcloud or by reading the code before it was
fixed. None was rejected.

1. **A trigger whose pause failed stayed running and read as converged
   (medium).** Reproduced: with `scheduler jobs pause` failing, apply stopped
   at `scheduler:pause:analytics-refresh` and the trigger stayed `ENABLED`. A
   fresh readback had no finding, and the plan summary was 0/0/0. Fix:
   - The desired state's trigger now carries a closed `state`, `PAUSED` or
     `ENABLED`. A trigger with no cadence can only be `PAUSED`.
   - Readback reads the live state, normalized to a closed set. A trigger
     that runs while `PAUSED` is desired is the finding
     `SCHEDULER_TRIGGER_ENABLED:<job>`, and the plan pauses it. Any other
     live state blocks the plan.
   - A paused trigger whose desired state is `ENABLED` gets a deferred
     resume, `SCHEDULER_TRIGGER_RESUME_PENDING`, which apply never runs.
     The guard still has no resume shape.
   - The check injects the pause failure and asserts that the re-plan holds
     exactly that pause. A process killed between the two calls ends in the
     same state and recovers the same way.
   - The header and the table no longer say "never starts a schedule". Between
     a failed pause and the next apply the trigger runs, and OPS-10's
     `--require-clean` preflight refuses the estate in the meantime.
2. **The OPS-2 surface did not match OPS-10's consumer (medium).** Reproduced
   against `claude/gcp-fp-w2-opsdb` `e46ceb56`: OPS-10's argv was refused,
   `rolloutTarget` was missing, and `production-migrate` had the wrong entry
   and env. This package took the contract OPS-10 already uses:
   - The CLI takes `--environment=<env>` in place of `--desired-state`, with
     the path taken from that environment's variable. It refuses a file that
     describes another environment.
   - `readback --require-clean` prints the readback, its plan digest and
     summary, and a closed verdict. It exits 0 only when the estate is clean.
   - `rolloutTarget(environment)` and `rolloutTargetFromDesiredState` are
     exported. This makes `process.env` the manifest's one ambient input, as
     the default of that one function, and the purity check pins that.
   - `production-migrate` renders `dist/production-migrations.mjs` with the
     ten env keys OPS-10's validator reads.
   - The validator also adopts OPS-10's name rules. The migration job's name
     carries the `migrate` token. No plane resource carries a `test` or
     `rehearsal` token. The image repository and the builder account carry
     the plane marker.
   - A new check runs OPS-10's `validateProductionMigrationEnvironment` and
     `validateRolloutTarget` on this render, for production and staging. It
     is skipped on this branch, because OPS-10's modules are absent here.
   - An integration rehearsal ran in a scratch tree: `git archive` of
     `e46ceb56`, with this package's files laid over it and the two
     `package.json` script additions merged. The OPS-2 gate passed 179 of
     179, the new check included. OPS-10's checks (rollout, production
     migrations, runtime grants, test database) passed 45 of 45.
     `loadRolloutTargetFromInfraManifest` returned a target that
     `validateRolloutTarget` accepts. OPS-10's exact argv parsed, and with no
     gcloud on `PATH` it failed closed.
3. **Bucket birth could lose its proof (low).** Reproduced from the code: the
   receipt was opened only after the irreversible insert. Fix:
   - The `--receipt-out` file is reserved (`O_CREAT|O_EXCL|O_NOFOLLOW`,
     0600) before any call. An existing or unwritable path refuses with
     `BUCKET_BIRTH_RECEIPT_PATH_UNAVAILABLE`, with no listing and no insert.
   - Every failure after the insert carries `bucketInserted: true`.
   - A failed receipt write carries the content-free receipt. The CLI prints
     it on stdout as `created_receipt_unwritten` and exits 1.
   - A run that ends without a receipt removes its empty reservation.
4. **The analytics-refresh Job could never run outside the test estate
   (low).** Reproduced: the env OPS-2 renders, run as that Job, makes
   `resolveAnalyticsRefreshDatabase` refuse with
   `ANALYTICS_V2_REFRESH_TARGET_FORBIDDEN`, in both planes. Fix:
   - `DEFERRED_JOBS` defers the Job's create, its scheduler grant and its
     trigger's create (`ANALYTICS_REFRESH_PRODUCTION_TARGET_UNAVAILABLE`), so
     today the fast path creates no trigger at all.
   - The manifest check pins the entry's refusal. When the entry gains a
     reviewed production target, that check fails, and the deferral is
     removed together with it.
   - The checks pass `jobDeferrals: {}` to exercise the path that applies
     after that, the trigger paths included.
5. **Apply re-enabled a deliberately disabled account or role (low).**
   Reproduced: a disabled edge-invoker account planned
   `iam service-accounts enable`, and a `DISABLED` role planned `--stage=GA`.
   Fix:
   - A disabled managed account is the finding and blocker
     `SERVICE_ACCOUNT_DISABLED:<role>`.
   - A role stage other than GA is `CUSTOM_ROLE_DISABLED` or
     `CUSTOM_ROLE_STAGE_NOT_GA`.
   - Either refuses the whole plan, even when bundled with unrelated drift.
   - `iam service-accounts enable` left the guard, and no plan carries
     `--stage`.

The two notes needed no change. The edit to
`cloud-run/postgres-production-configuration.check.mjs` is recorded in
[Deviations](#deviations-from-the-brief-following-the-code-and-owner-decisions).
The CR-3 versus D4 interim ledger-schema conflict stays an owner decision.

## Open

- **Runtime quarantine store and the history proof (SIMP-4 and CR-7).**
  `GcsQuarantineObjectStore` still takes an optional bucket-history proof.
  Without it, on a soft-delete-0 bucket, its missing-object `head` and its
  `delete` list soft-deleted generations, and Cloud Storage answers that
  query with HTTP 400, so both fail closed with 503. The production
  composition must change that store, or read the proof from the bucket-birth
  receipt, before it serves storage. CR-3 deliberately no longer carries it
  (decision record, "Superseded planning contracts", item 3).
- **The runtime ledger role (SIMP-4 before CR-7).**
  `src/postgres-client.ts` still requires a second schema, so a production host
  cannot be composed from CR-3 alone until SIMP-4 lands. Decision D4 allows an
  interim second schema on the same instance, but CR-3 now refuses `LEDGER_*`
  settings. An interim schema would be a new, reviewed setting.
- **The analytics-refresh Job and trigger are deferred.** The fast path
  creates neither, because `cloud-run/analytics-refresh.mjs` (not owned here)
  resolves only test targets. Lifting the deferral needs a reviewed
  production target path in that entry, then removing the `DEFERRED_JOBS`
  entry and its pin. The analytics share of the connection budget stays
  reserved meanwhile.
- **Resuming the trigger is two steps.** OPS-3 resumes it, and the owner sets
  the desired `state` to `ENABLED`. Without the second step, the next OPS-2
  plan shows a pause, before authorization. A failed pause leaves the trigger
  running until the next apply, and OPS-10's preflight refuses meanwhile.
- **Integration with W2-OPSDB.** Only `apps/worker/package.json` conflicts
  (one added script key on each side, both kept). After the merge:
  - Import `PRODUCTION_MIGRATION_JOB` in place of the mirrored entry and env.
  - The OPS-10 cross-check then runs unskipped.
  - OPS-10's test "without the infrastructure manifest every verb fails
    closed" still passes, now through `GCP_INFRA_DESIRED_STATE_UNCONFIGURED`,
    so its name should change.
- **A bucket insert whose outcome is unknown** (a network failure or a
  non-200 answer) is reported as a failure before the insert. A rerun's
  listing then shows whether the bucket exists. Its proof would then have
  to be read back by hand.
- **First live readback.** The readback normalization follows the documented
  Admin API resource shapes, but no real gcloud output has been parsed. The
  owner's first `readback` and `plan` against the real project is the
  qualification. Expect shape fixes there.
- **Owner prerequisites the tooling does not do.** Enabling APIs. The
  operator's `iam.serviceAccounts.actAs` on the runtime, migrator and scheduler
  accounts. The edge invoker's key for the Cloudflare secret. The secret
  values. The migrator's `CREATE` on the database. The build source bucket and
  the builder's read grant (OPS-10).
- **OPS-10 runtime grants** stay with the migration job, not IaC. The runtime
  role needs `EXECUTE` on `insert_telemetry_v1_contribution`,
  `storage_journal_append` and `storage_owner_link_ensure`.
