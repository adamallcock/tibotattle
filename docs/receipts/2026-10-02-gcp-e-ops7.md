# GCP E-OPS7 backup-restore rehearsal tool

This is a 2026-10-02 receipt for stream E-OPS7 on the side integration branch
`claude/gcp-fp-int-b`, built on `102f7789`. The tool, its check, the runbook
section and this receipt are in the commit that adds this file. It records
**local, offline** evidence only: one macOS arm64 workstation, Node 26.2.0.
No Google Cloud resource was read or written, no `gcloud` command reached a
live project, no PostgreSQL database was opened, nothing was pushed or merged.
Every instance, backup and database row in the tests is a synthetic fake; the
only real input is the committed staging desired state, read as a file.

The tool has never run against a live instance. Its gcloud argv and the shape
of gcloud's JSON output are unverified against the provider (see
[Not proven](#not-proven)).

## What it does

`apps/worker/scripts/gcp-backup-restore-rehearsal.mjs` rehearses restoring the
staging primary (`cloudSql.instance` of the committed staging desired state)
into one scratch instance, `<source>-rehearsal-<id>` (path `backup` appends
`b`). That is the `SCRATCH_INSTANCE_PATTERN` that OPS-10's migration job
already accepts as a scratch target.

| Step | Path `pitr` | Path `backup` |
|---|---|---|
| Preflight (reads) | Describe the source (RUNNABLE, POSTGRES_17, region, PITR on, the point in time inside the log retention); the scratch name must not exist; a read-only fingerprint of the source database | Same, plus the backup run must be SUCCESSFUL and the source's, and the source disk must fit the planned scratch disk |
| Restore | `sql instances clone <source> <scratch> --point-in-time`, then a label patch | `sql instances create <scratch>` (plane posture, no deletion protection, no automated backups, labelled), then `sql backups restore <id> --restore-instance=<scratch> --backup-instance=<source>` |
| Ready | Poll until RUNNABLE, then open a database session | Same |
| Verify | Migration history, schema-shape digests, exact row counts, keyed head and tail row digests; the source read again afterwards | Same |
| Do-not-restore | The injected step, if any, on the scratch only | Same |
| Teardown | Patch to no deletion protection, no final backup, no retain-on-delete; read back; delete; read back the instance list and the scratch's backups | Same |

Timings in the receipt: `cloneMs`, or `createMs` and `restoreBackupMs`;
`readyMs`, from the first mutation to a database session on the scratch;
`verifyMs`; `teardownMs`; `totalMs`.

The verdict is `passed` only when the source read the same before and after,
the histories, schema shapes, table sets, row counts and samples are equal,
and every table could be quoted safely. A source that moved is `inconclusive`.
The row-sample key is 32 random bytes per run, held in memory; no row digest,
key or row text reaches the receipt.

`uploadsMayReopen` is true only when the run completed, the verification
passed, the scratch history equals this checkout's primary manifest, and the
injected `doNotRestore.reapply(target)` returned exactly
`{ status: "done", listSha256, entries, matched, purged }` with
`purged === matched <= entries`. The CLI injects no step, because custody of
the list is OA-9, decided after cutover. Every CLI receipt therefore reads
`false` with `DO_NOT_RESTORE_STEP_NOT_PROVIDED`, and its best exit status is 2.

offline.

| Cleanup of an unlabelled scratch or one labelled for another id | `..._SCRATCH_NOT_OWNED`; no patch or delete | cleanup deletes only ... |

Other behaviour the tests pin: the dry run makes no call; the plan digest
changes with the point in time or sample size; a failed clone that left an
instance is torn down, and one that left none reads `already-absent`; a scratch
that never becomes ready is still deleted; an unreadable backup listing is
`unavailable`, never `none-found`; the receipt file is reserved owner-only
before any mutation, written on success and on a failure after the scratch may
exist, and released on a refusal before it. Each fake database session is
checked statement by statement: only the read-only `BEGIN`, `SET LOCAL`, the
tagged `SELECT`s and `ROLLBACK`, never a write keyword.

A mutation check removed, in turn, the guard's scratch-only target rule, the
`uploadsMayReopen` gate, the unsafe-teardown refusal, the read-only session
refusal and the scratch-exists refusal. Each removal failed one or two tests;
the source was restored before the gates below.

## Not proven

- The live gcloud behaviour: that `sql instances clone --point-in-time`,
  `sql backups restore --backup-instance` into a freshly created instance, and
  `sql instances patch --no-final-backup --no-retain-backups-on-delete` accept
  these argv with SDK 569.0.0, and that `describe`, `list` and
  `sql backups list --filter=instance=<scratch>` print the fields the tool
  reads. The argv were checked against the local SDK's `--help` only.
- That a restored scratch keeps the migrator's Cloud SQL IAM user, so that the
  IAM-authenticated session opens on it. Likely for a clone; less certain for
  a backup restored into an instance created by this tool.
- That the operator may impersonate `tibotattle-staging-migrator`; the
  committed desired state grants the token-creator role on the verifier only.
- That staging holds a migrated schema to compare.
- Recovery time and recovery point on real data: the receipt's timings are
  measured only when the main session runs it.
- Anything about production, the do-not-restore list, or a real recovery
  (OPS-7's verifier job, paired restore and replay proofs are not in scope).

## Open issues

- **OA-9 versus the cutover precondition.** The cutover runbook's Backups
  precondition asks that the restore rehearsal reapplied the do-not-restore
  list before uploads reopened. The owner deferred custody of that list (OA-9)
  to after cutover, so no rehearsal can report `uploadsMayReopen: true` before
  cutover. The runbook now lists this as an open gap needing an owner
  decision.
- **Brief versus item paths.** The E-OPS7 brief names
  `scripts/gcp-backup-restore-rehearsal.mjs`; OPS-7's item names
  `apps/worker/scripts/gcp-restore-rehearsal.mjs` among a larger set (a
  scratch-only verifier job, PG17 specs). The tool lives beside the other OPS
  tools in `apps/worker/scripts/`; OPS-7's verifier job and replay proofs
  remain `not built`.
