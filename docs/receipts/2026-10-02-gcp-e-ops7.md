# GCP E-OPS7 backup-restore rehearsal tool

This is a 2026-10-02 receipt for stream E-OPS7 on the side integration branch
`claude/gcp-fp-int-b`. It covers two commits: `b6463841` (the tool, built on
`102f7789`) and the review-fix commit that adds the
[Review of b6463841](#review-of-b6463841) section. It records **local,
offline** evidence only: one macOS arm64 workstation, Node 26.2.0, gcloud SDK
569.0.0 read as source, and one throwaway local PostgreSQL 17.10 cluster with
synthetic rows. No Google Cloud resource was read or written, no `gcloud`
command reached a live project, nothing was pushed or merged. Every instance,
backup, operation and database row in the tests is a synthetic fake; the only
real input is the committed staging desired state, read as a file.

The tool has never run against a live instance. Its gcloud argv and the shape
of gcloud's JSON output are unverified against the provider (see
[Not proven](#not-proven)).

## What it does

`apps/worker/scripts/gcp-backup-restore-rehearsal.mjs` rehearses restoring the
staging primary (`cloudSql.instance` of the committed staging desired state)
into one scratch instance, `<source>-rehearsal-<id>` (path `backup` appends
`b`). That is the `SCRATCH_INSTANCE_PATTERN` that OPS-10's migration job
already accepts as a scratch target.

| Step | Path `pitr` | Path `backup` |
|---|---|---|
| Preflight (reads) | Describe the source (RUNNABLE, POSTGRES_17, region, PITR on, an explicit point in time inside the log retention); the scratch name must not exist; a read-only fingerprint of the source database, with a write watermark | Same, plus the backup run must be SUCCESSFUL and the source's, and the source disk must fit the planned scratch disk |
| Restore | `sql instances clone <source> <scratch> --point-in-time --async`, then a label patch. `--point-in-time=after-preflight` picks the point a minute after the first source read and waits until it is a minute old | `sql instances create <scratch> --async` (plane posture, no deletion protection, no automated backups, labelled), then `sql backups restore <id> --restore-instance=<scratch> --backup-instance=<source> --async` |
| Wait | Each operation polled with `sql operations describe` to DONE, bounded per step (clone and restore 6 h, create and delete 1 h, patches 30 min) | Same |
| Ready | Poll until RUNNABLE, then open a database session | Same |
| Verify | Migration history, schema-shape digests, exact row counts, keyed head and tail row digests; the source read again afterwards, with its watermark | Same |
| Do-not-restore | The injected step, if any, on the scratch only | Same |
| Teardown | Only once this run's clone was accepted with an operation that did not fail. Wait (1 h bound) until the scratch is settled and no operation on it is unfinished; patch to no deletion protection, no final backup, no retain-on-delete; read back; delete; read back the instance list and the scratch's backups | Same, armed by the accepted create |

Timings in the receipt: `pointInTimeWaitMs`; `cloneMs` and `labelMs`, or
`createMs` and `restoreBackupMs`, each to its operation's end; `readyMs`, from
the first mutation to a database session on the scratch; `verifyMs`;
`teardownMs`; `totalMs`.

The verdict is `passed` when the scratch equals the source and the source read
the same, data and watermark, before and after. A source that moved is
`inconclusive` (`RESTORE_SOURCE_MOVED_DURING_RUN`). A scratch that differs is
`failed` only when the source is shown unchanged since the recovery point,
which needs `--point-in-time=after-preflight`. Otherwise a difference is
`inconclusive` with `RESTORE_SOURCE_UNCHANGED_SINCE_RECOVERY_POINT_UNPROVEN`;
that is always the case on the backup path. The row-sample key is 32 random
bytes per run, held in memory; no row digest, watermark digest, key or row text
reaches the receipt.

`uploadsMayReopen` is true only when the run completed, the verification
passed, the scratch history equals this checkout's primary manifest, and the
injected `doNotRestore.reapply(target)` returned exactly
`{ status: "done", listSha256, entries, matched, purged }` with
`purged === matched <= entries`. The CLI injects no step, because custody of
the list is OA-9, decided after cutover. Every CLI receipt therefore reads
`false` with `DO_NOT_RESTORE_STEP_NOT_PROVIDED`, and its best exit status is 2.

## Review of b6463841

A review of `b6463841` raised three findings. Each was checked against the code
and, for the first, against the gcloud SDK 569.0.0 source. All three held, and
all three are fixed in the review-fix commit.

| Finding | Evidence checked | Fix |
|---|---|---|
| High: a PITR clone that outlasts gcloud's wait leaves an unlabelled full copy of staging that the run cannot delete and `cleanup` refuses | `lib/googlecloudsdk/api_lib/sql/operations.py` sets `_OPERATION_TIMEOUT_SECONDS = 600`. `clone.py`, `backups/restore.py`, `patch.py` and `delete.py` wait with that default; only `create` takes `--timeout` (default 3600). On timeout gcloud raises `OperationError` and exits non-zero while the operation continues. The tool's 3-hour figure was only the spawn kill timer, and the old in-run teardown patched a scratch still in `PENDING_CREATE` | Every mutation is `--async`; the tool polls `sql operations describe` up to explicit per-step bounds. Teardown and cleanup wait (1 h bound) until the scratch is settled and no operation on it is unfinished before any patch, and leave it with `RESTORE_REHEARSAL_SCRATCH_BUSY` rather than patch it busy. `cleanup --adopt-unlabelled` (PITR only, its own authorization `restore-rehearsal-cleanup-adopt-unlabelled:staging:<scratch>`) removes a clone whose label step never ran |
| Medium: the backup path compared the scratch with the source as it is now, so any write after the backup read as a restore defect (`failed`) | `compareFingerprints` compared the scratch with the closing source read and checked only before-versus-after stability | Each source read carries a write watermark (per-table `n_tup_ins`, `n_tup_upd`, `n_tup_del` with table oids, the statistics reset time, the server start time). A difference is `failed` only when the recovery point follows the first source read (`after-preflight`) and the source, data and watermark, did not move; otherwise `inconclusive` with `RESTORE_SOURCE_UNCHANGED_SINCE_RECOVERY_POINT_UNPROVEN`. The runbook states the backup-path precondition and drops the "note the last write time" step, which `sql instances describe` cannot answer |
| Low: the in-run teardown deleted whatever carried the scratch name, so a second run with the same id could delete the first run's scratch | `scratchMayExist` was set before the create or clone call, and teardown ran without an ownership check | Teardown is armed only by an accepted create or clone whose operation did not fail (Cloud SQL refuses an existing name). A refused, failed or operation-less create or clone deletes nothing and reports `teardown.armed: false` with `scratchPresent` |

The earlier report's open issue, "synchronous calls with a 3-hour per-call
timeout", was wrong: gcloud's own wait was 600 seconds for clone, restore,
patch and delete. No synchronous wait remains.

## Refusals and their negative tests

`apps/worker/scripts/gcp-backup-restore-rehearsal.check.mjs`, 38 tests, all
offline. The fake gcloud models Cloud SQL's operations: each `--async`
mutation returns an operation that finishes after a set number of
observations, a clone or create shows `PENDING_CREATE` until then, a clone
inherits the source's user labels, and a patch or delete of a busy instance is
refused and recorded. The tests run on a virtual clock, so the 6-hour and
1-hour bounds are exercised in full.

Other behaviour the tests pin: the dry run makes no call and prints the
operation bounds; `after-preflight` picks a whole-second point at least a
minute after the first source read, clones only once it is a minute old, and
takes the closing source read at least two minutes after it; with that point
covered, a changed row, history, schema shape or table set is `failed`; a
failed label patch or backup restore still deletes the scratch; the receipt
file is reserved owner-only before any mutation, written on success, on a
failure after the scratch may exist and on an unproven-ownership refusal, and
released on a refusal before any mutation. Each fake database session is
checked statement by statement: only the read-only `BEGIN`, `SET LOCAL`, the
tagged `SELECT`s and `ROLLBACK`, never a write keyword.

A mutation check broke, in turn, the settle wait, arming before acceptance,
keeping teardown armed after a failed create, the unproven-recovery-point
verdict, the watermark in source stability, describing unreturned operations,
the `--async` requirement, adoption of foreign labels, plain cleanup of
unlabelled scratches, the point-in-time wait, the statistics wait, the
coverage condition and the operation timeout. Each broke 1 to 4 tests. The
five mutations of the first round (scratch-only target, uploads gate,
unsafe-teardown refusal, read-only refusal, scratch-exists refusal) still
break tests; removing only the redundant `blockedBy.length === 0` conjunct is
an equivalent mutant, and removing it with the manifest condition breaks one.
The source was restored from a copy and compared byte for byte.

The watermark query and the rest of the fingerprint ran once against a
throwaway local PostgreSQL 17.10 cluster (loopback only, synthetic schema, then
deleted). The watermark query ran inside the read-only transaction; two reads
left it unchanged; an insert followed by a delete left every row digest equal
and moved the watermark, so the verdict read `inconclusive` with
`RESTORE_SOURCE_MOVED_DURING_RUN`; and a write inside the read-only
transaction was refused with SQLSTATE 25006.

## Not proven

- The live gcloud behaviour: that `sql instances clone --point-in-time
  --async`, `sql backups restore --backup-instance --async` into a freshly
  created instance, and `sql instances patch --no-final-backup
  --no-retain-backups-on-delete --async` accept these argv with SDK 569.0.0;
  that `--async --format=json` prints the operation with its `name`; and that
  `describe`, `list`, `sql operations describe`, `sql operations list
  --instance=<scratch>` and `sql backups list --filter=instance=<scratch>`
  print the fields the tool reads. The argv were checked against the local
  SDK's `--help` and source only.
- That Cloud SQL refuses a clone or create whose name exists at request time.
  If it instead accepted the request and failed the operation, the tool would
  still not delete (a failed create or clone disarms teardown), but that path
  is unobserved.
- Which operations `sql operations list --instance=<scratch>` returns for a
  clone (a clone's operation may be filed under the source). Teardown also
  waits on the clone operation it holds and on the instance state, so either
  filing is covered.
- That cumulative statistics reach shared memory within two minutes of a
  write on Cloud SQL, as PostgreSQL's 60-second `PGSTAT_MAX_INTERVAL` implies,
  and that the operator's clock is within a minute of Google's.
- That a restored scratch keeps the migrator's Cloud SQL IAM user, so that the
  IAM-authenticated session opens on it. Likely for a clone; less certain for
  a backup restored into an instance created by this tool.
- That the operator may impersonate `tibotattle-staging-migrator`; the
  committed desired state grants the token-creator role on the verifier only.
- That staging holds a migrated schema to compare.
- Recovery time and recovery point on real data: the receipt's timings are
  measured only when the main session runs it.
- Anything about production, the do-not-restore list, or a real recovery
  (OPS-7's verifier job, paired restore and replay proofs are not in scope).

## Open issues

- **OA-9 versus the cutover precondition.** The cutover runbook's Backups
  precondition asks that the restore rehearsal reapplied the do-not-restore
  list before uploads reopened. The owner deferred custody of that list (OA-9)
  to after cutover, so no rehearsal can report `uploadsMayReopen: true` before
  cutover. The runbook now lists this as an open gap needing an owner
  decision.
- **Backup path verdicts.** The backup path cannot show the source unchanged
  since the backup, so a difference there is always `inconclusive`. Making it
  decisive would need a watermark captured before the backup (for example an
  on-demand backup taken inside a quiesced window the tool observes), which
  this tool does not take because it never acts on the source.
- **Brief versus item paths.** The E-OPS7 brief names
  `scripts/gcp-backup-restore-rehearsal.mjs`; OPS-7's item names
  `apps/worker/scripts/gcp-restore-rehearsal.mjs` among a larger set (a
  scratch-only verifier job, PG17 specs). The tool lives beside the other OPS
  tools in `apps/worker/scripts/`; OPS-7's verifier job and replay proofs
  remain `not built`.
