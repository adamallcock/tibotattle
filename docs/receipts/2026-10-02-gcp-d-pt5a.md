## How a stage behaves

1. **Sealed-side preflight, before the target is touched.** The sealed file's
   hash is re-verified (`CUTOVER_SEALED_SOURCE_CHANGED`), then every table's
   column set must equal the spec's mapped columns plus its reviewed omissions
   (`CUTOVER_COLUMN_UNMAPPED`; hidden and generated columns are excluded), every
   sealed value must canonicalize in the closed vocabulary
   (`CUTOVER_SOURCE_VALUE_INVALID`; a JSON text carrying `\u0000` or an unpaired
   surrogate escape is refused here, because PostgreSQL's `jsonb` refuses it
   with 22P05 or 22P02), every inserted row must fit one page
   (`CUTOVER_PAGE_ROW_TOO_LARGE`), every sealed foreign key must close
   (`PRAGMA foreign_key_list`), and the stage's lineage checks must hold
   (`CUTOVER_SOURCE_LINEAGE_INVALID`, `CUTOVER_V12_SOURCE_INVALID`,
   `CUTOVER_JOURNAL_SOURCE_INVALID`, `CUTOVER_PENDING_OBJECT_INVALID`,
   `CUTOVER_ADMISSION_*`, `CUTOVER_CORRECTION_CAS_GUARD_PRESENT`,
   `CUTOVER_CORRECTION_OWNER_NOT_ACTIVE`, `CUTOVER_SCHEMA_MARKER_MISMATCH`, `CUTOVER_ERASED_OWNER_EVIDENCE_PRESENT`,
   `CUTOVER_TYPED_OWNER_AUTHORITY_INVALID`).
2. **Target preflight.** Prerequisite stages are checked through PT-1's ledger,
   PT-3's receipts are compared with the sealed counts
   (`CUTOVER_PARENT_RECEIPT_MISMATCH`), the trigger policy must cover every
   target trigger (PT-1's missing or stale refusal), the target layout must
   match the spec (`CUTOVER_TARGET_COLUMN_MISMATCH`), foreign-key order must be
   satisfiable (`CUTOVER_IMPORT_ORDER_INVALID`), and each table must be empty or
   match its checkpoint.
3. **Writes.** Pages are at most 256 rows and 4 MiB, one transaction per page,
   with a pending checkpoint. Large-row specs use 8-row sealed pages and
   100-row target pages. Triggers are enabled except for the reasoned
   suppressions below. A refusal that comes from the target itself (a guard or
   a constraint firing on a page) rolls back that page only and surfaces as
   `CUTOVER_TARGET_WRITE_REFUSED` with the SQLSTATE and the constant guard
   name; the checkpoint stays at the last committed page and the stage receipt
   stays incomplete. Only sealed-side refusals are guaranteed to precede the
   first write.
4. **Resume and replay.** A resume verifies the prefix chain and the target row
   count (`CUTOVER_CHECKPOINT_DIVERGED`, `CUTOVER_TARGET_ROW_COUNT_DIVERGED`)
   and may use a different page size. A completed stage replays as a no-op that
   writes nothing (row `xmin` values are unchanged).
5. **Verification.** The target's canonical table digest, read in the sealed
   key order through one server-side cursor (see [Digest scan](#digest-scan)),
   is compared with the sealed digest
   (`CUTOVER_TELEMETRY_TABLE_DIGEST_MISMATCH`), then the
   checkpoint and the table receipt complete, identity high-water marks are
   raised, and the stage receipt closes. `assertStageComplete` is PT-1's own.

Refusals are content-free: an error carries a code and table and column names
only, never a sealed value (a test plants a marker value and searches the
error, its message and its stack).

### Digest scan

Verification reads each target table in the sealed key order: text keys under
`COLLATE "C"`, which is SQLite's BINARY order for UTF-8. The first version
paged with keyset predicates (`WHERE key > $last ORDER BY key LIMIT 2000`). An
explicit `COLLATE "C"` cannot use a primary-key index, on any database,
because the planner matches an index's collation by identity (a database whose
default collation is C is no different). Every page therefore re-scanned and
re-sorted the rest of the table, and the cost grew with the square of the row
count. The scan now declares one `NO SCROLL` cursor and fetches pages from it,
inside the transaction its callers already hold (outside one it refuses closed
with SQLSTATE 25P01). PT-3's scan has the same change.

Measured on the local cluster over a text-keyed table on a `en_US.UTF-8`
database, the whole digest including canonicalization and SHA-256:

| Rows | Keyset pages | Cursor |
|---|---|---|
| 100,000 | 0.4 s | 0.09 s |
| 400,000 | 3.0 s | 0.33 s |
| 1,000,000 | 14.7 s | 1.0 s |

The first `FETCH` carries the sort, and PT-1's default 120 s statement timeout
applies to it. The owner's real tables have not been sized (MEAS-3).

### Chunk-owned registrations

Sealed `pending_quarantine_objects` rows whose `contribution_id` is a chunk id
are imported verbatim into `pending_objects`, with the kind rewritten from D1's
`telemetry` to `telemetry_v1`, `telemetry_v11` or `telemetry_v12`. A registration that
does not match its chunk's object key, or a `deleting` one without its lease,
refuses
(`CUTOVER_PENDING_OBJECT_INVALID`). The count and digest are kept in a
`chunk-registrations` checkpoint per stage and read with
`readChunkRegistrationReceipts(handle)` for PT-8's `pending-registrations`
stage. A registration in `deleting` with a lease is covered by the spec.

## PT-3 defect found and fixed

Commit `2c968083` fixes a latent production-blocking bug in the merged PT-3
importer. Its target digest scan ordered rows with an unqualified
`ORDER BY "id"`. In PostgreSQL that resolves to the select list's text alias,
so integer keys sorted as text and any table with more than nine such keys
(10 sorts before 2) produced a digest mismatch. The Q-1 corpus has too few
audit rows to trigger it; a 14-row `admin_action_audit` regression test fails
without the fix (`CUTOVER_IDENTITY_TABLE_DIGEST_MISMATCH [table=admin_action_audit]`)
and passes with it. This engine qualifies its sort keys from the start. The PT-3
spec now creates three targets (`count: 3`).

## Decisions to confirm

- **Header promotion is a proof, not a copy.** The live v1 and v1.1 header
  tables are imported directly by `telemetry-v1-v11`, so `header-promotion`
  verifies that the live headers equal the seal and records a receipt with their
  digests; no mirror, archive or staging relation is created. The alternative,
  which this branch did not build, is a staged migration widening migration
  0040's CHECK constraints so archived headers can live in a mirror.
- **Withdrawn owners' typed memberships are imported** (the insert guard is
  suppressed with a recorded reason), because they are D1 history admitted
  before the withdrawal. An erased link is refused. Confirm that PT-8's owner
  disposition agrees.
- **A withdrawn owner's correction history refuses; it is not imported.** D1
  keeps correction history when an owner withdraws, but PostgreSQL's insert
  guards (primary 0034) admit it only for an active participant with an active
  owner link. Suppressing those two guards, as for the typed memberships, would
  follow "Past contributions: Keep them" and needs an owner decision and a
  recorded reason. Until then the stage refuses with a closed code before the
  target is touched, which is the same line PT-8-lite draws by requiring
  history and facts empty. If PT-8 ever allows populated history, decide this
  first.
- **Registration kind is rewritten** to the family kind, as above.
- **Usage correction is imported, not decided.** The runtime row imports with
  PostgreSQL `source_state` left at `staged`; the Q-1 runtime is `active`, and
  the go or no-go on that state is PT-8's P4 (`CUTOVER_CORRECTION_RUNTIME_ACTIVE`),
  not this stage's.

## Deviations from the PT-8-lite design's tokens

PT-8 consumes `TELEMETRY_PRODUCTION_DISPOSITIONS` (57 entries: 10, 17, 11, 0,
12, 1, 4 and 2 by stage), so these differ from the design table and must be
carried into its coverage module:

- `telemetry_v12_records` is `mapped:telemetry-v12` (the design said imported),
  because the PostgreSQL target is `telemetry_v12_typed_records` with a changed
  column set. The same holds for the runtime, attributions, usage, quota and
  session tools of v1.2, the two typed memberships and the correction runtime.
- `typed_v1_authority_requests` is `must-be-empty` (the design said imported):
  pending requests are in-flight admission state, not history, so a row refuses with `CUTOVER_ADMISSION_PENDING_REQUESTS`.
- The two typed-legacy schema markers are `schema-marker` and the correction CAS
  guard is `must-be-empty`.

`PRODUCTION_STAGING_RELATIONS` and `PRODUCTION_RETAINED_RELATIONS` are both
empty: no stage creates or keeps a relation in `tibotattle_transfer`, and the
spec shows the control schema holding only its frozen relations after all
stages. No staged migration was needed.

## Limits and open issues

- **Real shapes are unverified.** Nothing has run against a real export. The
  specs prove the contract against the d43c8f92 schema and the Q-1 corpus.
- **Two tables never import a row in any test.** `telemetry_v11_records` and
  `typed_v1_preservation_proofs` are empty in the Q-1 corpus and in the
  augmented seal, so only their layout, closure and an empty-table import are
  covered; a populated v1.1 record or preservation proof is unproven.
- **Target-side refusals are mid-stage by nature.** A guard or constraint on the
  target can only refuse when a page reaches it, so `CUTOVER_TARGET_WRITE_REFUSED`
  can follow committed pages. It is transactional per page and resumable, but it
  is not a preflight refusal.
- **A smaller page budget refuses a replay.** The page budget is checked against
  every inserted table in the preflight, so replaying a finished stage with a
  budget below its largest sealed row now refuses
  (`CUTOVER_PAGE_ROW_TOO_LARGE`) instead of passing as a no-op.
- **Effective-reader parity is not re-run.** That check is TypeScript and Vite
  only. Table digests, the 48-table equivalence test and PT-8-E's parity sample
  stand in for it; none of them is the readers.
- **Journal-derived `input_source_digests` and `input_versions`** stay at their
  seed values, exactly as in the rehearsal; analytics recomputes them.
- **Cost of verification.** `sealed.verify()` hashes the whole sealed file on
  each call, so each stage calls it only a few times. The owner's real corpus
  has not been timed; the large-row page sizes are a bound, not a measurement
  (MEAS-3 and the dense-owner measurement remain). The digest scan is linear
  now, but its first `FETCH` sorts the whole table under a 120 s statement
  timeout; time the largest text-keyed table on a non-C database.
- **Rehearsal spec schema names.** The equivalence test runs the rehearsal
  chain in a database named for this stream (`d_pt5a_rehearsal_*`), dropped on
  teardown. Its two schemas inside keep the rehearsal importers' required name
  prefix, so only they do not carry the stream id.
- **Concurrent test runs.** Every database the new spec creates is its own, so
  it shares no database with another suite. The cluster-global transfer role
  is created under the advisory lock the other W2-SEAL specs share, held for
  the life of one cluster fixture, so two fixtures cannot be alive in one
  process.
- **Policy pin.** The check pins `telemetryProductionPolicySha256()` at
  `b8fbb1bf19c101253f760d85e6e382d30a61afc0b3a5b060ae852b73c2fb8c93` (it was
  `82998111387fa2df72b8615f1285590a9d4d8ae0056b054469d0ce025417632f` before the
  two correction guards' recorded reasons were corrected). Any
  reviewed change to a stage's tables, columns, closure, triggers or
  dispositions must update it.
