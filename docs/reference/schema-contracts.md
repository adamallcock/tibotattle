# Schema and contract lifecycle

TiboTattle uses closed JSON Schemas and generated contract artifacts to make
privacy, compatibility, release evidence, and destructive workflows fail
closed. This reference identifies canonical sources, mirrors, generators,
versioning, and retirement rules.

and contract-status records. They are policy state, not JSON Schema mirrors.
`config/codex-contract-ledger.json` and
`config/windows-compatibility-ledger.json` are compatibility ledgers with their
own source-derived checks.

## Canonical versus generated

- Change the canonical package/schema/policy source first.
- Never hand-edit `generated/` or the root telemetry v0.2 mirrors.
- Run the named generator, inspect its diff, then run the check mode.
- A mirror must remain byte-canonical after normalized JSON formatting; do not
  add explanatory fields to only the mirror.
- Human explanations belong here or in source policy metadata, not in a second
  manually maintained field dictionary.

## Closed privacy contract

Privacy-sensitive schemas must:

- use an explicit version and stable `$id`;
- close objects with `additionalProperties: false` wherever arbitrary fields
  would broaden data collection;
- define bounded strings, arrays, counts, timestamps, and enums;
- reject unknown provider fields rather than forwarding them;
- keep missing/unavailable/unknown states explicit;
- have negative tests for content, paths, credentials, identifiers, and
  oversized input; and
- document purpose, privacy class, retention class, public eligibility,
  provider provenance, and limitations for every telemetry v0.1 field through
  `field-policy.json`.

Schema validation is necessary but not sufficient: construction/projection
code must also avoid reading forbidden content in the first place.

## Compatibility and versioning

Use a new contract version when a consumer could assign a different meaning to
the same valid bytes. Additive fields are not automatically compatible when
objects are closed; producer, consumer, consent, storage, relay, public
projection, and deletion/export paths must declare the same transition.

A version change includes:

1. canonical schema and runtime validator;
2. producer and every consumer;
3. TypeScript/public types and package exports;
4. compatibility/consent status;
5. fixtures and positive/negative tests;
6. generated mirrors/dictionaries;
7. storage migration or dual-read window where required;
8. API/privacy/architecture documentation; and
9. retirement criteria for the old version.

Do not weaken a schema or test to accept an already-invalid payload. Fix the
producer or introduce an explicit reviewed version transition.

## Retirement

A contract can be removed only after source search and runtime review prove:

- no current producer, consumer, route, storage row, migration, release
  artifact, or supported compatibility window uses it;
- retained data has a reviewed migration/export/deletion disposition;
- public and native clients have passed the removal version boundary;
- tests, fixtures, generated files, docs, and tool inventory are updated; and
- the deletion does not erase release evidence still needed to verify a
  published artifact.

When those conditions hold, delete the obsolete schema and its obsolete prose
together. Do not leave a deprecated contract appearing current indefinitely.

## Validation

```bash
npm run telemetry:check
npm run telemetry:upload-schemas:check
npm run telemetry:browser:check
npm run release:evidence:validate -- \
  --manifest /absolute/path/release-manifest.json \
  --artifacts-dir /absolute/path/release-directory
npm run docs:check
```

Release-evidence validation is read-only but requires the exact candidate
manifest and artifact directory; the bare package script deliberately refuses
to guess them. R7 regeneration is intentionally absent from this routine list:
it reads environment-specific private evidence and remains a protected owner
workflow.
