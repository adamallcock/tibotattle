## Recommendation

Keep the GCP backend on synthetic and test-only transfer evidence. Do not start a production D1 export or row extraction. Cloudflare documents no Time Travel clone/fork into a separate database; restore overwrites the source in place and cancels in-flight queries. Cloudflare's D1 export endpoint warns that a large export makes the D1 database unavailable to serve queries, and the import/export guide says a running export blocks other database requests. A schema-only export still calls that export operation; the documentation does not promise that no-data exports avoid the block. [Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/), [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/), [D1 import/export guidance](https://developers.cloudflare.com/d1/best-practices/import-export-data/).

The documented metadata-only path is suitable for an optional read-only confirmation: GET D1 database metadata and GET its current Time Travel bookmark. These endpoints return database metadata and an opaque bookmark, not rows or a separate snapshot. Cloudflare's D1 database metadata marks num_tables deprecated and inaccurate, so use a read-only sqlite_schema inventory only if the actual table-name count must be checked. Do not use wrangler d1 export --no-data for that check. [Get D1 Database API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/get/), [Get D1 database bookmark API](https://developers.cloudflare.com/api/resources/d1/subresources/database/subresources/time_travel/methods/get_bookmark/).

If the project requires an online full-source copy, first build and qualify a source-wide change journal/snapshot and object-mutation protocol. Otherwise, the defensible full transfer is an explicitly scheduled operator maintenance window with a source write fence and a separately coordinated R2/deletion-ledger capture. Neither path is authorized by this review. If the export operation blocks requests, stop; do not retry, issue a schema-only export, or switch traffic.

## Cloudflare snapshot and export behavior

- **No separate Time Travel clone is documented.** Cloudflare says Time Travel does not yet clone or fork an existing database. A restore overwrites the same database in place and cancels in-flight queries. A bookmark is a recovery pointer, not a read-at-bookmark query or clone API. [Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/), especially “Restore a database” and “Notes”; [bookmark API](https://developers.cloudflare.com/api/resources/d1/subresources/database/subresources/time_travel/methods/get_bookmark/).
- **Full and filtered exports share the serving-risk boundary.** The export API is POST /accounts/{account_id}/d1/database/{database_id}/export. For larger databases it can make D1 unavailable for queries while running; the client must continually poll or the task automatically cancels. The API supports no_data, no_schema, and table filters, but it does not document an availability exemption for any of these options. The best-practices page separately says a running export blocks other database requests. Do not test the schema-only variant on the live ingestion D1. [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/), [D1 import/export guidance](https://developers.cloudflare.com/d1/best-practices/import-export-data/).
- **The export bookmark is not a clone selector.** In the polling response, at_bookmark identifies the current Time Travel bookmark for that D1 and remains fixed for the duration of the export. The API describes current_bookmark as polling state; it does not expose an export-at-an-arbitrary-historical-bookmark option. A separate GET bookmark returns the current bookmark or nearest bookmark at/before a timestamp, for restore. [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/), [bookmark API](https://developers.cloudflare.com/api/resources/d1/subresources/database/subresources/time_travel/methods/get_bookmark/).
- **D1 is single-threaded.** Cloudflare says each individual D1 database processes one query at a time. An export that blocks requests therefore creates a production availability event, not merely a slow background copy. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- **R2 and D1 have no shared point-in-time snapshot.** R2 is strongly consistent for each read/write/delete and for each list operation; a list reports the bucket at that operation’s point in time. Multiple pages, D1 reference rows, the separate deletion ledger, and object reads are not one atomic cross-product snapshot. R2 exposes an object version token and ETag; ETag-conditional reads and version rechecks can detect a source change, but they do not preserve a deleted or overwritten body. Cloudflare’s S3 compatibility table marks GetBucketVersioning and PutBucketVersioning unsupported, so do not assume S3-style historical versions are available. [R2 consistency model](https://developers.cloudflare.com/r2/reference/consistency/), [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/).

## Existing source and importer contracts

The current operations runbook separates primary D1, the deletion ledger, and QUARANTINE R2. Privacy documentation says private owner erasure fences uploads, withdraws aggregates, writes an independently verified tombstone, removes owned R2 objects, and completes D1 removal; the deletion ledger suppresses erased data after restore. A main-D1-only dump cannot carry these cross-store effects or prove they are reconciled ([privacy reference](../reference/local-data-and-privacy.md), lines 198–200 and 301–314; [private owner erasure runbook](../runbooks/production-operations.md), lines 483–558).

The GCP candidate’s typed legacy importer intentionally refuses an ordinary live D1 source or caller-built “immutable” export descriptor. At candidate commit 2353603883078253a6d562b5ef250bc041cf7d2d, apps/worker/scripts/postgres-typed-legacy-transfer.mjs lines 25–35 says independent paged reads of live D1 are not a consistent snapshot; lines 121–147 admit only branded synthetic fixtures or sealed SQLite rehearsal sources. Lines 1190–1218 say byte sealing and SQLite integrity checks do not prove the remote export’s provenance or a cross-database freeze. Its page-based importer is staged rehearsal evidence only (lines 956–1022); it does not publish a reader or authorize erasure. Hashing an export after download therefore does not turn it into a production snapshot proof.

The GCP candidate’s apps/worker/typed-ingestion-migrations/0002_delivery_journal.sql is explicitly new-target-only and says it does not attach triggers to an existing production DB (lines 1–2). Its storage_ingestion_changes journal cannot be treated as a production-wide D1 change feed. The accountless retention snapshot is a useful bounded pattern, not a full-copy solution: apps/worker/src/accountless-retention-transfer-source.ts lines 1–13 describes a one-batch capture, immutable materialization, and trigger invalidation for opted-out accountless v1.1 retention markers; migration 0063 defines only that narrow proof-row family. The snapshot includes sensitive identity and credential-hash fields and is owner-only. It neither snapshots the other D1 tables nor coordinates QUARANTINE R2 or DELETION_LEDGER. Its presence in candidate source is not proof that migration 0063 is deployed in the reported live D1.

The primary checkout’s apps/worker/src/mutation-barrier.ts lines 1–9 says its fence is temporary and specific to the accountless schema move, makes no claim that reads from older Worker requests have completed, and is disabled in that source snapshot. It is not a production-wide export fence. The per-participant/day telemetry pin in apps/worker/src/telemetry-v1-source-selection.ts lines 188–228 records an analytical mutation epoch and input revision for a bounded selected vector; lines 267–270 recheck that vector. It is not a journal for all 174 tables or all R2/ledger changes. The production erasure implementation in apps/worker/src/participant-erasure.ts lines 87–93, 159–170, and 173–218 illustrates why the D1, deletion-ledger, and R2 lifecycles must be included in any cutover protocol.

The GCP candidate’s apps/worker/scripts/postgres-object-transfer-rehearsal.mjs is synthetic-only (lines 4–13). It pins an inventory digest and checks per-object versions during rehearsal, which is a good change-detection contract, but it is not a production snapshot service and does not create cross-store atomicity.

## Bounded next slices

### Test-only rehearsal

1. Keep the current GCP target test-only. First publish a synthetic product-schema inventory and gap map, then extend the existing typed importer only for the next explicitly selected table family and representative storage/v1.2 types; do not claim its 14-table legacy family covers all 174 tables or create a live D1 adapter.
2. In a disposable, small synthetic D1 only, test the documented export lifecycle and polling/cancellation behavior. Compare full versus no-data export behavior there and record duration and output size. This tests the API workflow without putting the serving production database through an export. If a D1 import is needed to seed that fixture, split files at or below Cloudflare’s 5 GiB Wrangler import limit. [D1 import/export guidance](https://developers.cloudflare.com/d1/best-practices/import-export-data/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
3. Exercise the PostgreSQL import with frozen synthetic SQLite input: exact schema/migration receipts; BLOB and integer handling; deterministic source/target row digests; bounded paging, retries and restart; changed-source refusal; and rejection of unknown tables/columns. The Cloudflare SQL export must first be converted to the local SQLite rehearsal format; the candidate importer then verifies local byte stability, not remote source provenance or consistency.
4. Use synthetic owners and objects to rehearse restore/erasure precedence: an erased owner stays excluded after replay; the independent deletion ledger tombstone remains authoritative; object overwrite/delete during pagination invalidates or stops the transfer; resumptions do not resurrect a missing old R2 object.
5. Keep all output aggregate-only and content-free. Do not log identifiers, object keys, telemetry rows, credentials, SQL dump contents, or raw manifests.

### Production prerequisite: choose one consistency model

**Option A — planned source freeze and export.** Before any production extraction, obtain an owner-approved maintenance window sized by a disposable export rehearsal. Stop or fence every write route and scheduled writer that can mutate the primary D1, the deletion ledger, or QUARANTINE object pointers/bodies. Verify there are no in-flight operations that can finish after the fence; the existing migration barrier is insufficient for that claim. Capture D1 and ledger bookmarks/watermarks and schema/migration receipts, export D1 while accepting that [Cloudflare documents query unavailability during export](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/), inventory and transfer R2 using pinned ETag/version checks while object writers and erasure remain fenced, then import into an isolated GCP staging target. Reconcile table counts and deterministic digests, deletion tombstones, R2 object references and bytes, authority state, and replay/rollback behavior before a separate cutover decision. Keep Cloudflare authoritative until every parity and rollback gate passes. The GCP test backend’s backup/health result is not a source backup or a production rollback proof.

**Option B — online base copy with change capture and a short final fence.** Install and qualify a source-side transactional change journal before starting the base copy. It must cover inserts, updates, deletes, authority/erasure changes, and schema changes for every transferred table, with ordered watermarks and a replayable tombstone policy. In parallel, define an object mutation ledger or copy-on-write protocol that captures R2 create/replace/delete intent and pins exact object generations; reconcile all D1 references and the separate deletion ledger against it. Copy a stable base, replay each source journal through recorded watermarks, then pause new writes briefly, drain in-flight operations, capture final D1/ledger/R2 watermarks and reconcile the tail before switching authority. Preserve a reversible target and source rollback path. The existing target-only ingestion journal, 0063 narrow retention snapshot, and object rehearsal do not satisfy these requirements. This is a substantial design/implementation slice; until it is qualified, online production transfer is not supported by the reviewed contracts.

## Explicit stop and remaining gates

Stop before any production export call if the intended workflow cannot accept the documented D1 query block or cannot keep polling through completion. Do not issue the export and then try to abort around serving impact; Cloudflare documents that failing to poll causes automatic cancellation, not that cancellation avoids the interval of unavailability. Do not substitute Time Travel restore, schema-only export, a post-download hash, or a GCP health check for a consistent source capture.

Before a production transfer, the remaining proof gates are: (1) owner choice between the maintenance-window and online-journal designs; (2) reviewed source code and deployment proof for the chosen write fence or change stream; (3) complete table, deletion-ledger, R2, and authority inventory with no private payload in evidence; (4) source export duration/size and target import conversion rehearsal on synthetic data; (5) full GCP route, authorization, privacy-erasure, replay, and rollback parity; and (6) a separately approved production source extraction and later cutover. None is established by this review.
