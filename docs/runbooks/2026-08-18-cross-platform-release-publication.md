# Cross-platform release publication runbook

This runbook defines the common evidence and publication order for macOS,
Windows, and Linux. It is an activation contract, not a claim that every
platform is currently released. The release manifest is the source of truth:
if a platform, architecture, format, channel, digest, or required native
assurance is absent, that subject is not an official TiboTattle release. Every
official artifact has a v1 manifest entry. Its `sbom` and `provenance` fields
are present but may be `null`; when `sbom` is an object, its required
`attestation` field is also present and may be `null`. `null` explicitly means
that the corresponding evidence was not published, not that the artifact is
unofficial.

The macOS operator sequence is in
[macos-stable-release-runbook.md](./macos-stable-release-runbook.md). The
independent user checks are in [verify-release.md](../verify-release.md), and
the design decision is in
[2026-08-18-cross-platform-release-trust.md](../decisions/2026-08-18-cross-platform-release-trust.md).

## 1. The common contract

Every final downloadable subject gets one artifact entry in the canonical
manifest generated by scripts/generate-release-evidence.js. The checked-in
interface is intentionally offline and deterministic:

~~~bash
npm run release:evidence:generate -- \
  --input <release-evidence-input.json> \
  --base-dir <staging-directory> \
  --output <release-manifest.json> \
  --sha256sums <SHA256SUMS>

npm run release:evidence:validate -- \
  --manifest <release-manifest.json> \
  --artifacts-dir <staging-directory> \
  --sha256sums <SHA256SUMS>
~~~

The input must bind the product, semver version, exact protected tag, exact
source commit, canonical HTTPS repository URL, and at least one artifact.
Each artifact identifies:

- channel: direct or store;
- platform: macos, windows, or linux;
- architecture and format;
- final filename, byte count, and SHA-256;
- `sbom`: an SPDX JSON SBOM whose subject SHA-256 is the final artifact digest,
  or `null` when no SBOM is published;
- `sbom.attestation`: a bundle/digest object inside a non-null `sbom`, or
  `null` when that SBOM attestation is not published;
- `provenance`: a Sigstore bundle with the same final-artifact subject digest,
  or `null` when no source/build evidence is published;
- the required native platform assurances;
- the updater mechanism, with updater metadata when enabled; and
- store provider/listing data and a machine-generated
  `store-delivery-receipt-v1` document only for a store artifact. The receipt
  must identify the final Store-retrieved subject, not an upload candidate.

The v1 generator requires these evidence keys in every artifact entry, but
allows the values to be `null`. The complete non-null set—SPDX SBOM,
`sbom.attestation`, and provenance, all bound to the exact final digest and
cryptographically verified by the trusted hosted finalizer—is the **attested
v1 profile/path**. A native/checksum-only artifact may publish with explicit
`null` evidence and may claim only the native/checksum assurances it actually
carries. It must not imply source-to-binary provenance.

The generator re-hashes supplied files and fails closed on path traversal,
symlinks, duplicate subjects, digest drift, source mismatch, invalid SPDX
documents, incomplete assurances, direct/store conflation, or non-canonical
ordering. The release descriptor is staging input; do not publish it when it
contains local paths or operator-only fields.

The protected attestation action emits the bundle paths and signer outputs
needed to enrich that descriptor. Operators must consume that generated or
enriched descriptor for the final manifest; do not hand-author attestation
metadata, signer identities, or bundle digests. If the caller workflow has not
yet materialized its generated descriptor output, stop at that boundary and
wire the caller to the action's generated-descriptor interface before
publishing.

The composite exposes the generated descriptor as
`steps.attest.outputs.enriched-release-descriptor-path` and exposes its base
directory as `steps.attest.outputs.enriched-release-descriptor-base-dir`. Pass
both outputs to `scripts/generate-release-evidence.js`; do not hand-author
signer, predicate, builder, run, runner, or bundle-digest metadata. If either
output is absent, stop publication at that boundary.

The separate SBOM-attestation bundle produced by the protected finalizer is
also a public release asset when this artifact uses the attested v1 profile. It
must be preserved beside the provenance bundle and verified against the same
final artifact subject. The canonical manifest records it as
`artifact.sbom.attestation`; artifact-specific filenames prevent two subjects'
bundles from being confused. The GitHub release is canonical for the manifest,
any non-null SBOM, and any non-null bundles. The website only exposes
availability and installer digest.

## 2. Native finalizer contracts

The common manifest does not replace native signing or installation checks.
Each platform finalizer must finish every byte-changing operation before
attestation or digest generation.

| Subject | Native final bytes | Required direct assurances | Current status |
| --- | --- | --- | --- |
| macOS direct | Developer ID-signed, notarized, stapled DMG; arm64 and any later architecture as separate subjects | cleanInstallSmokePassed, developerIdSigned, hardenedRuntime, notarizationAccepted, ticketStapled, gatekeeperAssessmentPassed | Existing arm64 local finalizer; protected GitHub attestation/publication caller remains a gate |
| macOS Store | Final App Store-delivered subject retrieved and hash-verified after acceptance, with a `store-delivery-receipt-v1` receipt | storePublisherVerified, storeBuildVerified, storeSignatureVerified; receipt binds provider/listing/source/final filename/bytes/SHA-256 and states `deliveryState: final`, `uploadCandidate: false` | Separate Store subject; never equate its bytes with the DMG or an upload candidate |
| Windows direct | One selected native x64 installer/package, after signing nested executables and final package | cleanInstallSmokePassed, authenticodeSigned, timestamped | Qualification only; no supported installer is currently claimed |
| Windows Store | Final Microsoft Store-delivered subject retrieved and hash-verified after acceptance, with a `store-delivery-receipt-v1` receipt | storePublisherVerified, storeBuildVerified, storeSignatureVerified; receipt binds provider/listing/source/final filename/bytes/SHA-256 and states `deliveryState: final`, `uploadCandidate: false` | Future separate subject; never describe the upload candidate as delivered |
| Linux direct | Native x86_64 AppImage or a package from a real signed repository | cleanInstallSmokePassed, artifactIntegrityVerified, plus distribution-specific detached/repository evidence where applicable | Qualification only; no supported artifact is currently claimed |
| Linux Store/repository | Final Flathub, Snap, APT, or RPM-delivered subject retrieved and hash-verified, with a `store-delivery-receipt-v1` receipt | storePublisherVerified, storeBuildVerified, storeSignatureVerified; receipt binds provider/listing/source/final filename/bytes/SHA-256 and states `deliveryState: final`, `uploadCandidate: false` | Future separate subject; a loose package or upload candidate is not repository evidence |

The current repository's assurance vocabulary and allowed Store providers live in
config/release-evidence.js. Do not invent a new assurance key in a release
descriptor without updating that checked-in contract and its tests.

Direct and Store subjects are never interchangeable:

- A website, GitHub release, or Homebrew DMG is a direct subject.
- Mac App Store, Microsoft Store, Flathub, Snap, APT, and RPM outputs are
  separate store/repository subjects.
- A Store may rebuild or re-sign an upload. Its digest, provenance, native
  acceptance, delivery receipt, and updater metadata must have their own
  manifest entry. The receipt itself is included in the manifest metadata and
  in `SHA256SUMS`.
- An update feed or updater manifest is another subject; it is not verified by
  the initial installer digest.

## 3. Protected finalizer permissions and workflow boundary

The native finalizer job that invokes GitHub artifact attestations must grant
only the permissions it needs:

~~~yaml
permissions:
  contents: read
  id-token: write
  attestations: write
  artifact-metadata: write
~~~

Use GitHub-hosted native runners for the platform being finalized. Do not run
untrusted pull-request code in a signing/attestation job. Production actions
and reusable workflows must be pinned to full commit SHAs; the repository
policy check is scripts/check-release-workflow-policy.mjs.

The repository's pinned actions/attest revision is:

~~~text
actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6  # v4.2.2
~~~

The checked-in caller-facing composite action is
.github/actions/attest-release-artifact/action.yml. It accepts the final
artifact path, SPDX path, evidence directory, and release-descriptor path. For
an artifact claiming the attested v1 profile/path, a protected native finalizer
calls it after all final-byte operations:

~~~yaml
- name: Attest the frozen final subject
  id: attest
  uses: ./.github/actions/attest-release-artifact
  with:
    artifact-path: <final-artifact>
    sbom-path: <artifact.spdx.json>
    evidence-directory: <evidence-directory>
    release-descriptor-path: <release-evidence-input.json>
~~~

Invoke the composite once for the frozen subject. The composite derives signer
identity from the trusted hosted job context; callers do not pass signer fields.
It invokes both pinned
`actions/attest` steps—one for SLSA provenance and one for the SPDX
`sbom.attestation`—then runs scripts/release-attestation-evidence.mjs for
preflight and collection. Do not add a second caller step for either
attestation. Its caller still owns the protected runner, permissions, exact-tag
gate, and publication order.

The composite preserves the emitted files as
`<artifact-filename>.provenance.bundle.json` and
`<artifact-filename>.sbom.bundle.json`, and exposes those paths in its outputs.
The checked-in collector checks regular non-symlink files, exact subject
digests, SPDX structure, descriptor association, and bundle copying. It never
creates a claim on its own, uploads an artifact, publishes a release, or signs
local bytes. If the action or checked-in evidence interface is missing, the
finalizer must stop.

A local macOS build can produce a valid signed/notarized DMG but cannot honestly
produce a GitHub Actions build attestation for that local checkout. Until the
protected native finalizer has run the pinned action against the exact final
bytes, the release may carry native signing and checksum evidence only, with
explicit `null` evidence fields; it must not claim GitHub source/build
provenance. The sanitized `.dmg.release.json`
receipt is a separate Sparkle updater input: the publisher intentionally places
it under a content-addressed R2 key, but that narrow publication does not make
it the canonical cross-platform manifest or a general public evidence file.

## 4. Final-byte order

Run the stages in this order for every native platform. Steps 6–8 are required
only for an artifact claiming the attested v1 profile/path; a
native/checksum-only artifact records explicit `null` evidence instead and may
skip those attestation steps.

1. Start from a clean checkout at the exact protected annotated version tag.
2. Build on the native controlled runner with the committed lockfile.
3. Run native tests and clean install/upgrade/uninstall checks.
4. Complete all byte-changing operations: package, sign nested binaries,
   sign the final installer, timestamp, notarize, staple, compress, or produce
   repository metadata as appropriate.
5. Freeze the final subject bytes. Record the file path and digest. Any
   mutation after this point invalidates every later evidence item.
6. For the attested v1 profile/path, produce the SPDX SBOM for that exact
   subject and verify its subject digest.
7. For the attested v1 profile/path, invoke the protected composite once; it
   runs both `actions/attest` steps and re-checks the frozen artifact/SBOM bytes.
8. For the attested v1 profile/path, preserve its artifact-specific provenance
   and `sbom.attestation` bundle outputs beside the final subject.
9. Generate and validate release-manifest.json and SHA256SUMS with
   scripts/generate-release-evidence.js.
10. Create a draft GitHub release and upload only reviewed public assets.
11. Copy every draft asset from the reviewed staging area into a fresh
    verification directory. Validate the manifest and SHA256SUMS and source
    identity there. For the attested v1 profile/path, also verify both
    artifact-specific attestation bundles. Do not call `gh release verify` on a
    draft; the fresh `gh release download` check runs after publication below.
12. Publish the draft, read back its immutable state, then run gh release verify
    and gh release verify-asset for the release and every uploaded asset.
13. Only after those post-publication checks pass, publish Sparkle/R2, Homebrew,
    website, Store, and updater metadata.

A release that fails any stage remains a draft or is stopped. Do not replace
assets in an immutable release. Rebuild from a new release tag if final bytes
or evidence need to change.

## 5. Draft and immutable release publication

The public asset set for a direct subject always includes the final platform
artifact, `release-manifest.json`, `SHA256SUMS`, and `verify-release.md`. Include
the following only when the artifact's manifest fields are non-null:

- the SPDX JSON SBOM when `artifact.sbom` is non-null;
- `<artifact-filename>.provenance.bundle.json` when `artifact.provenance` is
  non-null; and
- `<artifact-filename>.sbom.bundle.json` when
  `artifact.sbom.attestation` is non-null.

The complete non-null set is the attested v1 profile/path. A
native/checksum-only release publishes the baseline asset set and records
explicit `null` evidence fields; do not upload placeholder or stale bundles.

For a `store` channel subject, upload the final Store-retrieved artifact and
the full `store-delivery-receipt-v1` JSON document alongside the canonical
manifest and `SHA256SUMS`. The manifest's `artifact.store.receipt` metadata
must point to that receipt, and `SHA256SUMS` must contain its filename and
SHA-256. Never substitute a Store upload candidate, a receipt for a different
listing, or a receipt whose `deliveryState` is not `final` and
`uploadCandidate` is not `false`.

Do not publish release-evidence-input.json when it contains local paths or
operator-only fields. The sanitized macOS `*.dmg.release.json` is a special
case: pass it only to the guarded Sparkle publisher, which intentionally stores
it as a content-addressed updater receipt in R2. Do not copy that receipt into
general GitHub evidence or the website. Never publish credentials, signing
logs, raw local paths, or whole staging directories.

Create and upload a draft. Use a reviewed, existing notes file; keep the path
quoted so shell metacharacters cannot turn a placeholder into input/output
redirection:

~~~bash
TAG="vX.Y.Z"
REPO="adamallcock/tibotattle"
ARTIFACT="<final-artifact>"
ARTIFACT_NAME="$(basename "$ARTIFACT")"
RELEASE_MANIFEST="<release-manifest.json>"
SHA256SUMS="<SHA256SUMS>"
VERIFY_GUIDE="docs/verify-release.md"
NOTES_FILE="./release-notes/X.Y.Z.md"
test -s "$NOTES_FILE"

gh release create "$TAG" --repo "$REPO" --verify-tag --draft \
  --title "TiboTattle X.Y.Z" --notes-file "$NOTES_FILE"

# Native/checksum-only path (artifact.sbom and artifact.provenance are null):
gh release upload "$TAG" --repo "$REPO" \
  "$ARTIFACT" \
  "$RELEASE_MANIFEST" "$SHA256SUMS" "$VERIFY_GUIDE"
~~~

For the attested v1 profile/path, produce and verify the final SPDX file and
both artifact-specific bundles first, then use this upload command instead of
the baseline command, with these additional paths (and only these additional
paths):

~~~bash
SPDX="<artifact.spdx.json>"
SPDX_NAME="$(basename "$SPDX")"
EVIDENCE_DIRECTORY="<evidence-directory>"
PROVENANCE_BUNDLE="$EVIDENCE_DIRECTORY/$ARTIFACT_NAME.provenance.bundle.json"
SBOM_BUNDLE="$EVIDENCE_DIRECTORY/$ARTIFACT_NAME.sbom.bundle.json"

gh release upload "$TAG" --repo "$REPO" \
  "$ARTIFACT" "$SPDX" "$PROVENANCE_BUNDLE" "$SBOM_BUNDLE" \
  "$RELEASE_MANIFEST" "$SHA256SUMS" "$VERIFY_GUIDE"
~~~

Before publication, validate the exact draft staging directory locally. This
is an offline check: the validator reads only the files in the directory and
does not fetch release metadata. The protected action's generated/enriched
descriptor is the input used to create `release-manifest.json`; do not replace
it with hand-authored attestation metadata:

~~~bash
DRAFT_DIR="<fresh-draft-staging-directory>"
npm run release:evidence:validate -- \
  --manifest "$DRAFT_DIR/release-manifest.json" \
  --artifacts-dir "$DRAFT_DIR" \
  --sha256sums "$DRAFT_DIR/SHA256SUMS"
~~~

For the attested v1 profile/path only, the GitHub CLI bundle checks are
separate for provenance and `sbom.attestation`; run both with the exact release
constraints. Replace the placeholder signer values with those recorded in the
generated release manifest:

~~~bash
VERIFY_DIR="<fresh-draft-download-directory>"
COMMIT="<40-character source commit from the release manifest>"
SIGNER_WORKFLOW="<signer workflow path from the release manifest>"
SIGNER_DIGEST="<trusted signer-workflow commit from the release manifest>"

gh attestation verify "$VERIFY_DIR/$ARTIFACT_NAME" \
  --bundle "$VERIFY_DIR/$ARTIFACT_NAME.provenance.bundle.json" \
  --repo "$REPO" \
  --predicate-type "https://slsa.dev/provenance/v1" \
  --signer-workflow "$SIGNER_WORKFLOW" \
  --signer-digest "$SIGNER_DIGEST" \
  --source-ref "refs/tags/$TAG" \
  --source-digest "$COMMIT" \
  --deny-self-hosted-runners

gh attestation verify "$VERIFY_DIR/$ARTIFACT_NAME" \
  --bundle "$VERIFY_DIR/$ARTIFACT_NAME.sbom.bundle.json" \
  --repo "$REPO" \
  --predicate-type "https://spdx.dev/Document/v2.3" \
  --signer-workflow "$SIGNER_WORKFLOW" \
  --signer-digest "$SIGNER_DIGEST" \
  --source-ref "refs/tags/$TAG" \
  --source-digest "$COMMIT" \
  --deny-self-hosted-runners
~~~

`--bundle` reads the attestation bundle from the downloaded file rather than
fetching that bundle through the GitHub API; trusted-root resolution may still
require the normal GitHub CLI/network trust path. These checks can therefore be
run against a draft asset, but any verification failure is a publication gate
for the claimed attested profile. A checksum-only path does not run them and
must retain explicit `null` evidence fields.

After all draft checks pass, publish and read back:

~~~bash
gh release edit "$TAG" --repo "$REPO" --draft=false
gh release view "$TAG" --repo "$REPO" \
  --json tagName,isDraft,isImmutable,assets
test "$(gh release view "$TAG" --repo "$REPO" --json tagName --jq '.tagName')" = "$TAG"
test "$(gh release view "$TAG" --repo "$REPO" --json isDraft --jq '.isDraft')" = "false"
test "$(gh release view "$TAG" --repo "$REPO" --json isImmutable --jq '.isImmutable')" = "true"

# Download every published asset into a fresh directory. The validator below
# is deliberately offline after this download.
VERIFY_DIR="$(mktemp -d "${TMPDIR:-/tmp}/tibotattle-release-verify.XXXXXX")"
gh release download "$TAG" --repo "$REPO" \
  --dir "$VERIFY_DIR" --pattern "*" --clobber
npm run release:evidence:validate -- \
  --manifest "$VERIFY_DIR/release-manifest.json" \
  --artifacts-dir "$VERIFY_DIR" \
  --sha256sums "$VERIFY_DIR/SHA256SUMS"
~~~

Only now run the release-level checks:

~~~bash
gh release verify "$TAG" --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/$ARTIFACT_NAME" \
  --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/release-manifest.json" --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/SHA256SUMS" --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/verify-release.md" --repo "$REPO"
~~~

For an attested v1 profile/path, also run `gh release verify-asset` for the
published SPDX file and each non-null, artifact-specific bundle:

~~~bash
gh release verify-asset "$TAG" "$VERIFY_DIR/$SPDX_NAME" --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/$ARTIFACT_NAME.provenance.bundle.json" \
  --repo "$REPO"
gh release verify-asset "$TAG" "$VERIFY_DIR/$ARTIFACT_NAME.sbom.bundle.json" \
  --repo "$REPO"
~~~

Run verify-asset for every uploaded asset, not only the installer. If the
release is not immutable, the repository setting is not active, or a release
asset differs from the manifest, stop all downstream publication.

## 6. Platform activation gates

### macOS

The existing local finalizer is scripts/release-macos-app.js. It must finish
Developer ID signing, hardened runtime, Apple notarization, ticket stapling,
Gatekeeper assessment, and clean installation before freezing the DMG. The
protected GitHub native finalizer still needs a real caller workflow with the
permissions above, pinned actions, protected environments, exact-tag checks,
and a fresh draft-to-published verification rehearsal. Until then, do not
claim GitHub source/build provenance for the local DMG.

### Windows

Do not publish an EXE or MSIX merely because the Electron development
configuration exists. First choose one direct installer contract, qualify
native Windows x64 clean install/upgrade/uninstall and host-access behavior,
sign nested executables and the final package with Authenticode, and use a
trusted SHA-256 timestamp. Add the native finalizer and manifest entry only
after those checks pass. Microsoft Store output is a separate subject.

### Linux

Do not publish a loose AppImage, DEB, or RPM as a universally trusted Linux
release. First qualify a native x86_64 AppImage or a real signed package
repository, including credential/key storage, process/file access, clean
install, update/no-update, and uninstall behavior. Add detached signature or
repository metadata as the selected distribution requires. Flathub and Snap
are separate `store` channel subjects.

### Stores and updater channels

Store submissions must record their own provider/listing, publisher/build/
signature assurances, and a `store-delivery-receipt-v1` document after the final
Store-delivered subject has been retrieved and hash-verified. That receipt must
bind the provider, listing, source version/tag/commit/repository, final artifact
filename, bytes, and SHA-256, and must state `subjectKind: store-retrieved`,
`deliveryState: final`, and `uploadCandidate: false`. The manifest records the
receipt metadata and `SHA256SUMS` includes the receipt filename and digest. A
Store entry may describe only that delivered subject, never the upload
candidate. Homebrew checks the direct DMG URL and SHA-256 but does not establish
source provenance. Sparkle, Windows update metadata, and Linux repository
indices are separate signed/update subjects.

## 7. Fail-closed checklist

Stop before publication if any of these are true:

- the checkout is dirty, the source tag is not exact/annotated, or the commit
  is not the reviewed release commit;
- the final artifact changed after signing, timestamping, notarization, or
  attestation;
- a manifest field claims non-null SBOM, `sbom.attestation`, or provenance
  evidence but its asset is missing, malformed, or bound to a different subject
  digest; explicit `null` evidence is valid for a native/checksum-only path;
- the release descriptor has a different source identity, duplicate subject,
  direct/store mix-up, unsafe path, or incomplete native assurances;
- the native runner, signer workflow, action revision, or permissions are not
  the protected values;
- Windows/Linux tests or package signing are not complete for the claimed
  subject;
- draft assets were not downloaded and revalidated from a fresh directory;
- the published release is not immutable or gh release verify/verify-asset fails;
- the downstream feed, website, Homebrew, or Store subject has not been
  updated from the verified final bytes.

A checksum proves integrity of downloaded bytes. A native signature proves a
platform-specific publisher assertion. A GitHub attestation provides
source/build evidence only when independently verified against the exact
repository, source ref/digest, signer workflow, and runner constraints. None
is a universal safety or vulnerability guarantee. See verify-release.md for
the user-facing explanation and commands.
