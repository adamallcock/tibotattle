# G4 Privacy and Security Incident Response Runbook

## Release status

This runbook is deliberately pre-production. The central Worker has no public
deployment or public route, external participants are unauthorized, and the
fastest safe production containment action is therefore still to keep it
undeployed.

Primary incident owner: Adam Allcock.

Backup incident owner: **unassigned — blocking before G4**.

No real upload pilot may begin until a backup owner, contact channel, cloud
project/region, processor inventory, retention policy, and participant notice
are recorded in a dated approval receipt.

## Stop conditions

Stop enrollment, upload, processing, and publication immediately if any of the
following occurs:

- prompt, response, code, command, path, URL, email, credential, raw identifier,
  or other prohibited content reaches an official export, request, store, log,
  trace, error, or response;
- one participant can read, export, modify, rotate, revoke, or delete another
  participant's state;
- an object or database becomes publicly readable;
- enrollment or recovery abuse exceeds declared limits;
- validator isolation, key separation, or deletion cannot be proven;
- aggregate output exposes a suppressed or row-like contribution;
- a signing, encryption, recovery, upload, or administrator credential is
  suspected compromised; or
- the named owner cannot account for retained objects and derived outputs.

## Current containment controls

The current development checkpoint has:

- no public Worker route and `workers_dev: false`;
- an enrollment mode that can be set to `disabled`;
- strict D1-backed enrollment, upload-registration, processing, and publication
  controls that fail closed when their singleton state is unavailable;
- a local-only fixed-vocabulary operator command with explicit restoration
  confirmation and no administrator HTTP endpoint;
- a live loopback drill proving that a running Worker observes containment
  without restart or redeployment;
- fixed closed central routes;
- strict request/plaintext/record limits;
- privacy-canary rejection;
- opaque R2 object names;
- participant-scoped D1 reads, export, and deletion;
- personal results, export, revocation, individual contribution deletion, and
  full participant deletion that remain available during containment; and
- fixed error codes without payload reflection.

The following production controls are still missing and block a pilot:

- authenticated and audited production operation of the independent switches,
  including dual approval, rollback, and alert integration;
- edge admission and abuse-rate limiting;
- production KMS/keyring rotation and retired-key rejection;
- isolated validator identity/runtime;
- retention/lifecycle enforcement and deletion tombstones;
- backup/restore suppression of deleted participants;
- cloud audit/log field and retention inspection;
- alerts, budgets, queue controls, and safe operator dashboards; and
- a participant notification decision tree and contact channel.

## Development containment command

The current command is deliberately local-only. It rejects `--remote`.

```bash
npm --prefix apps/worker run control:collection -- \
  --action contain-all \
  --persist-to <isolated-local-state>

npm --prefix apps/worker run control:collection -- \
  --action restore-all \
  --confirm RESTORE_COLLECTION \
  --persist-to <isolated-local-state>
```

Independent `pause-*` and confirmed `resume-*` actions exist for `enrollment`,
`upload-registration`, `processing`, and `publication`. Do not reinterpret this
development command as a production administrator interface.

## Severity

| Severity | Example | Initial action |
|---|---|---|
| SEV-0 | Prohibited content escaped, cross-tenant access, public object, active key compromise | Disable every ingress/processing/publication path; revoke affected credentials/keys; preserve only content-free evidence; notify backup/reviewer |
| SEV-1 | Deletion failure, validator isolation failure, aggregate disclosure, repeated auth bypass | Disable affected subsystem and enrollment; quarantine outputs; begin bounded store/lineage inventory |
| SEV-2 | Rate-limit abuse, elevated rejection/cost, stale processing, non-sensitive availability failure | Pause enrollment or uploads; inspect fixed aggregate signals; do not request participant raw logs |
| SEV-3 | Single fixed-code client failure with no privacy or integrity impact | Record bounded diagnostic counts and investigate normally |

## Evidence boundary

Incident evidence may include only:

- request ID generated by the service;
- fixed event, route class, status, and error-code enums;
- coarse environment and service version;
- bounded counts, byte sizes, durations, queue ages, and timestamps;
- opaque internal object/database references restricted to incident operators;
  and
- code/config/artifact hashes.

Do not copy request bodies, decrypted records, access/recovery/invitation
capabilities, authorization headers, IP addresses, provider account
identifiers, raw logs, browser storage, or participant downloads into tickets,
chat, email, screenshots, or postmortems.

## Containment sequence

1. Confirm the symptom using fixed non-sensitive signals only.
2. Record UTC detection time, affected environment/version, severity, and named
   incident lead.
3. Disable the smallest safe path; for uncertainty involving content,
   authorization, or keys, disable all enrollment/upload/processing/publication.
4. Preserve code/config hashes and bounded service state. Do not preserve
   decrypted payloads merely for debugging.
5. Revoke affected access/upload/admin credentials and disable or rotate the
   affected key version. Do not destroy the old key until the retained-object
   inventory and deletion obligations are understood.
6. Enumerate affected opaque objects, D1 relations, derived analyses, aggregate
   versions, caches, backups, and participant notification references through
   bounded operator tooling.
7. Delete prohibited content immediately after the minimum legally/operationally
   required evidence decision. Quarantine access must remain least-privilege.
8. Rebuild or withdraw affected personal/public artifacts according to the
   approved deletion/public-history policy.
9. Decide participant notification using scope, sensitivity, access, harm,
   jurisdiction, and containment evidence. Never include another participant's
   data or capabilities in a notice.
10. Restore only from a reviewed version after the relevant drill/test passes
    and the named human approves reopening.

## Required pre-pilot drills

| Drill | Pass evidence |
|---|---|
| Global collection containment | A running loopback Worker observes all four D1 switches without redeploy; intake/publication stop; personal stats/export/deletion remain available; explicit restore resumes the pending upload; all personal D1 and R2 objects are removed |
| Canary content | Encrypted nested canary is rejected; no canonical row, log content, response value, or retained object remains |
| Stolen access capability | Rotation/revocation stops personal access without granting upload or recovery powers |
| Stolen recovery capability | Attempt limits engage; recovery rotates credentials; old capabilities fail; no enumeration signal |
| Invitation replay/Sybil | One grant creates one eligibility unit; replay/concurrency fail; open/local participants cannot unlock pilot aggregates |
| Cross-tenant request | Participant A cannot read/export/delete/rotate participant B under every endpoint and cache condition |
| Unauthorized object read | Public/other-service read fails; object name reveals no participant/provider/time metadata |
| Validator isolation failure | Processing stops before canonicalization; enrollment/upload switches remain independently controllable |
| Encryption-key compromise | Active key is disabled/rotated; retired key policy is enforced; development keys cannot decrypt production |
| Deletion failure | Retry/tombstone completes every store; restore does not resurrect deleted participant data |
| Bad aggregate release | Current artifact is withdrawn, caches invalidated, deletion/lineage rebuild runs, prior-release policy is applied |

Each drill produces a dated receipt with code/config hashes, fixed outcomes,
store counts, elapsed time, residual risks, and the human decision. Passing unit
tests alone is not a drill receipt.

The development global-containment drill has a dated
[verification receipt](./2026-07-26-g4-incident-containment-verification-receipt.md).
It is one required drill, not G4 approval.

## Restoration gate

Reopening requires:

- root cause and affected scope are bounded;
- prohibited content and unauthorized access paths are removed;
- all relevant credentials/keys are rotated or explicitly retained with a
  reason;
- deletion, backup/restore, and aggregate rebuild obligations are satisfied;
- regression/adversarial tests pass in the isolated environment;
- cloud logs and public endpoints are inspected directly;
- the participant-notification decision is recorded; and
- both the primary and backup incident owners approve restoration.

## Postmortem

Publish only a content-free operational postmortem containing timeline,
fixed-category impact, control failures, remediation, owners, deadlines, and
verification links. Do not publish participant counts smaller than the approved
disclosure threshold, exact participant activity times, opaque identifiers,
credentials, object names, or payload-derived examples.
